## 1. 목적과 범위

요구사항정의서(IM-001 v1.0, 41건)의 요구사항마다 시험 항목 하나를 두고, 그 요구사항이 PoC 수준에서 충족되는지 확인한다.
판정 기준은 과업지시서 Ⅱ.1 나항(대표 도구·대표 데이터셋 우선, 전 항목 연동 강제 없음)과 Ⅱ.5 나항(구조와 운영 개념의 시연 가능성)이다.

- 시험 번호는 IM-001 의 요구사항 순서대로 매긴다. 번호는 재사용하지 않는다.
- 이 문서의 판정은 **수행사의 검증 판정**이다. 발주기관의 인수 확인은 따로 받고, 받으면 판정을 `인수 확인`으로 바꾼다.
- PR 병합, CI 통과, 이슈 닫힘은 그 자체로 검증이 아니다. 아래 절차대로 확인한 기록이 있어야 `검증 완료`로 적는다.
- 시험에서 나온 결함은 결함관리대장(IM-006)에 DEF 번호로 남긴다.

## 2. 시험 방법과 판정 값

| 방법 | 뜻 | 증거 |
|---|---|---|
| `T` 테스트 | 자동 시험이나 실제 조작으로 기대 결과를 재현한다 | 시험 실행 기록, 응답·화면 기록 |
| `D` 시연 | 실제 화면에서 시나리오대로 조작해 보인다 | 화면 기록, 조작 순서 |
| `R` 공식검토 | 문서·코드·설정을 대조해 확인한다 | 검토 기록(대조한 파일·항목) |

| 판정 | 뜻 |
|---|---|
| 미착수 | 아직 시험하지 않았다 |
| 검증 중 | 일부 절차를 수행했고 남은 절차가 있다 |
| 보완 필요 | 기대 결과와 다른 점이 나왔다. 결함(IM-006) 또는 보완 이슈로 넘겼다 |
| 재검증 대기 | 보완을 마쳤고 다시 시험할 차례다 |
| 검증 완료 | 수행사가 절차를 모두 수행했고 기대 결과와 같다. 남은 제한은 비고에 적는다 |
| 인수 확인 | 발주기관이 결과를 확인했다 |

## 3. 시험 환경

| 구분 | 환경 | 비고 |
|---|---|---|
| 자동 시험 | 시험용 DB(임시 저장소, 시험마다 비움) + `pytest`·`vitest`. 같은 시험이 GitHub Actions 에서 PR 마다 돈다 | 개발·공개 DB 를 시험에 쓰지 않는다 |
| 조작 시험 | 내부 검증 환경. 공개 환경과 웹·API·DB·문서 저장소를 따로 둔다 | 공개 환경에서는 시험하지 않는다 |
| 시험 사업 | 검증·인계 사업(IM-001 v1.0 등록), 거절 사례용 `[시험]` 사업 | 확정은 사업마다 한 번이라 거절 사례는 `[시험]` 사업에서도 본다 |
| 시험 계정 | 수행사가 만든 발주기관·용역사 역할 계정 | 이 계정의 확정·승인은 공식 인수가 아니다 |
| 모델 | 로컬 모델 서버(Ollama). 임베딩 `bge-m3`(1024차원) | 답변 모델은 시험 기록에 이름을 적는다 |

## 4. 수행 순서

관련 요구사항을 묶어 한 흐름으로 시험한다. 한 요구사항이 여러 묶음에 걸치면 모든 묶음을 마쳐야 `검증 완료`다.

| 묶음 | 흐름 |
|---|---|
| 1 | 명세서 등록 → 항목 확인 → 제출 → 요구사항 목록 확정 → 원문 위치·이력·권한 |
| 2 | 조직·참여 업체·접근권한 |
| 3 | GitHub·Redmine 연결·수집 |
| 4 | 표준화·추적관계 |
| 5 | WBS·산출물 |
| 6 | 지표·조회·AI 질의 |
| 7 | 완료 판정·회귀 |
| 8 | 운영·인계(설치·백업·복원) |

## 6. 시험 절차

요구사항마다 실제 조작으로 확인할 장면이다. 자동 시험은 5절에 적은 파일을 돌린다.
절차 안에 예로 든 요구사항 코드는 시험 대상이 아니다. 시험 대상은 번호 줄의 코드 하나다.

- **TST-001** `SWFR.CON.001` 커넥터는 공통 인터페이스를 구현하며, 신규 도구 연동이 커넥터 구현체 추가만으로 가능해야 한다 (시나리오 S2-2)
  - 절차: 검토자가 `도구 연동`에서 GitHub·Redmine 연결을 하나씩 만들고 수집 → `동기화 이력`에 두 연결이 같은 모양(회차·건수·상태)으로 보이고, 코드 검토에서 상위 계층에 도구별 분기가 없다
- **TST-002** `SWFR.CON.002` 연동 대상과 필드 매핑을 코드 수정 없이 설정으로 변경할 수 있어야 한다 (시나리오 S2-3)
  - 절차: 소유 업체 용역사가 `PATCH /connections/{id}/mapping` 으로 `riskTracker` 를 바꾸고 전체 수집 → 그 트래커 일감이 `일반 이슈`가 아니라 리스크로 분류된다(화면 없음, API 시연)
- **TST-003** `SWFR.CON.003` GitHub에서 저장소·커밋·Pull Request·이슈·마일스톤을 수집해야 한다 (시나리오 S2-2)
  - 절차: 용역사가 `도구 연동`에서 GitHub 연결 → 수집 → `동기화 이력`의 커밋·PR·이슈·마일스톤 건수가 GitHub 원본과 같고, `일반 이슈`에 원본 번호 링크와 마일스톤이 보인다
- **TST-004** `SWFR.CON.004` Redmine에서 프로젝트·이슈·버전·트래커·이슈관계를 수집해야 한다 (시나리오 S2-3)
  - 절차: 용역사가 Redmine 연결 → 수집 → `일반 이슈`에 RM-n 일감이 트래커·버전과 함께 원본 건수만큼 보이고, 이슈 관계가 추적 링크로 이어진다
- **TST-005** `SWFR.CON.005` 마지막 수집 시점 이후의 변경분만 수집하며, 반복 수집이 재현 가능해야 한다 (시나리오 S2-5·S2-7·S1-6)
  - 절차: 용역사가 같은 연결을 세 번 수집(그 사이 원천에서 일감 하나만 수정) → 변경 없는 회차는 새로 반영 0, 수정 회차는 그 한 건만 바뀌고 세 회차 결과가 재현된다
- **TST-006** `SWFR.CON.006` 연동 대상 도구의 인증정보를 등록하고 연결 상태를 확인할 수 있어야 한다 (시나리오 S2-2·S2-3)
  - 절차: 용역사가 `도구 연동`에서 권한 부족 토큰으로 연결 확인 → 부족 권한 안내, 정상 토큰 → "확인됨", 저장 뒤 목록에는 토큰 끝 4자리만 보인다
- **TST-007** `QUR.CON.001` 커넥터는 원천 도구의 데이터를 변경하지 않아야 한다 (읽기 전용) (시나리오 S2-2·S2-5)
  - 절차: 검토자가 수집 전후 GitHub·Redmine 원본(이슈 수정 시각·감사 기록)을 대조 → 쓰기 흔적이 없고, 정적 시험이 어댑터 쓰기 호출 0 을 보인다
- **TST-008** `SWFR.CON.007` PDF·DOCX·XLSX·HWP·HWPX에서 텍스트와 표를 추출하되, 표는 행·열 구조를 유지해야 한다 (시나리오 S2-4·S1-4)
  - 절차: 용역사가 `자료`에 PDF·DOCX·XLSX·HWP·HWPX 를 하나씩 올림 → 모두 처리 완료, 자료 상세에서 글과 표(행·열 유지)가 보인다

- **TST-011** `SWFR.PIP.003` 요구사항·이슈·산출물·커밋 간의 추적관계를 생성해야 한다 (시나리오 S1-3)

### 8.3 절차 (INST-S01 ~ INST-S09)

집계 질의(INST-S09)는 **합성 자료(IM-009)를 투입한 집계 시험**이다. 실제 도구(GitHub·Redmine)에서 수집하는 시험은 폐쇄망 안에 그 도구가 있어야 하므로 이 절의 대상이 아니며, 있으면 별도 항목(INST-S10, 환경 전제)으로 둔다.

| ID | 단계 | 입력 | 기대 결과 | 실패 시 기록 |
|---|---|---|---|---|
| INST-S01 | **인터넷 차단 확인** | 호스트에서 외부 주소(예: 공인 DNS·패키지 저장소·GHCR) 접속 시도 | 전부 실패(이름 풀이 실패 또는 연결 거부). 결과를 캡처 | 차단이 안 되면 시험 중단 |
| INST-S02 | 반입 적재 | `docker load` 이미지 5종, 모델 파일 적재 | 이미지·모델 목록에 반입 태그·다이제스트가 보이고 체크섬이 8.2 와 같다 | 불일치 항목과 값 |
| INST-S03 | 설정 준비 | `.env` 를 예시에서 복사, 비밀값(JWT 키·연결 토큰 키·DB 비밀번호)을 현장에서 생성 | 필수 키 전부 설정. 값은 기록하지 않음 | 빠진 키 이름 |
| INST-S04 | DB 초기화·마이그레이션 | migrate 이미지 실행 | 최신 버전까지 성공, 시작 로그에 외부 접속 시도 없음 | 실패한 V 번호와 메시지 |
| INST-S05 | 기동 | compose 로 DB → 모델 서버 → API → 웹 순 | health 200, 기동 로그에 외부 다운로드·외부 호출 없음 | 실패 서비스·로그 발췌 |
| INST-S06 | 로그인·기본 조회 | 관리자 계정 생성(8.1 수행자) → 로그인 → 발주기관 조직·계정 발급 → 사업 등록 | UC-001-S01·UC-002-S01 기대 결과 | 실패 단계 |
| INST-S07 | 문서 처리(임베딩 온프레미스) | TD-DOC-4 업로드 | 처리 완료, 색인 모델 `bge-m3`, 외부 호출 없음 | 실패 사유 |
| INST-S08 | 시험 자료 투입·건수 확인 | IM-009 1~5절을 TD-PRJ-1 에 투입(투입 스크립트, 재생 자료. 외부 도구 호출 없음) → 상태 S0 | 이슈 16(일반 이슈 9), 요구사항 3, WBS 말단 5, 제출본 2, 문서 색인 완료. IM-009 7.3 과 건수 일치 | 불일치 항목과 값 |
| INST-S09 | 온프레미스 질의(합성 자료 집계) | UC-060-S01·S02·S04 를 온프레미스 생성 모델로 | S01 22종·2쪽 출처, S02 일반 이슈 9건(INST-S08 자료 기준), S04 근거 부족. 수치·유효 출처·근거 일치(UC-060-S09 판정 기준), 모델 배지 온프레미스, 네트워크 모니터 외부 호출 0 | 실패 질문·응답 |
| INST-S10 | (환경 전제) 폐쇄망 안 실제 도구 수집 | 폐쇄망 내부에 GitHub·Redmine 이 있을 때만 UC-011-S01 | 수집 성공·건수 일치 | 도구가 없으면 「해당 없음」으로 기록(실패 아님) |

### 8.4 판정 기준 (IT-01 ~ IT-10)

| ID | 기준 | 확인 방법 |
|---|---|---|
| IT-01 | 시험 내내 호스트·컨테이너에서 외부 네트워크 연결이 한 번도 성립하지 않는다 | INST-S01 캡처 + 시험 중 네트워크 모니터(연결 시도 로그) |
| IT-02 | 반입한 모든 이미지·모델의 체크섬이 8.2 와 일치한다 | INST-S02 |
| IT-03 | 외부 다운로드 없이 마이그레이션이 최신 버전까지 성공한다 | INST-S04 로그 |
| IT-04 | API·웹·DB·모델 서버가 기동하고 health 가 정상이다 | INST-S05 |
| IT-05 | 관리자·발주기관 계정 생성과 로그인이 된다 | INST-S06 |
| IT-06 | 문서 업로드·추출·색인이 온프레미스 임베딩으로 완료된다 | INST-S07 |
| IT-07 | 합성 자료 투입 뒤 건수가 IM-009 와 일치하고, 온프레미스 생성 모델로 문서·집계·근거 부족 질의가 UC-060 판정 기준대로 동작한다 | INST-S08·S09 |
| IT-08 | 설정·로그·화면 어디에도 비밀값 원문이 없다 | INST-S03·S05 로그 검사 |
| IT-09 | 반입 목록 문서만 보고 절차를 따라갈 수 있다(문서 외 구전 지식 없음) | 수행자 기록 |
| IT-10 | 결과 기록에 환경·버전·다이제스트·기준일·수행자·확인자가 있다 | 7절 기록 |

통과 = IT-01~IT-10 전부 충족. 하나라도 미충족이면 실패로 기록하고 사유를 남긴다. **클라우드 위임 모델이나 인터넷 연결 환경에서 한 시험은 이 절의 통과로 세지 않는다.**

### 8.5 사용자 준비 사항

- 반입 장비(OS·GPU 사양)와 반입 매체 결정(8.1 결정 필요 두 건).
- 온프레미스 생성 모델 선정.
- 수행자·확인자 지정과 일정.
- 시험용 비밀값은 현장에서 생성하고 시험 뒤 폐기한다.
