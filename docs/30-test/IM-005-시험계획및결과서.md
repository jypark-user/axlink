# AX Link 시험계획·결과서 (IM-005)

**2026년 AX 프로젝트 관리 운영 프레임워크 개발 용역**
발주 (재)전주정보문화산업진흥원 · 수행 유저인사이트(주)
**v0.1 초안** · 2026-11-02 · 시험 수행 중

> v0.1 은 시험 항목 41건의 번호(TST-001~041)와 절차를 정하고, 첫 묶음(명세서 등록·확정)의 결과를 적은 판이다.
> 나머지 묶음은 수행하면서 결과 열과 7절 수행 기록을 채운다.

## 1. 목적과 범위

요구사항정의서(IM-001 v1.0, 41건)의 요구사항마다 시험 항목 하나를 두고, 그 요구사항이 PoC 수준에서 충족되는지 확인한다.
판정 기준은 과업지시서 Ⅱ.1 나항(대표 도구·대표 데이터셋 우선, 전 항목 연동 강제 없음)과 Ⅱ.5 나항(구조와 운영 개념의 시연 가능성)이다.

- 시험 번호는 IM-001 의 요구사항 순서대로 매긴다. 번호는 재사용하지 않는다.
- 이 문서의 판정은 **수행사의 검증 판정**이다. 발주기관의 인수 확인은 따로 받고, 받으면 판정을 `인수 확인`으로 바꾼다.
- PR 병합, CI 통과, 이슈 닫힘은 그 자체로 검증이 아니다. 아래 절차대로 확인한 기록이 있어야 `검증 완료`로 적는다.
- 시험에서 나온 결함은 결함관리대장(IM-006)에 DEF 번호로 남긴다.

## 2. 시험 방법과 판정 값

| 방법 | 뜻 | 증거 |
|---|---|---|
| `T` 테스트 | 자동 시험이나 실제 조작으로 기대 결과를 재현한다 | 시험 실행 기록, 응답·화면 기록 |
| `D` 시연 | 실제 화면에서 시나리오대로 조작해 보인다 | 화면 기록, 조작 순서 |
| `R` 공식검토 | 문서·코드·설정을 대조해 확인한다 | 검토 기록(대조한 파일·항목) |

| 판정 | 뜻 |
|---|---|
| 미착수 | 아직 시험하지 않았다 |
| 검증 중 | 일부 절차를 수행했고 남은 절차가 있다 |
| 보완 필요 | 기대 결과와 다른 점이 나왔다. 결함(IM-006) 또는 보완 이슈로 넘겼다 |
| 재검증 대기 | 보완을 마쳤고 다시 시험할 차례다 |
| 검증 완료 | 수행사가 절차를 모두 수행했고 기대 결과와 같다. 남은 제한은 비고에 적는다 |
| 인수 확인 | 발주기관이 결과를 확인했다 |

## 3. 시험 환경

| 구분 | 환경 | 비고 |
|---|---|---|
| 자동 시험 | 시험용 DB(임시 저장소, 시험마다 비움) + `pytest`·`vitest`. 같은 시험이 GitHub Actions 에서 PR 마다 돈다 | 개발·공개 DB 를 시험에 쓰지 않는다 |
| 조작 시험 | 내부 검증 환경. 공개 환경과 웹·API·DB·문서 저장소를 따로 둔다 | 공개 환경에서는 시험하지 않는다 |
| 시험 사업 | 검증·인계 사업(IM-001 v1.0 등록), 거절 사례용 `[시험]` 사업 | 확정은 사업마다 한 번이라 거절 사례는 `[시험]` 사업에서도 본다 |
| 시험 계정 | 수행사가 만든 발주기관·용역사 역할 계정 | 이 계정의 확정·승인은 공식 인수가 아니다 |
| 모델 | 로컬 모델 서버(Ollama). 임베딩 `bge-m3`(1024차원) | 답변 모델은 시험 기록에 이름을 적는다 |

## 4. 수행 순서

관련 요구사항을 묶어 한 흐름으로 시험한다. 한 요구사항이 여러 묶음에 걸치면 모든 묶음을 마쳐야 `검증 완료`다.

| 묶음 | 흐름 |
|---|---|
| 1 | 명세서 등록 → 항목 확인 → 제출 → 요구사항 목록 확정 → 원문 위치·이력·권한 |
| 2 | 조직·참여 업체·접근권한 |
| 3 | GitHub·Redmine 연결·수집 |
| 4 | 표준화·추적관계 |
| 5 | WBS·산출물 |
| 6 | 지표·조회·AI 질의 |
| 7 | 완료 판정·회귀 |
| 8 | 운영·인계(설치·백업·복원) |

## 6. 시험 절차

요구사항마다 실제 조작으로 확인할 장면이다. 자동 시험은 5절에 적은 파일을 돌린다.
절차 안에 예로 든 요구사항 코드는 시험 대상이 아니다. 시험 대상은 번호 줄의 코드 하나다.

- **TST-001** `SWFR.CON.001` 커넥터는 공통 인터페이스를 구현하며, 신규 도구 연동이 커넥터 구현체 추가만으로 가능해야 한다 (시나리오 S2-2)
  - 절차: 검토자가 `도구 연동`에서 GitHub·Redmine 연결을 하나씩 만들고 수집 → `동기화 이력`에 두 연결이 같은 모양(회차·건수·상태)으로 보이고, 코드 검토에서 상위 계층에 도구별 분기가 없다
- **TST-002** `SWFR.CON.002` 연동 대상과 필드 매핑을 코드 수정 없이 설정으로 변경할 수 있어야 한다 (시나리오 S2-3)
  - 절차: 소유 업체 용역사가 `PATCH /connections/{id}/mapping` 으로 `riskTracker` 를 바꾸고 전체 수집 → 그 트래커 일감이 `일반 이슈`가 아니라 리스크로 분류된다(화면 없음, API 시연)
- **TST-003** `SWFR.CON.003` GitHub에서 저장소·커밋·Pull Request·이슈·마일스톤을 수집해야 한다 (시나리오 S2-2)
  - 절차: 용역사가 `도구 연동`에서 GitHub 연결 → 수집 → `동기화 이력`의 커밋·PR·이슈·마일스톤 건수가 GitHub 원본과 같고, `일반 이슈`에 원본 번호 링크와 마일스톤이 보인다

  - 절차: 검토자가 연결 등록 뒤 화면·API 응답·서버 로그·DB 를 대조 → 토큰 원문은 어디에도 없고 DB 에는 암호문, 다른 업체 사용자 응답에는 힌트도 없다
- **TST-040** `SER.SEC.002` 외부 인터넷 접속 없이 설치·구동이 가능해야 하며, 필요한 반입 요소를 문서화해야 한다 (시나리오 기반)
  - 절차: 운영자가 인터넷이 없는 새 서버에서 반입 목록과 구축 매뉴얼만으로 설치 → 로그인·조회·문서 처리·질의가 된다
- **TST-041** `SER.SEC.003` 발주기관·용역업체 역할을 구분하고, 용역업체는 자신이 연결된 프로젝트만 조회할 수 있어야 한다 (시나리오 S2-1·S2-6)
  - 절차: 용역사 A 가 참여하지 않은 사업 주소를 직접 열면 403, `사업 목록`에는 자기 사업만, 같은 사업 참여 업체 B 의 연결 설정 변경은 거절된다
