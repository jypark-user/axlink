# 로컬 실행 절차

개발 환경 전체를 도커로 띄운다. DB·마이그레이션·Ollama·API·웹이 컨테이너다. Redmine 은 선택 실행이다.
호스트에서 직접 돌리는 방법은 아래 "호스트 직접 실행"에 대안으로 남겨 둔다.
근거는 [ARC-001](../20-design/ARC-001-백엔드-언어-파이썬-전환.md), 운영 배포는
[배포-운영-절차](../40-manual/배포-운영-절차.md).

## 1. 도커로 전체 실행 (기본)

처음 한 번은 저장소 루트에 `.env` 를 둔다(`.env.example` 참고). 데이터가 이미 있으면
`AXLINK_SECRET_KEY` 는 원래 값을 그대로 둔다. 새 키로 바꾸면 저장된 도구 연결 토큰을 풀 수 없다.

실행 방법은 두 가지다.

| 목적 | 명령 | 고친 소스 반영 |
|---|---|---|
| 일반 실행 | `docker compose -f infra/docker-compose.yml up -d --build` | 안 됨(다시 `--build` 해야 반영) |
| 개발하며 실행 | `docker compose -f infra/docker-compose.yml watch` | 됨. `app/`·`frontend/` 를 고치면 컨테이너로 옮긴다 |

- `watch` 는 이미지를 만들고 일반 실행과 같은 서비스를 띄운 뒤, 파일을 지켜본다.
- `watch` 창을 닫거나 Ctrl+C 로 끝내도 이미 뜬 서비스는 계속 돈다. 파일 반영만 멈춘다.
- 브라우저에서 <http://localhost:5173> 을 연다.

| 서비스 | 컨테이너 | 주소 |
|---|---|---|
| 웹(Vite 개발 서버) | `axlink-web` | <http://localhost:5173> |
| API(uvicorn, 재시작 감시) | `axlink-api` | <http://127.0.0.1:8080/api/health> |
| PostgreSQL + pgvector | `axlink-postgres` | `localhost:15432` |
| Flyway | `axlink-flyway` | 띄울 때마다 한 번 돌고 끝난다 |
| Ollama | `axlink-ollama` | `localhost:11434` |
| Redmine(선택) | `axlink-redmine` | <http://localhost:3000> |

- **기동 순서.** postgres 준비 → flyway 성공 → api 준비 → web 이다. flyway 가 실패하면 API 가 뜨지 않는다.
- **Windows 폴더를 붙이지 않는다.**
  - API·웹·Flyway 는 소스(`app/`, `frontend/`, `db/migration/`)를 이미지에 넣어 쓴다.
  - 도커가 Windows `D:` 를 붙여 두는 연결(9p)이 10-01 에 여러 번 끊겨, 붙여 쓰던 컨테이너가 I/O 오류를 냈기 때문이다.
  - 호스트의 `.env` 파일·`.git`·`var`·`node_modules`·`.venv` 는 컨테이너에 들어가지 않는다. 비밀값은 `.env` 를 컴포즈가 환경변수로만 넘긴다.
- **watch 가 하는 일.**

  | 무엇이 바뀌면 | 하는 일 |
  |---|---|
  | `app/` | 컨테이너로 옮기고 API 가 다시 뜬다 |
  | `frontend/` | 컨테이너로 옮기고 Vite 가 반영한다 |
  | `pyproject.toml`·`frontend/package*.json` | 해당 이미지를 다시 만든다 |
  | `db/migration/` | 마이그레이션 이미지를 다시 만든다 |

- **데이터.**
  - DB·Ollama·Redmine 은 기존 이름 있는 볼륨(`axlink_pgdata`, `axlink_ollama`, `axlink_redminedb`, `axlink_redminefiles`)을 그대로 쓴다.
  - 업로드 문서와 수집한 저장소 파일은 `axlink_documents` 볼륨(`/data/documents`)이다. 10-01 에 호스트 `var/documents` 에서 옮겼다. 호스트의 원본은 지우지 않고 남겨 두었다(되돌릴 때 쓴다).
- **멈추기와 다시 띄우기.**
  - 멈출 때는 `docker compose -f infra/docker-compose.yml stop`, 다시 띄울 때는 `up -d` 다.
  - **`down` 을 쓰지 않는다.** 이 프로젝트의 컨테이너를 지운다. `-v` 를 붙이면 개발 데이터 볼륨까지 지운다.
- **Docker 를 다시 시작한 뒤.**
  - 일반 실행: 다시 실행할 것이 없다. 컨테이너는 `restart: unless-stopped` 라 스스로 다시 뜬다(직접 멈춘 것은 그대로 멈춰 있다).
  - 개발하며 실행: `watch` 는 Docker 와 함께 끊기므로 다시 실행한다. 서비스는 이미 떠 있으니 `docker compose -f infra/docker-compose.yml watch --no-up` 으로 파일 반영만 다시 붙여도 된다.
- **Redmine(샘플 원천)은 선택 실행이다.** 위 두 명령은 Redmine 을 띄우지 않는다. 필요할 때만:

  ```bash
  docker compose -f infra/docker-compose.yml --profile redmine up -d redmine-db redmine
  ```

  10-01 에 기동 중 세그폴트가 반복돼 멈춰 두었다. PC 점검 뒤에 다시 띄운다.
- **스케줄러.**
  - API 안에 일별 스냅샷·주기 수집 스케줄러가 있다. 그래서 API 는 컨테이너 하나만 띄운다.
  - 도커로 띄운 동안 호스트에서 uvicorn 을 같이 돌리지 않는다. 같은 DB 에 스케줄러가 둘이 된다.

### 문서 볼륨 이전 전으로 되돌리기

10-01 이전에는 API 가 저장소를 `/app` 에 통째로 붙여 쓰고, 문서를 호스트 `var/documents` 에 두었다.
되돌릴 때는 다음 순서로 한다.

1. 이전 전 설정을 다시 둔다. 보관본은 `var/archive/2026-10-01-docs-volume/docker-compose.before.yml`·`api.Dockerfile.before` 다.
2. 이전 뒤 새로 올린 문서가 있으면 볼륨에서 호스트로 먼저 꺼낸다.

   ```bash
   docker cp axlink-api:/data/documents/. var/documents/
   ```

3. `D:` 연결이 끊겨 있으면 Docker Desktop 을 다시 시작한다.
4. `docker compose -f infra/docker-compose.yml up -d --build api` 를 실행한다.

볼륨(`axlink_documents`)은 되돌린 뒤에도 지우지 않는다.

### DB 에 저장된 생성 모델 주소

관리 화면에서 고른 생성 모델 서버 주소는 DB(`llm_setting`, `llm_model_cache`)에 저장된다.
컨테이너 API 에서는 `localhost` 가 자기 자신이라, 이 주소가 `http://ollama:11434` 여야 한다.
호스트 실행으로 되돌릴 때는 다시 `http://localhost:11434` 로 바꾼다.

```bash
# 도커 실행으로 옮길 때
docker exec axlink-postgres psql -U axlink -d axlink -c "begin;   update llm_model_cache set base_url='http://ollama:11434' where base_url='http://localhost:11434';   update llm_setting set base_url='http://ollama:11434' where base_url='http://localhost:11434'; commit;"
# 호스트 실행으로 되돌릴 때는 두 주소를 맞바꿔 같은 문장을 실행한다
```

임베딩 주소는 DB 가 아니라 환경변수(`AXLINK_EMBEDDING_BASE_URL`)다. 컴포즈가 컨테이너망 주소를 준다.

## 2. 호스트 직접 실행 (대안)

도커 API·웹을 먼저 멈춘다(`docker compose -f infra/docker-compose.yml stop api web`).
DB·Ollama 주소를 위 절에 따라 `localhost` 로 되돌린 뒤 띄운다.

```bash
docker compose -f infra/docker-compose.yml up -d postgres flyway ollama
py -m venv .venv
.venv/Scripts/python -m pip install -e ".[dev]"
.venv/Scripts/python -m uvicorn app.main:app --port 8080 --reload
cd frontend && npm ci && npm run dev
```

- 호스트에 로컬 PostgreSQL 이 있어 컨테이너는 **15432** 로 노출한다.
- pgvector·pg_trgm·pgcrypto 확장은 V1 이 설치한다.
- `/api` 는 vite 가 8080 으로 프록시한다(`frontend/vite.config.ts`).
- 호스트 실행은 문서를 `var/documents` 에서 읽는다. 10-01 이후 컨테이너가 받은 문서는 `axlink_documents` 볼륨에만 있으니 `docker cp axlink-api:/data/documents/. var/documents/` 로 먼저 꺼낸다.

## 3. 외부 주소로 열기 (/ax-link/)

개발 PC 를 `https://dev.userinsight.co.kr/ax-link/` 로 연다. 앞단 프록시가 `/ax-link/` 만 이 PC 의
5173 으로 넘긴다. 웹은 Vite 개발 서버 대신 빌드본(nginx)이고 API 는 운영 이미지다. watch 는 없다.

```bash
V=0.2.0-<짧은 커밋>
docker build -f docker/api.Dockerfile --target prod --build-arg AXLINK_VERSION=$V -t axlink-api:$V .
docker build -f docker/web.Dockerfile --target prod --build-arg AXLINK_VERSION=$V \
  --build-arg AXLINK_BASE_PATH=/ax-link/ -t axlink-web:$V .
docker build -f docker/migrate.Dockerfile -t axlink-migrate:$V .
AXLINK_VERSION=$V docker compose -f infra/docker-compose.yml -f infra/docker-compose.ext.yml \
  up -d --no-deps --no-build api web
```

- Git Bash 에서는 빌드 전에 `export MSYS_NO_PATHCONV=1`. 안 하면 `/ax-link/` 가 `C:/Program Files/Git/ax-link/`
  로 바뀐다(10-07 5174 흰 화면). 지금은 `vite.config.ts` 가 그런 앱 경로를 거부하고, 이미지 빌드가
  `frontend/scripts/check-build.mjs` 로 자산 경로를 검사해 앱 경로 밖을 부르면 멈춘다. CI 도 `/` 와
  `/ax-link/` 두 경로로 빌드해 같은 검사를 돌린다.
- 반영했다고 말하기 전에 화면 점검을 돌린다. 첫 HTML 과 API 의 200 만으로는 화면이 뜨는지 모른다.

  ```bash
  cd frontend
  SMOKE_URL=http://localhost:5173/ax-link SMOKE_USER=<아이디> SMOKE_PASSWORD=<비밀번호> \
  SMOKE_CHROME="C:/Program Files/Google/Chrome/Application/chrome.exe" node scripts/smoke-web.mjs
  ```

  앱 경로의 JS·CSS 로딩과 형식, 렌더링, 로그인, 보호 화면 직접 접근·새로고침, 콘솔 오류, 실패한
  요청을 본다. 하나라도 실패하면 0 이 아닌 값으로 끝난다.
- `.env` 에 `AXLINK_JWT_SECRET`(32자 이상)와 `AXLINK_SECRET_KEY` 가 있어야 API 가 뜬다(운영 검사).
  `AXLINK_SECRET_KEY` 는 저장된 연결 토큰을 푸는 키라 바꾸지 않는다.
- 웹은 `dev.userinsight.co.kr`·`localhost`·`127.0.0.1`·`192.168.0.50` 만 받는다(그 밖은 421).
  `http://localhost:5173/` 는 `/ax-link/` 로 보낸다.
- 프록시가 경로를 떼고 넘기든 붙여 넘기든 같은 화면이 나온다. 프록시에는 AI 답변(SSE)을 모아 두지
  않게 버퍼링을 끄고(`proxy_buffering off`), 읽기 시간 300초, 업로드 100MB 를 둔다.
- 외부에 열린 뒤에는 위 표의 시드 비밀번호가 이 PC 의 DB 에서 바뀌어 있다. 시드 값은 새 DB 에만 맞다.

## LLM (Ollama, 11434)

임베딩(`bge-m3`)은 로컬 Ollama 컨테이너가 **CPU** 로 만든다. 1.2GB 모델이라 청크 32건
배치가 1초 안에 끝난다.

```bash
docker compose -f infra/docker-compose.yml up -d ollama
docker exec axlink-ollama ollama pull bge-m3
```

- GPU 를 붙이지 않는다. 09.15 실측에서 WSL2 컨테이너 + RTX 3070 조합은 bge-m3 러너가
  배치 임베딩 중 세그폴트로 죽어 `/api/embed` 가 400 을 냈다.
- 생성 모델은 `AXLINK_LLM_MODEL` 로 고른다. 기본은 `qwen3:4b`(로컬). 개발 PC 에서 더 큰
  모델을 쓰려면 Ollama 계정에 연결하고 `-cloud` 모델을 지정한다
  (`docker exec axlink-ollama ollama signin` 뒤 `AXLINK_LLM_MODEL=gemma4:31b-cloud`).
  **납품 환경은 폐쇄망 온프레미스가 원칙**이라 클라우드는 개발·검증용으로만 쓴다.
- 클라우드 모델은 Ollama 의 `format` 스키마 강제를 무시한다. JSON 출력은 프롬프트 규칙에만
  기대므로 `app/rag/answer.py`·`routing.py` 의 출력 형식 지시를 지우면 안 된다.
- Fake 임베딩(`AXLINK_EMBEDDING_PROVIDER=fake`)은 시험 전용이다. 개발 DB 에 그 벡터가
  들어가면 검색이 통째로 망가진다. 색인은 `embedding_model` 에 만든 모델을 기록하므로
  `select embedding_model, count(*) from doc_chunk group by 1` 로 확인할 수 있다.

## Redmine (샘플 원천, 3000)

작업 이슈·리스크·결함의 원천 도구다. 구조(트래커·버전 M1~M6·커스텀 필드 REQ ID·REST 활성화)는
스크립트가 만들고, **이슈 내용은 사람이 넣는다.** 생성기로 심은 이슈는 샘플 대표성이 없기 때문이다.

```bash
docker compose -f infra/docker-compose.yml --profile redmine up -d redmine-db redmine   # 첫 부팅 1~2분
docker cp infra/redmine/axlink_init.rake axlink-redmine:/usr/src/redmine/lib/tasks/
docker exec -e SECRET_KEY_BASE=change-me-in-local-env axlink-redmine bin/rake axlink:init
```

- 관리자: `admin` / `axlink-admin` (로컬 전용). API 키는 rake 출력 또는 「내 계정」에서
- 커넥터 연결값: base URL `http://localhost:3000` · 대상 `axlink` · 인증은 API 키

### 독립 실행 (5174 연동 검증, 10-13~)

앱 Compose 와 수명·볼륨을 나눈 구성이다. 지금 5174 검증에 쓰는 Redmine 이 이것이다.

```bash
# 비밀값 파일은 infra/redmine.env.example 을 저장소 밖으로 복사해 무작위 값으로 채운다
docker compose -p axlink-redmine -f infra/docker-compose.redmine.yml --env-file <비밀값 파일> \
  up -d redmine-db redmine
docker cp infra/redmine/axlink_init.rake axlink-rm:/usr/src/redmine/lib/tasks/
docker exec -e SECRET_KEY_BASE=<비밀값 파일의 값> axlink-rm bin/rake axlink:init
# 시험 프로젝트·계정(rm-prep·rm-collector·rm-dev). 비밀번호·API 키는 컨테이너 안 파일로만 나온다
docker cp infra/redmine/axlink_verify.rake axlink-rm:/usr/src/redmine/lib/tasks/
docker exec axlink-rm sh -c 'SECRET_KEY_BASE="$REDMINE_SECRET_KEY_BASE" \
  AXLINK_SECRETS_OUT=/tmp/axlink-verify.env bin/rake axlink:verify'
docker cp axlink-rm:/tmp/axlink-verify.env <저장소 밖> && docker exec axlink-rm rm /tmp/axlink-verify.env
# 컨테이너 안 앱(API)이 http Redmine 을 쓰려면 중계를 띄운다. API 를 다시 만들 때마다 다시 띄운다
docker compose -p axlink-redmine -f infra/docker-compose.redmine.yml --env-file <비밀값 파일> \
  --profile relay up -d --force-recreate relay
```

- 이미지는 digest 로 고정했다(Redmine 6.1.4, PostgreSQL 16.14). 올릴 때 digest 와 날짜를 같이 바꾼다.
- 볼륨 `axlink-redmine_pgdata`(DB)·`axlink-redmine_attachments`(첨부). 이 프로젝트에도 `down` 을 쓰지 않는다.
- `axlink:verify` 는 `admin` 의 알려진 비밀번호를 무작위로 바꾼다. 다시 돌리면 시험 계정 비밀번호·API 키가 새로 바뀐다(AX Link 연결의 키도 바꿔 넣어야 한다).
- 백업·이전: DB 는 `pg_dump`, 첨부는 볼륨 사본, 비밀값 파일은 따로(`서버-이전-복원-절차.md` 7절).

## 개발용 계정 (시드 V4 · V20)

| 아이디 | 비밀번호 | 역할 | 보이는 사업 |
|---|---|---|---|
| `r1` | `admin` | SUPER_ADMIN | 전체 |
| `r2` | `admin` | CLIENT (한국디지털공사) | 자기 조직 사업 |
| `r3` | `admin` | CONTRACTOR (넥스트소프트) | 배정된 사업 |

로그인 식별자는 이메일이 아니라 아이디다(V20). 형식 제약이 없어 이메일 주소를
아이디로 써도 된다.

## 테스트

시험은 세 갈래이고 `pytest -m` 으로 고른다.

| 갈래 | 표식 | 필요한 것 | CI |
|---|---|---|---|
| 단위 | 없음 | 없음 | `테스트 (DB·모델 없음)` |
| DB | `db` | 시험용 DB(이름이 `_test` 로 끝남) | `테스트 (시험용 DB)` |
| 실모델 | `live` | Ollama·토큰, `AXLINK_LIVE=1` | 돌리지 않는다 |

**시험용 DB 를 따로 쓴다.** 스위트가 시드 사업의 연결과 그 연결이 수집한 데이터를
지우기 때문이다. 이름이 `_test` 로 끝나지 않는 DB 에는 어떤 갈래도 붙지 않는다. live 도 같다.

시험용 DB 는 개발 스택과 다른 Compose 프로젝트(`infra/docker-compose.test.yml`, 이름 `axlink-test`)로
띄운다. 네트워크·컨테이너 이름이 따로라서 이 프로젝트를 올리고 내려도 개발 PostgreSQL·Redmine·Ollama
에는 영향이 없다. 포트는 이 PC 에서만 붙게 `127.0.0.1:15433` 에 연다. 데이터는 메모리(tmpfs)에만
있어서 띄울 때마다 비어 있다.

```bash
docker compose -f infra/docker-compose.test.yml up -d postgres
docker compose -f infra/docker-compose.test.yml run --rm flyway

# localhost 가 아니라 127.0.0.1 로 적는다. Windows 에서 localhost 는 ::1 로 먼저 풀리는데,
# 시험 DB 는 IPv4 에만 열려 있어 커넥션 풀이 30초씩 기다리다 실패한다.
export AXLINK_DATABASE_URL=postgresql://axlink:axlink@127.0.0.1:15433/axlink_test
.venv/Scripts/python -m pytest -m "not live"                       # DB 가 없으면 db 시험은 skip
AXLINK_REQUIRE_DB=1 .venv/Scripts/python -m pytest -m "db and not live"   # DB 문제는 실패로 끝난다
.venv/Scripts/python -m ruff check app tests

# 다시 비우려면 내렸다가 위 두 줄을 다시 실행한다
docker compose -f infra/docker-compose.test.yml down
```

스키마 검사는 두 곳이 나눠 맡는다.

| 누가 | 무엇을 본다 | 무엇은 안 본다 |
|---|---|---|
| `flyway migrate` (적용 전 validate) | 이미 적용된 파일의 체크섬 변조, 이력에는 있는데 파일이 없는 버전, 적용 순서 | 없음 |
| `tests/conftest.py` | 시험용 DB 인가, 붙는가, 성공한 마지막 번호가 `db/migration` 최신 번호와 같은가, 실패 기록이 없는가 | 중간 번호 누락, 체크섬, 파일과 이력의 내용 일치 |

conftest 는 "최신까지 올렸는가" 만 확인한다. 나머지는 빈 DB 에 `flyway migrate` 를 돌리는
위 절차(CI 도 같다)가 보장한다. 이미 쓰던 시험 DB 를 그대로 다시 쓸 때는 따로 확인한다.

```bash
docker compose -f infra/docker-compose.test.yml run --rm flyway \n  -url=jdbc:postgresql://postgres:5432/axlink_test -user=axlink -password=axlink \n  -locations=filesystem:/flyway/sql validate
```

참고로 V25 는 처음부터 없는 번호다. Flyway 는 번호가 비어도 허용한다.

`AXLINK_REQUIRE_DB=1` 이면 위 conftest 검사에 걸리는 문제를 skip 하지 않고 바로 실패로 끝낸다.
CI 의 DB 작업이 이 모드다. `AXLINK_REQUIRE_DB` 가 없으면 같은 문제에서 DB 시험이 skip 된다.

실모델 시험은 켤 때만 돈다. DB 를 쓰는 실모델 시험(`test_rag_live`·`test_general_questions_live`)도
시험용 DB 에서만 돈다. 그 DB 에 색인된 문서가 있어야 답이 나온다.

```bash
AXLINK_LIVE=1 .venv/Scripts/python -m pytest -m live -s
```

실행 결과를 남기려면 junit 으로 `var/test-results/` 에 쓴다(gitignore). CI 는 같은 파일을
작업마다 artifact(90일)로 보관한다.

```bash
.venv/Scripts/python -m pytest -m "db and not live" --junitxml=var/test-results/backend-db.xml
cd frontend && npm run build && npx vitest run --reporter=default --reporter=junit --outputFile.junit=../var/test-results/frontend.xml
```
