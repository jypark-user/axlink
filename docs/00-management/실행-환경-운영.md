2026-10-07 확정. 개발 PC 한 대에서 두 환경을 나눠 돌린다.

| | 5173 공개 환경 | 5174 내부 개발·검증 환경 |
|---|---|---|
| 용도 | 발주기관이 쓰는 환경. 안정적으로 유지한다 | 모든 변경을 먼저 올려 확인한다 |
| 주소 | `https://dev.userinsight.co.kr/ax-link/` (앞단 프록시), 내부 `http://192.168.0.50:5173` | `http://localhost:5174/ax-link/`, 내부 `http://192.168.0.50:5174`. 외부 프록시에 잇지 않는다 |
| Compose | `infra/docker-compose.yml` + `infra/docker-compose.ext.yml` (프로젝트 `axlink`) | `infra/docker-compose.int.yml` (프로젝트 `axlink-int`) |
| DB · 문서 | `axlink_pgdata` · `axlink_documents` | `axlink-int_pgdata` · `axlink-int_documents` (영구 볼륨) |
| 스케줄러·자동 동기화 | 켬 | 끔 |
| 화면 표시 | 없음 | 맨 위 띠 "내부 개발·검증 환경 (5174)" 와 데이터 기준 시점 |
| 로그인 키 | `.env` 의 `AXLINK_JWT_SECRET` | `.env.int` 의 다른 키. 서로의 로그인이 통하지 않는다 |
| 모델 서버 | `axlink-ollama` | 같은 것을 쓴다. 문서 처리는 한 번에 하나, 무거운 평가는 따로 시간을 잡는다 |

## 반영 순서

1. PR 을 병합한다. 병합은 5173 배포 승인이 아니다.
2. main 으로 이미지를 만들고(태그 = 버전-커밋) 5174 에 올린다. 마이그레이션도 5174 DB 에 먼저 적용한다.
3. 5174 에서 확인한다. 결과를 사용자가 확인한다.
4. 5173 반영은 사용자가 정한 시점에 한다. 순서: API 중지(쓰기 중지) → DB 덤프·문서 볼륨 백업과 복원 확인 →
   마이그레이션 → 웹·API 다시 만들기 → 내부·외부 확인.
5. 개발 DB(5174)를 공개 DB(5173)에 덮어쓰지 않는다. 5174 데이터는 공개 DB 의 사본이거나 시험 데이터다.

## 5174 다루기

```bash
# 띄우기·다시 만들기 (이미지 태그를 정한다)
AXLINK_INT_VERSION=<태그> docker compose -f infra/docker-compose.int.yml up -d

# 멈추기 (볼륨은 남는다. down 은 쓰지 않는다)
docker compose -f infra/docker-compose.int.yml stop

# 마이그레이션
docker run --rm --network axlink-int_default \
  -e FLYWAY_URL=jdbc:postgresql://int-postgres:5432/axlink \
  -e FLYWAY_USER=axlink -e FLYWAY_PASSWORD=axlink axlink-migrate:<태그> migrate
```

- 공개 데이터 사본을 넣을 때는 기준 시점을 `AXLINK_INT_LABEL` 에 적어 화면 띠에 보이게 한다
  (예: `내부 개발·검증 환경 (5174) · 공개 데이터 사본 2026-10-07 16:00`).
- 사본에는 공개 환경 계정과 비밀번호 해시가 그대로 들어온다. 확인용 계정은 5174 에서만 만든다.
- 자동 시험용 DB 는 tmpfs·`--rm` 으로 따로 띄운다. 5174 볼륨을 시험에 쓰지 않는다.
