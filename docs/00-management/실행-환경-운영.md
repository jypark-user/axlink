# 실행 환경 운영 기준

2026-10-07 확정, 2026-11-25 개정. 개발 PC 한 대에서 공개 환경과 내부 환경을 나눠 돌린다.
처음에는 내부 개발·검증을 5174(Compose 프로젝트 `axlink-int`)에서 했고, 11-25 에 5174 를 닫고 5177 로 옮겼다.

| | 5173 공개 환경 | 5177 내부 개발·검증 환경 |
|---|---|---|
| 용도 | 발주기관이 쓰는 환경. 안정적으로 유지한다 | 화면·API 변경을 먼저 올려 확인한다 |
| 주소 | `https://dev.userinsight.co.kr/ax-link/` (앞단 프록시), 내부 `http://192.168.0.50:5173` | `http://localhost:5177`, API `127.0.0.1:18177`. 외부 프록시에 잇지 않는다 |
| 실행 | GitHub Actions 가 만든 main 이미지(GHCR, digest 고정). `infra/docker-compose.yml` + `docker-compose.ext.yml` + `docker-compose.ghcr-ext.yml` (프로젝트 `axlink`) | 소스 실행. API 는 API 이미지에 작업 공간의 `app/` 를 넣어 `uvicorn --reload` 로, 웹은 호스트 Vite 로 띄운다 |
| DB · 문서 | `axlink_pgdata` · `axlink_documents` | `axlink-dev_pgdata` · `axlink-dev_documents` (영구 볼륨, 옛 5174 데이터 사본) |
| 스케줄러·자동 동기화 | 켬 | 켬 |
| 모델 서버 | `axlink-ollama` | 같은 것을 쓴다. 문서 처리는 한 번에 하나, 무거운 평가는 따로 시간을 잡는다 |

## 반영 순서

1. PR 을 병합한다. 병합은 5173 배포 승인이 아니다.
2. main CI 가 성공하면 GitHub Actions 가 이미지를 GHCR 에 게시한다. CI 가 실패하면 게시되지 않는다.
3. 화면·API 동작은 5177 에서 확인하고 결과를 사용자가 확인한다. 5177 은 소스 실행이라 이미지 확인을 대신하지 않는다.
4. 게시된 이미지로 5173 DB 사본을 검증한다. 공개 DB 덤프를 내부망 임시 DB(tmpfs)에 복원해 새 마이그레이션을 적용하고,
   핵심 데이터 건수가 그대로인지, 새 API 이미지가 그 위에서 정상으로 뜨는지 본다.
5. 5173 반영은 사용자가 정한 시점에 한다. 순서: API 중지(쓰기 중지) → DB 덤프·문서 볼륨 백업과 복원 확인 →
   마이그레이션(DB 하나만 붙인 내부 네트워크) → 웹·API 다시 만들기 → 내부·외부 확인.
6. 개발 DB(5177)를 공개 DB(5173)에 덮어쓰지 않는다.

## 5177 다루기

- 서버 코드를 고치면 작업 공간의 `app/` 를 API 컨테이너에 넣는다. 넣은 뒤 다시 읽기는 자동이다.

  ```bash
  docker cp app/. axlink-dev-api-copy:/srv/axlink/app
  ```

- 로컬 Redmine 중계(`dev-rm-relay`)는 API 컨테이너의 네트워크 공간에 붙어 있다. API 컨테이너를 다시 만들면 중계도 다시 띄운다.
- 마이그레이션이 늘면 5177 DB 에도 적용한다. 새 V 파일만 migrate 이미지에 넣어 돌린다.
- 5177 DB 에는 공개 환경 계정과 비밀번호 해시가 사본으로 들어 있다. 확인용 계정은 5177 에서만 만든다.
- 자동 시험은 따로 띄운 시험 DB 로 한다. 5177 볼륨을 시험에 쓰지 않는다.

## 닫은 5174

컨테이너(`axlink-int-web`·`axlink-int-api`·`axlink-int-postgres`)만 멈추고 재시작 정책을 끄고 두었다.
볼륨 `axlink-int_pgdata`·`axlink-int_documents` 와 `infra/docker-compose.int.yml` 은 남아 있다.
다시 써야 하면 `docker start` 로 띄운다. 볼륨 삭제는 따로 결정한다.
