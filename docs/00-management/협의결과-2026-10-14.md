이 문서는 회의록이 아니라 협의에서 정한 방향을 요구사항·설계·작업 단위로 옮긴 기준이다. 명시적으로 정하지 않은 업무 정책은 확정하지 않는다.

## 1. 협의에서 정한 방향

| # | 방향 | 작업 이슈 |
|---|---|---|
| 1 | 한 사업을 공동 수주한 여러 업체를 등록·관리한다 | GH-138 |
| 2 | 요구사항은 확정된 요구사항 명세서를 기준선으로 독립 관리하고, 이슈·일감은 요구사항 ID 를 참조한다 | GH-139 |
| 3 | 수집한 이슈가 어느 도구·연결·저장소에서 왔는지 구분해 보인다 | GH-140 (선행 GH-136) |
| 4 | 발주기관이 WBS 단계·작업별로 필요한 산출물을 지정하고 양식을 올린다 | GH-141 |
| 5 | 인계 대상: GitHub 저장소, Redmine 실행 환경과 DB, 산출물 일체 | GH-51 (7절 목록) |
| 6 | 사용자 매뉴얼은 웹 안내 + PDF·DOCX, 설치·운영 안내와 분리 | GH-142 (후속) |

지표 정책은 그대로 둔다. 요구사항 이행률·산출물 승인률·WBS 완료 확인율은 서로 자동으로 바꾸지 않는다. 근거를 서로 찾아볼 수 있게 하는 것은 된다.

### 1-1. 확정한 정책 (2026-10-15)

10-14 협의 뒤 수행 책임자가 정리해 확정했다. 구현은 이 기준으로 한다. 다시 묻지 않는다.

**요구사항 기준선 (GH-139)**

- 용역사가 요구사항 명세서를 등록하고, 추출 결과를 확인·정리해 제출한다. 발주기관이 기준선을 확정한다.
- 확정 전(초안·제출 중) 목록은 현재 확정 요구사항으로 보이지 않는다. 기준선이 없는 사업은 "미등록·미확정"으로 보인다.
- 새 연결은 이슈에서 요구사항을 만들지 않는다(기본 끔). 기존 연결은 기준선 확정 전까지 지금처럼 만들고, 확정할 때 끈다. 그 뒤 이슈는 확정된 요구사항 ID 를 참조만 한다.
- 이후 수집은 요구사항 정의(코드·제목·본문·중요도)와 발주기관 지정 상태를 덮어쓰지 않는다. 추적관계는 기준선에 있는 ID 에만 잇고, 없는 ID 참조는 버리지 않고 미해결로 보인다.
- 기존 요구사항의 ID·추적관계·지정 상태·이력을 보존한다. 같은 코드인데 내용이 다르거나 기존 코드가 새 명세서에 없으면 차이를 보이고 자동으로 덮거나 지우지 않는다.
- 확정 뒤 변경은 새 버전의 차이와 사유를 발주기관이 보고 확정한다(후속 단위). 확정 뒤 새 파일을 올려도 기준선이 자동으로 바뀌지 않는다.

**공동 수급 (GH-138)**

- 참여 업체는 사업의 업무 정보(이슈·요구사항·일정·산출물·연결 상태)를 함께 조회한다.
- 연결 설정 변경·삭제는 그 연결의 소유 업체와 발주기관만 한다.
- 인증정보(토큰·비밀번호)는 공유 조회에서 뺀다. 지금처럼 끝 몇 글자 표시만 남긴다.
- 대표사·참여사는 표시 구분이다. 특별 권한이 없다.
- 업체·사용자 추가, 연결 소유 업체 변경으로 일반 참여자가 권한을 넓힐 수 없다. 기존 관리자 권한과의 관계를 문서에 적고 서버에서 검사한다.
- 권한 작업이 끝나기 전에는 실제 사업에 참여 업체를 추가하지 않는다.

**WBS 산출물 (GH-141)**

- 발주기관이 WBS 단계·작업별로 필요한 산출물과 양식을 지정한다.
- 항목(무엇을 내나), 양식(어떻게 쓰나), 제출본(낸 버전), 승인(판정)을 따로 관리한다.
- 22종은 분류이고 필수 목록이 아니다. 기존 제출·승인 이력은 보존한다.
- WBS 일정·가중치·실적은 편집하지 않는다(IM-001 10절 그대로).

**지표**

- 요구사항 이행률·산출물 승인률·WBS 완료 확인율은 독립으로 관리한다. 서로 자동으로 갱신하지 않는다. 관련 근거로 이동하는 연결은 둔다.

**범위 문서**

- 공동 수급 관리와 WBS 산출물 지정은 10-14 협의 요청으로 기록한다(IM-001 10-1절).
- IM-001 10절 제외 범위를 통째로 풀지 않는다. 이번에 더하는 범위만 적는다.
- 계약상 추가 지시 여부와 비용·일정 영향은 따로 확인한다(6절).

## 3. 기존 데이터와 권한에 미치는 영향

- 지우거나 다시 만드는 데이터는 없다. 모든 변경은 새 마이그레이션으로 더한다. 적용된 V51·V52 는 고치지 않는다.
- 요구사항 41건: 코드·추적 링크·지정(5174 에 3건)·이력 유지. 기준선은 덧붙이는 정보다.
- 공동 수급: 현재 다업체 사업이 없어 접근 범위 변화는 새로 업체를 추가할 때부터 생긴다. 권한 작업(GH-138) 전에 업체를 추가하면 지금 규칙(사업 안 전면 공유, 연결 수정도 공유)이 그대로 적용되므로 실제 사업에는 추가하지 않는다.
- 산출물: 기존 22종 버전·승인 기록 유지. 지정 산출물은 새 표다.
- 지표: 세 지표의 계산식은 바꾸지 않는다.

### 첫 작업 단위 제안: GH-140 이슈 원천 표시

정책 결정 없이 바로 할 수 있고, 다른 작업이 쓰는 "연결 구분"의 기초가 된다.

- API: `IssueResponse.source` 에 `connectionName`·`targetResource`. `GET /projects/{id}/issues?connectionId=` 필터. 요약 카드도 같은 조건.
- DB: 변경 없음(조회에 `tool_connection` 이름·대상을 더함). 다중 연결 키 구분은 화면 표시와 추적 해석에서 처리.
- 화면: 일반 이슈 표에 원천 열, 연결 선택 필터.
- 수용시험: ① GitHub 하나·Redmine 하나인 사업에서 이슈마다 도구·연결 이름·저장소·번호 링크가 맞다 ② 연결 필터의 건수가 요약 카드와 같다 ③ 같은 도구 연결 둘에서 같은 번호 이슈가 따로 보이고, 추적 링크가 다른 연결의 이슈로 잘못 붙지 않는다 ④ 다른 사업의 연결 id 로 거르면 0건(접근 범위 그대로).
