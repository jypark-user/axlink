## 1. 협의에서 정한 방향

| # | 방향 | 작업 이슈 |
|---|---|---|
| 1 | 한 사업을 공동 수주한 여러 업체를 등록·관리한다 | GH-138 |
| 2 | 요구사항은 확정된 요구사항 명세서를 기준선으로 독립 관리하고, 이슈·일감은 요구사항 ID 를 참조한다 | GH-139 |
| 3 | 수집한 이슈가 어느 도구·연결·저장소에서 왔는지 구분해 보인다 | GH-140 (선행 GH-136) |
| 4 | 발주기관이 WBS 단계·작업별로 필요한 산출물을 지정하고 양식을 올린다 | GH-141 |
| 5 | 인계 대상: GitHub 저장소, Redmine 실행 환경과 DB, 산출물 일체 | GH-51 (7절 목록) |
| 6 | 사용자 매뉴얼은 웹 안내 + PDF·DOCX, 설치·운영 안내와 분리 | GH-142 (후속) |

지표 정책은 그대로 둔다. 요구사항 이행률·산출물 승인률·WBS 완료 확인율은 서로 자동으로 바꾸지 않는다. 근거를 서로 찾아볼 수 있게 하는 것은 된다.

## 2. 항목별 현재 기능과 필요한 변경

분류: **보완** = 기존 요구사항·설계의 구현을 채움, **신규** = 요구사항정의서에 없던 항목, **범위 확인** = IM-001 10절(제외 범위)과 겹쳐 합의가 필요함.

| | 현재 | 필요한 변경 |

| 참조 검사 | 사업에 없는 코드는 "오타"로 보고 조용히 버린다. 화면에 안 보인다 | "명세서에 없는 ID 참조", 중복 코드, 추출 실패를 목록으로 보인다 |

## 3. 기존 데이터와 권한에 미치는 영향

- 지우거나 다시 만드는 데이터는 없다. 모든 변경은 새 마이그레이션으로 더한다. 적용된 V51·V52 는 고치지 않는다.
- 요구사항 41건: 코드·추적 링크·지정(5174 에 3건)·이력 유지. 기준선은 덧붙이는 정보다.
- 공동 수급: 현재 다업체 사업이 없어 접근 범위 변화는 새로 업체를 추가할 때부터 생긴다. 결정 전에 업체를 추가하면 지금 규칙(사업 안 전면 공유)이 그대로 적용된다.
- 산출물: 기존 22종 버전·승인 기록 유지. 지정 산출물은 새 표다.
- 지표: 세 지표의 계산식은 바꾸지 않는다.

### 첫 작업 단위 제안: GH-140 이슈 원천 표시

정책 결정 없이 바로 할 수 있고, 다른 작업이 쓰는 "연결 구분"의 기초가 된다.

- API: `IssueResponse.source` 에 `connectionName`·`targetResource`. `GET /projects/{id}/issues?connectionId=` 필터. 요약 카드도 같은 조건.
- DB: 변경 없음(조회에 `tool_connection` 이름·대상을 더함). 다중 연결 키 구분은 화면 표시와 추적 해석에서 처리.
- 화면: 일반 이슈 표에 원천 열, 연결 선택 필터.
- 수용시험: ① GitHub 하나·Redmine 하나인 사업에서 이슈마다 도구·연결 이름·저장소·번호 링크가 맞다 ② 연결 필터의 건수가 요약 카드와 같다 ③ 같은 도구 연결 둘에서 같은 번호 이슈가 따로 보이고, 추적 링크가 다른 연결의 이슈로 잘못 붙지 않는다 ④ 다른 사업의 연결 id 로 거르면 0건(접근 범위 그대로).
