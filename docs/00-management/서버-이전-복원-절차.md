# 서버 이전·복원 절차

| 항목 | 내용 |
|---|---|
| 상태 | 준비 문서. **이전은 실행하지 않았다** (2026-10-15 사용자 결정: 5173 은 지금 PC 에서 유지) |
| 대상 | 5173 공개, 5174 내부, Redmine(시험 원천) |
| 관련 | ARC-026(이미지 빌드), `실행-환경-운영.md`, `로컬-실행.md` 3절, `docs/40-manual/배포-운영-절차.md` |

지금 PC 가 불안정해(커널 패닉·세그폴트·도커 디스크 오류) 언제든 다른 장비로 옮길 수 있게 준비물과 순서를 적는다.
준비물의 실제 위치·해시·복원 확인 결과는 저장소 밖 기록(`var/notes/이전-준비물-*.md`)에 둔다. 키 값은 어디에도 적지 않는다.

## 1. 무엇을 옮기나

| 묶음 | 5173 | 5174 | Redmine | 없으면 |
|---|---|---|---|---|
| 실행 코드 | 실행 태그(지금 `deploy/5173-2026-10-07`) | main 커밋 | Redmine compose(저장소에 올린 뒤) | 다시 만들 수 없다 |
| 이미지 | GHCR digest 또는 `docker save` 파일 | GHCR digest | 공개 레지스트리 digest | 코드로 다시 빌드 |
| DB | `pg_dump -Fc` | 같음 | 같음 | 데이터 손실 |
| DB 밖 파일 | 문서 볼륨 | 문서 볼륨 | 첨부 볼륨 | 문서 열기·재처리 불가 |
| 키 | `.env`(`AXLINK_SECRET_KEY`·`AXLINK_JWT_SECRET`) | `.env.int` | `redmine.env` | 암호화 키가 없으면 저장된 도구 연결 토큰을 풀 수 없다 |
| 모델 | Ollama 버전, `bge-m3`(필수)·답변 모델, 클라우드 모델 서명 키 | 공유 | — | 다시 받는다. 서명 키는 재등록 |

옮기지 않는 것: 시험용 DB(tmpfs)·시험 볼륨, Ollama 모델 파일(다시 받는다), 진단 자료(메모리·크래시 덤프, 비밀정보가 들어 있을 수 있다).

## 2. 새 장비 전제

- x86-64, 메모리 32GB 이상 권장(Ollama 로컬 임베딩 포함), 디스크 50GB 이상.
- Docker Engine 또는 Docker Desktop, Compose v2. Git.
- 포트: 웹 5173(앞단 프록시가 넘겨 주는 곳), DB·Ollama 는 외부에 열지 않는다(`127.0.0.1` 로 묶는다).
- GHCR 를 쓸 때: `read:packages` 만 준 토큰. `docker login ghcr.io` 로 자격 증명 저장소에만 둔다.
- 하드웨어 진단(메모리 시험)이 끝난 장비. 지금 PC 와 같은 증상(세그폴트·CRC)이 나오면 거기서 멈춘다.

## 3. 이미지 확보

1. GHCR: 반영할 커밋의 `image-manifest.json` 에서 digest 를 고른다. `docker pull ghcr.io/jypark-user/axlink-api@sha256:…`(web·migrate 도). 라벨 `org.opencontainers.image.revision` 이 의도한 커밋인지 본다.
2. 레지스트리에 없는 판(예: 5173 의 `0.2.1-3784976`): 백업의 `docker save` 파일을 `docker load -i`.
3. 반입용 릴리스: `sha256sum -c SHA256SUMS` → `gunzip -c axlink-images-X.Y.Z.tar.gz | docker load`.
4. `latest`·`main` 같은 움직이는 태그로 띄우지 않는다. Ollama 도 버전을 고정한다(`ollama/ollama:0.33.1`).

## 4. 백업 뜨기 (옮기기 전)

### 4-1. 확정 백업 (전환 직전, 쓰기 중지)

1. 원래 서버의 API 를 멈춘다(`docker stop axlink-api`). 쓰기·스케줄러가 함께 멈춘다. 웹은 오류 화면을 보일 수 있다.
2. DB: `docker exec axlink-postgres pg_dump -U axlink -d axlink -Fc -f /tmp/x.dump` → `docker cp`.
3. 문서: `docker run --rm -v axlink_documents:/d:ro -v <백업>:/b alpine:3.20 sh -c 'cd /d && find . -type f -exec sha256sum {} + | sort -k2 > /b/documents.files.sha256 && tar cf /b/documents.tar .'` — API 가 멈춘 상태라야 일관된 사본이다.
4. `sha256sum` 을 남기고, 격리 컨테이너에 복원해 행 수를 원본과 대조한다(5-2).
5. 이 시점부터 원래 서버를 다시 켜지 않는다(켜면 새 쓰기가 백업 밖에 생긴다). 되돌릴 때만 켠다(8절).

### 4-2. 수시 백업 (서비스 유지)

- DB 는 실행 중 `pg_dump` 도 한 시점의 일관된 사본이다.
- 실행 중 볼륨 tar 는 **일관된 백업이 아니다.** 파일 해시 목록과 함께 "실행 중 사본"으로 기록한다.

## 5. 새 장비에서 복원 (격리 상태)

외부 프록시에 붙이기 전, 스케줄러를 끈 채로 확인한다. 원래 서버와 같은 도구에 동시에 수집하지 않게 하기 위해서다.

1. 저장소를 받고 실행 태그로 체크아웃한다.
2. 키: 백업의 `.env` 를 새 장비의 `.env` 로 둔다(권한은 소유자만). `AXLINK_SECRET_KEY`·`AXLINK_JWT_SECRET` 를 바꾸지 않는다.
3. 볼륨을 만들고 데이터를 넣는다.
   - DB: postgres(pgvector/pgvector:pg16)를 먼저 띄우고 `pg_restore -U axlink -d axlink --no-owner <dump>`.
   - 문서: `docker run --rm -v axlink_documents:/d -v <백업>:/b alpine:3.20 tar xf /b/documents.tar -C /d` → 해시 목록과 대조. 소유권은 API 실행 사용자에 맞춘다.
4. 스키마: 덤프의 버전을 확인한다. 옮기면서 버전을 올리지 않는다(올리는 것은 이전이 끝난 뒤 별도 반영).
5. Ollama: 버전 고정 이미지로 띄우고 `ollama pull bge-m3`, 답변 모델 준비. 클라우드 모델은 서명 키를 넣거나 새로 등록한다. DB `llm_setting` 의 모델 주소가 새 장비에서 맞는지 본다(`로컬-실행.md` "DB 에 저장된 생성 모델 주소").
6. API·웹을 **스케줄러를 끄고**(`AXLINK_SCHEDULER_ENABLED=false`) `127.0.0.1` 에만 열어 띄운다.

### 5-1. 확인 (격리 상태)

| 항목 | 방법 |
|---|---|
| 기동 | `/api/health` 버전 표시, 컨테이너 healthy |
| 로그인 | 실제 계정 하나(발주기관·용역사 각 1) |
| 문서 | 목록, 내려받기 1건(파일 해시가 백업과 같은지), 상세 |
| 검색 | AI 질의 1건이 근거 문서를 붙여 답한다(임베딩·모델 연결) |
| 지표 | 사업 개요·진행 상황 수치가 원래 서버 마지막 화면과 같다 |
| 연결 | 도구 연동 화면에서 연결 테스트(토큰이 풀리는지). **수집은 누르지 않는다** |
| 스냅샷 | 일별 스냅샷 목록이 백업 시점까지 있다 |

### 5-2. 복원 대조

`select count(*)` 로 사업·요구사항·이슈·문서·연결·사용자 수와 `flyway_schema_history` 최대 버전을 원래 서버(백업 직전)와 대조한다. 문서 볼륨은 해시 목록 전체를 대조한다.

## 6. 최종 전환

1. 4-1 확정 백업(원래 서버 API 중지 상태)으로 5절을 한 번 더 한다(격리 확인 때보다 뒤의 변경을 담는다).
2. 원래 서버의 API·웹 재시작 정책을 끈다(`docker update --restart=no axlink-api axlink-web`). **스케줄러가 두 곳에서 돌면 같은 도구를 두 번 수집하고 스냅샷이 두 번 찍힌다.** 원래 서버를 켜 둘 일이 있으면 `AXLINK_SCHEDULER_ENABLED=false` 로만 띄운다.
3. 새 장비의 API 를 스케줄러를 켜고 다시 띄운다. 웹을 프록시가 볼 주소에 연다.
4. 앞단 프록시(`dev.userinsight.co.kr/ax-link/`)의 대상을 새 장비로 바꾼다. 프록시 설정은 관리자와 같이 한다. 바꾸기 전 설정을 적어 둔다.
5. 외부 주소에서 5-1 의 로그인·문서·지표를 다시 본다.

## 7. 5174·Redmine

- 5174 는 공개 서비스가 아니다. 공개 전환이 끝난 뒤 같은 순서로 옮기되 외부 프록시에 붙이지 않는다. 공개 DB 를 5174 에 덮어쓰지 않는다(공개 데이터 사본을 넣을 때는 기준 시각을 `AXLINK_INT_LABEL` 에 적는다).
- Redmine: DB 덤프·첨부 tar·`redmine.env`. 이미지는 digest 로 고정돼 있다. 5174 API 와 같은 네트워크 공간을 쓰는 중계(relay)는 5174 API 를 다시 만들 때마다 다시 띄운다.

## 8. 실패 시 되돌리기

- 전환 전(격리 확인 중): 원래 서버는 그대로 돈다. 새 장비를 지우면 된다.
- 전환 뒤 문제: 프록시를 원래 서버로 되돌린다 → 원래 서버의 API·웹을 켠다(재시작 정책 복구). 전환 뒤 새 장비에 쌓인 쓰기는 원래 서버에 없다. 짧은 시간이면 그 사이 변경을 사용자에게 알리고, 길었으면 새 장비 DB 를 덤프해 원래 서버로 옮길지 따로 정한다.
- 두 서버를 동시에 쓰기 가능 상태로 두지 않는다.

## 9. 하지 않는 것 (이 문서 범위 밖)

- DNS 변경(프록시 대상만 바꾼다).
- 공개 DB 를 5174·시험 데이터로 덮어쓰기.
- 원래 서버의 볼륨·백업 삭제. 이전이 끝나고 일정 기간 둔 뒤 사용자 결정으로 정리한다.
