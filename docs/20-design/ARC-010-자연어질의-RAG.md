## 1. 결정

질문 하나는 **라우팅 → 검색 → 근거 게이트 → 생성 → 출처** 순서로 처리한다. 코드는
`app/rag/` 아래 `routing.py` `search.py` `answer.py` `service.py` 가 그 순서대로 맡는다.

절대 규칙 세 가지가 이 흐름의 뼈대다.

| 규칙 | 어디서 지키는가 |
|---|---|
| LLM 은 수치를 생성하지 않는다 | 집계 질문의 값은 대시보드와 같은 `semantic.run()` 이 SQL 로 뽑는다. 프롬프트에는 그 값만 넣고, 생성이 끝나면 답변의 숫자를 집계 값·근거 원문과 대조한다(수치 검문) |
| LLM 은 UI 를 생성하지 않는다 | 모델은 지표·차원·템플릿의 **키**를 고른다. 카탈로그에 없는 키는 버리고 문서 경로로 내려간다. 그림은 `infographic` 이벤트로 프런트의 위젯 렌더러가 그린다 |
| 근거 없는 답변은 차단한다 | 최고 코사인 유사도가 문턱 미만이면 모델을 부르지 않고 "근거 부족" 문안을 답으로 저장한다. 출처는 비운다 |

대화·메시지·출처는 기존 `conversation` `message` `message_source` 표(V1·V3·V14)에 그대로
담는다. 새 마이그레이션은 없다.

## 2. 라우팅 (SWFR.RAG.005)

모델에 카탈로그(`semantic_measure` `semantic_dimension`)를 통째로 주고 JSON 하나를 받는다.

```
집계: {"route": "AGGREGATE", "measure": "<지표 key>", "dimensions": [...], "template": "<템플릿>", "title": "...", "query": "<검색용 핵심어>"}
문서: {"route": "DOCUMENT", "query": "<검색용 핵심어>"}
```

읽는 규칙은 `routing.from_choice()` 에 있다.

- JSON 을 못 읽거나 `route` 가 AGGREGATE 가 아니면 **DOCUMENT** 다.
- `measure` 가 카탈로그에 없어도 DOCUMENT 다. 억지로 다른 지표에 맞추지 않는다.
- 허용되지 않은 차원은 버린다. 템플릿을 안 주면 차원 모양으로 정한다(없음 STAT_CARD,
  기간 LINE_CHART, 하나 BAR_CHART, 둘 STACKED_BAR_CHART). 위젯 생성(SWFR.WEB.001)과 같은 함수다.
- 집계 경로에서 `semantic.run()` 이 카탈로그 검증에 걸리면 그때도 DOCUMENT 로 내려간다.

저장되는 `route_type` 은 셋이다. AGGREGATE 로 갔는데 문서 근거도 게이트를 넘으면
**MIXED** 로 두 재료를 다 프롬프트에 넣는다. 넘지 못하면 AGGREGATE 로 집계 값만 넣는다.

라우팅 호출은 `json_schema={"type": "object"}` 로 **출력을 JSON 객체 하나로 묶는다**
(Ollama `format`, 온도 0). 09.14 실측에서 형식을 안 묶으면 qwen3:4b 가 `think: false` 인데도
영어로 생각을 늘어놓다 120초를 넘겼고, 묶으면 같은 질문에 2~5초 안에 JSON 만 냈다.
속성을 일일이 적은 스키마(route·query 만 필수)는 쓰지 않는다. 그 스키마를 주자 모델이
선택 속성을 통째로 건너뛰어 "AGGREGATE 인데 measure 없음" 이 됐다. 객체라고만 묶으면
프롬프트가 말한 여섯 키를 다 채웠다.

## 3. 하이브리드 검색 (SWFR.RAG.004)

두 후보 목록을 RRF(Reciprocal Rank Fusion, k=60)로 합친다. 각 목록은 20건, 프롬프트에는
상위 5건이 들어간다. 값은 `settings.rag_candidates` `rag_top_k` `rag_rrf_k` 다.

RRF 는 후보를 고르는 데만 쓰고, 근거 번호의 순서는 코사인 유사도로 매긴다. RRF 는 두 목록에
다 있는 것을 무조건 위로 올려서, 09.14 실측에서 벡터 1순위(ARC-003, 0.663)가 어휘 목록에도
걸린 진척률 산정체계 청크(0.604)에 밀려 4위로 갔다. 그래서 RRF 상위 10건(top_k 의 2배)을
후보로 두고 그 안에서 코사인 내림차순으로 5건을 뽑는다. 어휘로만 걸린 정확 일치도 후보에는
남는다.

| 갈래 | SQL | 인덱스 |
|---|---|---|
| 벡터 | `1 - (embedding <=> 질문벡터)` 내림차순 | `ix_doc_chunk__embedding_hnsw` (V1) |
| 어휘 | `content_tsv @@ websearch_to_tsquery('simple', q)` 또는 `q <% content` (트라이그램 word_similarity) | `ix_doc_chunk__tsv` `ix_doc_chunk__content_trgm` (V1) |

한국어는 조사가 붙어 `tsvector 'simple'` 로는 "이행률은" 과 "이행률" 이 다른 토큰이다.
그래서 어휘 쪽 본체는 트라이그램이고, tsvector 는 `SWFR.RAG.001` 같은 코드·영문의 정확
일치를 위해 남긴다. 벡터 검색은 원문 질문으로, 어휘 검색은 모델이 다듬은 `query` 로 한다.

검색 범위는 항상 `project_id = any(범위)` 다. 범위는 요청의 `projectScope` 와 접근 가능
사업의 교집합이고, 교집합에 빠지는 사업이 있으면 403 이다(SER.SEC.003).

## 4. 근거 게이트 (SWFR.RAG.007)

RRF 점수는 순위만 남기고 "얼마나 가까운가" 를 버려서 문턱을 세울 수 없다. 그래서 게이트는
후보 전체의 **최고 코사인 유사도**로 판단한다. 문턱은 `settings.rag_min_similarity`,
기본 **0.55** 다.

09.14 실측(bge-m3, 저장소 문서 5건 색인: ARC-003, 진척률 산정체계, IM-001, 인프라 배치방안, README).

않다. 문서가 늘면 다시 재고, 값은 설정으로만 바꾼다.

게이트에 막히면 답변은 서버가 만든 문안이고(최고 유사도와 문턱을 같이 적는다), 모델은
불리지 않으며, `finishReason` 은 `NO_EVIDENCE` 다. 색인이 아예 없는 범위면 그렇다고 답한다.

## 5. 생성과 수치 검문 (SWFR.RAG.001 · QUR.RAG.002)

프롬프트는 `answer.py` 에 있다. 시스템 지시의 핵심 네 줄이다.

1. 수치는 '집계 값' 절에 제공된 값만 그대로 인용한다. 없는 수치는 만들지 않고, 제공된 값을
   더하거나 나누어 새 수치를 만들지도 않는다.
2. 사실은 '근거' 절의 내용에서만 가져온다. 근거에 없는 내용은 모른다고 말한다.
3. 근거를 인용한 문장 끝에 근거 번호를 `[1]` 처럼 붙인다.
4. 제목·목록 기호 없이 문단으로 답한다.

사용자 메시지에는 질문, 집계 값(있으면 한 줄씩 `- 차원 값: 값단위`), 근거(번호 + 문서명 +
표제 경로 + 원문)가 들어간다. 집계 값의 줄은 서버가 정한 표기(소수 자리)로 적고, 검문도
같은 표기를 기준으로 하므로 모델이 그 줄을 베끼면 통과한다.

생성이 끝나면 답변의 숫자(각주 번호와 날짜는 제외)를 **질문·집계 값 줄·근거 원문**의
숫자 집합과 대조한다. 거기 없는 숫자가 있으면 답변 끝에 "※ 위 답변의 수치 … 은(는)
집계 값과 근거 원문에 없는 값입니다" 를 붙이고 `finishReason` 을 `NUMBER_GUARD` 로 남긴다.
이미 화면에 나간 조각을 되돌릴 수는 없어서 지우는 대신 표시한다. 저장되는 본문에도 붙는다.

생성은 스트리밍이다. `LlmPort.stream()` 을 추가했고 Ollama 는 NDJSON 으로 받는다.
문맥 길이는 `num_ctx 8192` 다. 기본 4096 은 근거 청크 5개를 못 담고, 넘치면 Ollama 가 앞을
조용히 자른다.

답변 출력도 `{"answer": "<답변>"}` 스키마로 묶는다. `think: false` 를 줘도 qwen3:4b 는 답
앞에 영어로 생각을 늘어놓았고(2,800~4,200자, 60~130초), 그 생각이 화면에 그대로 흘렀으며
그 안의 숫자("Rule 4")가 수치 검문에 걸렸다. `/no_think` 표식이나 "한국어만" 지시로는
막히지 않았다. 스키마로 묶으면 첫 토큰부터 JSON 이라 생각이 들어갈 자리가 없고, 같은
질문이 7~30초에 끝났다. 대가로 조각마다 JSON 문자열 이스케이프를 풀어야 하고(`answer.decode_answer`),
이스케이프가 조각 경계에 걸리면 다음 조각을 기다린다. 그래도 섞여 나오는 `<think>` 태그는
조각 경계에 걸려도 걷어낸다.

## 6. 출처 (SWFR.RAG.003 · SWFR.RAG.006)

근거 청크마다 `message_source` 한 행이다. `footnote_no` 가 프롬프트의 번호와 같아 답변의
`[n]` 이 그대로 출처 카드로 이어진다. 원문 위치는 청크가 보존한 표제 경로(`meta_json.headingPath`)
를 조각 앞에 붙여 보여 주고, 이슈·요구사항은 `source_uri` 가 외부 링크가 된다. 업로드 문서의
저장 경로는 링크가 아니라 비우고, 화면의 문서 목록(`/p/{사업}/documents`)으로 보낸다.

`sourceId` `projectId` `projectName` 은 저장하지 않고 `doc_chunk` 를 조인해서 채운다. 청크는
본문이 바뀔 때만 다시 만들어지므로(색인은 소스 단위 전량 교체), 답변 뒤 문서가 바뀌면
그 셋은 비고 제목·조각·링크만 남는다.

## 7. 처리 단위와 이벤트

질문 하나는 세 트랜잭션이다. 모델 호출이 그 사이에 있어 DB 연결을 붙든 채 기다리지 않게 하려는 것이다.

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| prepare | 대화 소유·사업 범위 확인, 사용자 메시지 저장 | 보통의 HTTP 오류(403·404·400) |
| stream | 라우팅·임베딩 후 검색·집계·답변 메시지(STREAMING)·출처 저장, 그다음 생성 | `error` 이벤트, 메시지는 ABORTED |
| finish | 본문·상태·소요시간 확정 | |

SSE 순서는 `start → delta… → sources → (infographic) → done` 이고 프런트
`use-ask-stream.ts` 가 기대하는 그대로다. 클라이언트가 끊으면 받은 데까지 ABORTED 로 남긴다.

## 8. 실모델 검증

`tests/test_rag_live.py` 가 위 문서 5건을 실제 bge-m3 로 색인하고 대표 질문을 API 로 흘린다.
Ollama 에 두 모델이 있을 때만 돈다. 09.14 실측(qwen3:4b Q4_K_M, CPU 추론, bge-m3).

| 질문 | 경로 | 지표 | 근거 수 | 1순위 근거 | 종료 사유 | 소요 |
|---|---|---|---|---|---|---|
| GitHub 와 Redmine 의 인증 방식은 어떻게 다른가요? | DOCUMENT | 없음 | 5 | ARC-003 도구 연동방식 | STOP | 6.6초 |
| 진척률은 어떻게 산정하나요? | MIXED | progress_representative_pct | 5 | 진척률 산정체계 | STOP | 32.3초 |
| 김치찌개 맛있게 끓이는 법 알려줘 | DOCUMENT | 없음 | 0 | 없음 (최고 유사도 0.41) | NO_EVIDENCE | 3.6초 |
| 이슈가 모두 몇 건인가요? | AGGREGATE | issue_count | 0 | 없음 (최고 유사도 0.54) | STOP | 10.1초 |

답변 원문은 다음과 같았다.

- GitHub/Redmine: "GitHub는 PAT `Authorization: Bearer` 헤더로 인증하는 반면, Redmine은 API 키
  `X-Redmine-API-Key` 헤더로 인증합니다. [1]" (각주 1 이 ARC-003 3절이다)
- 진척률: "진척률은 결정론적 계산으로 산출한다. AI는 수치를 만들지 않는다. [1]" 와 함께
  `progress_representative_pct` 인포그래픽. 인포그래픽의 값은 미측정(시험이 찍지 않는다).
- 김치찌개: 서버 문안. 모델은 불리지 않았다.
- 이슈 건수: "이슈 건수는 2건입니다." 시드 DB 의 `issue` 2행과 같고 수치 검문을 통과했다.
  문서 근거는 최고 유사도 0.54 로 게이트 아래라 AGGREGATE 다.

소요 시간은 CPU 추론(VRAM 미사용) 기준이고 라우팅 2~5초가 포함된다. 첫 질문은 모델 적재가
겹치면 더 걸린다. 4절 문턱 표의 관계없는 질문 여섯 개는 최고 유사도가 전부 문턱 아래였다.

## 9. 검토한 대안

**모델에게 SQL 을 쓰게 하기(text-to-SQL)** 는 절대 규칙 1 을 정면으로 어긴다. 모델이 고른
것은 카탈로그 키뿐이고, SQL 은 카탈로그 조각으로만 조립한다(ARC-006).

**벡터만 쓰기**는 코드·고유명사("SWFR.RAG.001", "Redmine")에 약하다. 어휘 검색을 붙이는
비용은 SQL 한 절이고 인덱스는 V1 에 이미 있었다.

**RRF 점수로 게이트 세우기**는 순위 융합 점수가 절대 거리를 잃어 문턱이 뜻을 갖지 못한다.
게이트는 코사인, 순위는 RRF 로 역할을 나눴다.

**수치 검문 대신 프롬프트만 믿기**는 경량 모델에서 통하지 않았다. 지시를 어긴 숫자를
지우지는 못하지만 표시는 남긴다. 검문이 없으면 어긴 줄도 모른다.

**재순위 모델(reranker)** 은 폐쇄망 반입 모델이 하나 더 늘고 PoC 규모(문서 수십 건)에서
차이를 보기 어렵다. 넣지 않는다.

## 10. 대가

- 문턱 0.55 는 이 저장소 문서 5건으로 잰 값이다. 발주기관 문서(HWP 공문서)가 들어오면 분포가
  달라질 수 있다. 값은 설정 하나이고, 재는 절차는 `tests/test_rag_live.py` 에 있다.
- 수치 검문은 숫자 표기 일치에 기대므로 "약 43%" 같은 반올림은 어긴 것으로 잡힌다.
  모델이 집계 줄을 그대로 베끼도록 지시하는 편을 택했다.
- 라우팅 프롬프트가 카탈로그 전체(약 2,400 토큰)를 싣는다. CPU 추론에서 질문당 3~5초다.
  지표가 수백 개로 늘면 카탈로그를 먼저 좁히는 단계가 필요하다.
- 답변 뒤 원문이 바뀌면 출처의 `sourceId` `projectId` 가 빈다. 열 두 개를 더하는 마이그레이션으로
  풀 수 있으나, 다른 갈래가 V24·V26 을 쓰는 중이라 이번에는 조인으로 갈음했다.
