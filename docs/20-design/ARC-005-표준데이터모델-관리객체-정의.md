# ARC-005 표준 데이터 모델: ISO/IEC 29110 관리 객체 정의

| | |
|---|---|
| 상태 | **확정** |
| 일자 | 2026-09-10 |
| 결정 | 유저인사이트(주) 수행 책임자 |
| 관련 | `SWFR.PIP.001` `SWFR.PIP.002` `SWFR.PIP.009` `SWFR.CON.002` |

---

## 1. 결정

**관리 객체를 두 층으로 정의한다.**

- **표준 엔터티**. 도구에서 계속 갱신되며 흘러들어오는 레코드다. 요구사항·이슈·리스크·
  코드변경 등을 각각 실체 테이블로 두고 상태를 추적한다.
- **산출물 항목**. ISO/IEC 29110-5-1-2 Basic Profile 산출물 분류 22종이다. `work_product`
  테이블이 "이 사업에 과업지시서가 있는가, 어느 버전인가, 승인됐는가"를 관리한다.
  산출물 관리대장의 한 줄에 해당한다. **사업마다 22개 항목으로 된 산출물 목록이 먼저
  있고, 수집이 그 항목을 채운다.**

이 분리가 핵심이다. 도구 이슈 수백 건을 전부 "산출물"로 취급하면 29110 분류가
무의미해지고, 반대로 전부 엔터티로만 두면 "요구사항추적표가 제출됐는가" 같은
산출물 질문에 답할 수 없다. 이슈는 표준 엔터티로 흐르고, 그 집합의 증거가
산출물 항목에 매핑된다.

"ISO/IEC 29110 **기반**"의 해석도 여기서 확정한다. 프로세스 인증이나 전 산출물
강제가 아니라 **분류 참조 틀**이라는 뜻이다. 과업지시서가 이 표준을 언급할 때마다
"기반"이라 쓰거나 괄호로 참조만 하는 점과, 수행기준의 범위 한정(6절)이 근거다.

## 2. 과업지시서 근거

ISO/IEC 29110-5-1-2 가 등장하는 곳은 다섯 군데이며 역할이 각각 다르다.

| 조항 | 원문 요지 | 이 설계에서의 대응 |
|---|---|---|
| Ⅰ.3 과업 목적 | "ISO/IEC 29110-5-1-2 Basic Profile 기반의 표준 데이터 모델과 통합 현황 대시보드를 구현" | 이 문서의 존재 이유 |
| Ⅱ.2 가 | "이종 도구의 데이터를 통합 조회·집계하기 위한 표준(정규화) 데이터 모델 정의 (ISO/IEC 29110-5-1-2 Basic Profile)" | 이 문서 전체. 표준 엔터티 + 산출물 22종 |
| Ⅱ.1 가 | "29110 Basic Profile 기반 비정형 문서(docx, xlsx, hwp, pdf) 수집 및 텍스트·표 구조 추출" | 수집한 문서를 22종 항목에 연결한다. 스키마(`document_upload_id`)는 있고 판별·적재 경로는 후속 구현 |
| Ⅱ.3 가 | "진척률, 일정 준수, 품질, 리스크, 산출물 현황을 발주기관 관점으로 시각화 (29110 기반)" | 시맨틱 카탈로그의 `iso_activity` 차원(PM·SI 활동 단계). 정의는 V1 시드에 있고 실행기는 후속 구현 |
| Ⅳ.3 | 제출 산출물(요구사항, 설계, 시험, 사용자취급설명서 등) 형식 비고 "ISO/IEC 29110 Basic Profile 기반" | 우리 납품물 자체가 같은 22종 분류를 따른다 (4절 자기참조 열) |

## 3. 표준 엔터티: 도구 데이터가 흐르는 곳

물리 스키마는 `db/migration/V1__init.sql` 이 단일 정의처다(파일 안 "4. STD"
주석 구획에 표준 엔터티 테이블이 모여 있다). 여기서는 각 엔터티가
**어느 도구의 무엇에서 오는지**(승격 규칙)를 확정한다. 구현은
`app/standard/service.py` 의 `promote_connection` 과 매핑 모듈
`app/standard/mapping.py`(GitHub) · `mapping_redmine.py`(Redmine)다.

| 테이블 | 관리 객체 | 원천과 승격 규칙 (현재 구현) |
|---|---|---|
| `requirement` | 요구사항 | GitHub 이슈 중 「유형: 요구사항」 라벨(연결별 설정)이 붙었거나 제목이 `[SWFR.xxx.###]` 꼴인 것. 제목의 대괄호 코드를 `code` 로 분리 |
| `issue` | 작업·결함 | GitHub 나머지 이슈 전부, Redmine 리스크 외 트래커(작업·결함·지원) 전부 |
| `risk` | 리스크 | Redmine 「리스크」 트래커(연결별 설정) |
| `code_change` | 형상 변경 | GitHub 커밋·PR. 발생 시각이 없으면 추이 지표에 못 쓰므로 버린다 |
| `work_product` | 산출물 항목 | 4절 참조. 현재는 저장소 파일 수집(`collect_files` 설정으로 경로별 유형 지정)만 항목을 채운다. 문서 업로드·수기 등록은 `source_kind` 값만 예약돼 있다 |
| `trace_link` | 추적관계 | **테이블만 있다.** 채우는 경로(REQ ID·커밋 대괄호 ID 교차 연결)는 후속 구현이다 |
| `progress_record` `correction_action` | 진척 기록·시정조치 | **테이블만 있다.** 원천 계약 컬럼은 준비돼 있고(시정조치는 V8), 승격 경로는 후속 구현이다 |
| `change_request` `meeting_record` `acceptance_record` | 변경요청·회의·검수 | **테이블만 있다.** 원천 계약 컬럼도 아직 없다. 도구에서 수집할지 수기 등록만 할지는 정하지 않았다 |
| `entity_history` | 변경 이력 | **테이블만 있다.** append-only 로 잠가 뒀고(UPDATE·DELETE 권한 회수, INV-16) 기록하는 코드는 후속 구현이다 |

구현 안 된 것을 구현된 것처럼 적지 않는다. "테이블만 있다"가 현재 사실이다.
스냅샷·집계(과업지시서 Ⅱ.2 가 "일별 스냅샷")도 이 문서 범위 밖이며
`docs/20-design/진척률-산정체계.md` 가 다룬다.

### 공통 원천 계약

도구에서 온 모든 표준 레코드는 네 값을 갖는다. 이것이 SWFR.PIP.002 의
"원천 도구·원본 ID·원문 위치 보존"이다.

```
tool_connection_id   어느 연결(도구)에서 왔나
external_id          그 도구 안에서의 원본 ID
external_url         원문 위치 (클릭하면 원본으로)
source_kind          TOOL | DOCUMENT | MANUAL
```

`unique (tool_connection_id, external_id)` 부분 유니크 제약 덕에 같은 원본을
몇 번 수집해도 한 레코드다. 이 계약은 requirement · issue · risk ·
code_change · work_product · progress_record · correction_action 에 동일하게 걸려 있다.

원천 기준 시각은 엔터티 성격에 따라 이름이 다르다. requirement·issue 는
`source_created_at`/`source_updated_at`, code_change 는 `occurred_at`, risk 는
`identified_at` 이다. 공통 계약에 넣지 않은 이유는 "언제"의 뜻이 엔터티마다 달라서다.

승격 이전 단계로 `raw_artifact` 가 원본 payload 전체를 내용 해시와 함께 보존한다.
표준화가 틀려도 원본에서 다시 만들 수 있고, 매핑을 고친 뒤 재승격하면 된다.

## 4. 산출물 22종: 29110 Basic Profile 분류

파일럿 논리 데이터모델에서 승계한 확정본이다. 코드·화면 라벨은
`app/standard/work_product_type.py`, 활동 매핑은 V1 시드가 단일 정의처이며
이 표는 그것을 옮겨 적은 것이다. 라벨은 발주기관 어휘를 쓴다(작업 규약 1절 9번 규칙).

활동 단계는 29110-5-1-2 Basic Profile 의 두 프로세스를 따른다.

- 사업관리(PM): PM_1 계획 수립 · PM_2 계획 실행 · PM_3 평가와 통제 · PM_4 종료
- 소프트웨어 구현(SI): SI_1 착수 · SI_2 요구사항 분석 · SI_3 설계 · SI_4 구현 ·
  SI_5 통합과 시험 · SI_6 인도

시맨틱 카탈로그(V1 시드 `semantic_dimension`)에 `iso_activity` 차원이 정의돼 있어
"설계 단계 산출물 현황" 같은 질의·위젯의 집계 축으로 쓸 수 있다. 카탈로그를 읽어
SQL 을 조립하는 시맨틱 레이어 실행기는 후속 구현이다.

| 코드 | 화면 라벨 | 활동 | 자기참조 대응물 (이 저장소) |
|---|---|---|---|
| `STATEMENT_OF_WORK` | 과업지시서 | PM_1 | 과업지시서 v1.1 (발주기관 수령 문서, 저장소 밖) |
| `PROJECT_PLAN` | 사업수행계획서 | PM_1 | `docs/00-management/WBS.xlsx` (작업계획 문서는 작성 예정) |
| `PROGRESS_STATUS_RECORD` | 진척 보고 | PM_2 | WBS 실적 열 + 진척률 집계(SWFR.PIP.010) |
| `MEETING_RECORD` | 회의록 | PM_2 | 협의 발생 시 `docs/00-management/` |
| `CHANGE_REQUEST` | 변경 요청서 | PM_2 | 없음 (발생 시) |
| `CORRECTION_REGISTER` | 시정조치 대장 | PM_3 | 없음 (발생 시) |
| `ACCEPTANCE_RECORD` | 검수확인서 | PM_4 | 없음 (M6 인도 시) |

| `VERIFICATION_RESULTS` | 검토 결과 | PM_3 | 없음 (검토 수행 시) |
| `VALIDATION_RESULTS` | 확인 결과 | PM_4 | 없음 (검수 수행 시) |
| `REQUIREMENTS_SPEC` | 요구사항정의서 | SI_2 | `docs/10-requirements/IM-001-요구사항정의서.md` |
| `TRACEABILITY_RECORD` | 요구사항추적표 | SI_2 | `docs/traceability.csv` (스크립트 생성물) |
| `SOFTWARE_DESIGN` | 설계서 | SI_3 | `docs/20-design/` (IM-003, ARC 문서군) |
| `TEST_CASES_PROCEDURES` | 시험계획서 | SI_3 | `docs/30-test/` (TST, 작성 예정) |
| `SOFTWARE_COMPONENT` | 프로그램 구성요소 | SI_4 | `app/` `frontend/` 소스 |

자기참조 열이 곧 과업지시서 Ⅳ.3 의 이행 증거다. 우리 납품물이 우리 분류표의
1번 시연 데이터가 된다. "없음 (발생 시)"는 해당 관리 이벤트가 아직 없다는 뜻이지
분류에서 뺀다는 뜻이 아니다. 항목은 있고 `applicable` 컬럼으로 해당 여부를 구분한다.

### 산출물 목록은 누가 만드는가

사업을 만들 때 22개 항목을 활동 구분과 함께 같이 만든다(`create_checklist`).
항목 없이 수집이 먼저 닿으면 `upsert_work_product` 가 항목을 즉석에서 만드는데,
예전에는 이때 활동 구분이 기본값(PM_1)으로 들어갔다.

**10-29 보강 (GH-184).** 활동 구분은 유형이 정한다. 사람이 고르지 않는다. 정형화 확정
화면의 PM·SI 활동 선택을 뺐고, 수집과 문서 확정이 새 버전을 만들 때도 앞 버전 값을
물려받지 않고 `work_product_type.activity_of` 로 유형 표에서 다시 읽는다. 그래서 목록
생성과 수집의 순서가 바뀌어도 활동이 어긋나지 않는다. 10-29 에 5173·5174 를 대조했을 때
유형과 활동이 어긋난 행은 없어서 데이터는 고치지 않았다.

29110 원문의 산출물 목록과 항목 수가 완전히 같지는 않으나, PoC 관리 관점에서
위 22종으로 확정한다. 유형 목록은 스키마 CHECK 제약이므로 추가는
마이그레이션으로만 가능하다. 임의로 늘어나지 않는 것이 의도다.

## 5. 이질 데이터 표준화 규칙

도구마다 다른 이슈·상태·필드를 통일하는 규칙이다. 전부 현재 구현 그대로다.

1. **원본 무손실이 먼저.** `raw_artifact` 에 payload 전체를 보존한 뒤 승격한다.
   승격하지 않는 종류(Redmine 버전·트래커)도 버리지 않는다. 마일스톤 지표의 재료다.
2. **분류는 도구가 원래 갖고 있는 신호로, 판별 이름은 설정으로.** GitHub 는 라벨, Redmine 은
   트래커가 갈림길이다. 어떤 라벨이 요구사항이고 어떤 트래커가 리스크인지는
   연결별 설정(`mapping_rules_json`, SWFR.CON.002)이다. 매핑 논리까지 설정으로
   빼지는 않는다. 그러면 설정이 곧 코드가 되기 때문이다.
3. **상태·심각도는 정해진 표준 값으로 통일하되, 기계적 신호를 1차 근거로.** Redmine 상태
   이름은 인스턴스마다 달라서 `is_closed` 플래그를 먼저 보고 이름은 보조로 쓴다.
   GitHub 이슈에 없는 심각도는 지어내지 않고 기본값(MAJOR)을 쓴다. 집계는 표준
   값으로만 하므로 도구가 늘어도 대시보드가 바뀌지 않는다.
4. **요구사항의 원천은 도구당 하나.** 요구사항은 GitHub 이슈에서만 만든다(작업 규약
   2절). Redmine 이슈는 요구사항으로 승격하지 않는다. 같은 요구가 두 도구에서
   이중 생성되는 것을 막기 위해서고, 교차 연결은 커스텀 필드 `REQ ID` 가 맡는다.

## 6. 범위: 무엇을 강제하지 않는가

과업지시서 수행기준 두 곳이 이 모델의 깊이를 한정한다.

- Ⅱ.1 나. "PoC 수준으로 대표 도구·대표 데이터셋을 우선 대상으로 하되 **전 항목
  연동을 강제하지 않는다.**" 따라서 22종 전부의 자동 수집을 목표하지 않는다.
  `source_kind` 가 TOOL 이 아니어도(DOCUMENT·MANUAL) 표준 모델 안에 있으면
  요구 충족이다.
- Ⅱ.2 나. "PoC 수준 **핵심 지표(진척·일정·품질·산출물) 중심으로** 우선 구현."
  따라서 표준 엔터티 중 지표의 분모·분자가 되는 것(requirement·issue·risk·
  code_change·work_product)을 먼저 구현했고, 나머지 관리 객체는 테이블(스키마)까지가
  현재 범위다.

범위 확대 요구가 오면 이 두 조항과 M1 합의서를 근거로 방어한다(작업 규약 6절).

## 7. 검토한 대안

**29110 프로세스 전체 모델링.** 활동·태스크·역할까지 데이터로 들면 PoC 규모를
넘는다. 발주기관 담당자가 확인하려는 것은 프로세스 준수가 아니라 진척·품질·산출물
현황이다. 산출물 분류와 활동 단계 축만 취한다.

**도구 스키마 그대로 노출.** 정규화 없이 GitHub·Redmine 필드를 직접 쓰는 방식이다.
도구가 늘 때마다 화면·지표가 흔들리고, "GitHub 만 쓰는 업체"와 "Redmine 만 쓰는
업체"를 같은 대시보드로 볼 수 없게 된다. 표준 모델이 존재하는 이유가 이것이다.

**산출물을 문서 폴더 관례로만 관리.** `docs/` 디렉토리 구조가 곧 분류라는 방식이다.
저장소가 없는 도구 조합(Redmine 단독)에서 무너지고, 버전·승인 상태를 붙일 곳이
없다. 항목(`work_product`)과 실물(파일·문서)의 분리를 유지한다.
