## 1. 문제

10-14 협의에서 한 사업에 저장소나 Redmine 프로젝트가 여럿 붙는 경우를 확인했다. 그때 세 가지가 깨진다.

1. **화면.** 일반 이슈 목록은 도구 이름(GITHUB·REDMINE)만 보였다. 저장소 두 곳에 5번 이슈가 있으면 둘 다 `GH-5` 로 나오고 어느 저장소 것인지 알 수 없었다.
2. **추적 링크.** `trace_service.build_project_links` 가 `GH`·`RM` 접두를 도구당 연결 하나로 풀었다. 연결이 둘이면 나중에 붙인 연결이 이겨서, 저장소 A 커밋의 `Refs: GH-5` 가 저장소 B 의 5번 이슈에 이어졌다. 재수집하면 기존 링크가 끊기고 다른 연결로 새로 생긴다.
3. **거르기.** 연결 단위로 볼 방법이 없었다.

원본 저장은 이미 연결 단위다. `raw_artifact` 는 `(tool_connection_id, external_id)`, `issue` 는 `uq_issue__source(tool_connection_id, external_id)` 가 키다. `issue_key` 에는 유일 제약이 없다. 그래서 데이터가 섞이지는 않았고, 섞인 것은 조회와 해석이다. 종류가 다른 원본의 번호 충돌(일감·버전·트래커)은 #137 에서 고쳤다.

## 2. 결정

### 2-1. 참조 해석

`GH-n`·`RM-n` 은 도구만 말하고 연결은 말하지 않는다. 다음 순서로 푼다.

| 근거가 나온 연결 | 가리킨 도구 | 해석 |
|---|---|---|
| GitHub 저장소 A | `GH-n` | 저장소 A 의 n 번 |
| Redmine 프로젝트 A | `RM-n` | 프로젝트 A 의 n 번 |
| 다른 도구 | 그 도구 연결이 사업에 하나 | 그 연결의 n 번 (지금과 같다) |
| 다른 도구 | 그 도구 연결이 둘 이상 | 고르지 않는다. 미해결로 세고 `ambiguous` 에 따로 센다 |

짐작해서 잇지 않는다(QUR.PIP.001). 연결이 하나뿐인 지금 사업은 결과가 바뀌지 않는다.

### 2-2. 응답과 화면

- `SourceRef` 에 `connectionName`(연결 이름), `target`(저장소·Redmine 프로젝트), `number`(원천 번호, `issue:` 같은 종류 접두를 뗀 것)를 더했다. 기존 필드는 그대로다.
- `GET /api/projects/{id}/issues`·`/issues/summary` 에 `connectionId` 를 받는다. 사업 조건과 같이 걸어서, 다른 사업의 연결 id 를 넣으면 0건이다. 사업 접근 검사는 그대로 먼저 한다. 형식이 틀린 id 는 400 이다.
- `/issues/summary` 에 `sources`(연결별 이슈 수)를 더했다. 연결을 골라 물어도 사업 전체 연결을 낸다. 화면의 연결 고르기가 이것을 쓴다.
- 이슈 화면: 원천 열에 도구 · 연결 이름 · `저장소 #번호` 원문 링크, 위에 연결 고르기, 행을 누르면 상세(도구·연결·저장소·원천 번호·원문 링크).
- 추적 셀의 이슈 이름: 같은 도구 연결이 사업에 둘 이상일 때만 `GH-5 · 저장소 A` 처럼 연결 이름을 붙인다. 원문 링크는 원래 이슈마다 따로 저장돼 있었다.

### 2-3. DB

바꾸지 않았다. 키는 이미 연결 단위이고, 연결 이름·대상은 `tool_connection` 에 있다. 마이그레이션이 없다.

## 3. 데이터 전환

- 이슈·원본·수동 링크·이력은 그대로다.
- 같은 도구 연결이 하나인 사업: 링크 결과가 같다. 같은 링크가 같은 id 로 남는 것을 시험으로 확인했다.
- 같은 도구 연결이 이미 둘인 사업: 다음 링크 재생성 때 잘못 이어졌던 자동 링크를 닫는다. 근거는 그대로이고 해석만 바뀐 것이라 끊김(`BROKEN`)으로 두지 않고 ARC-024 2-5 의 정정으로 남긴다.

| 경우 | 상태 | 사유 | 대체 링크 |
|---|---|---|---|
| 같은 참조가 이번엔 근거가 나온 연결의 대상으로 풀림 | `SUPERSEDED` | `연결 해석 정정으로 대체: GH-5 을 …` | 새 링크 id |
| 다른 도구 참조인데 그 도구 연결이 여럿이라 대상을 정하지 못함 | `SUPERSEDED` | `연결 해석 정정으로 제외: RM-7 의 …` | 없음 |
| 원천 근거가 사라짐 | `BROKEN` | `원천 근거가 다시 확인되지 않음` | 없음 |

  판별은 옛 링크의 도착점을 `GH-n`·`RM-n` 으로 되돌려, 같은 출발점이 이번에 같은 참조를 가졌는지로 한다. 옛 링크의 관계·근거·만든 시각은 그대로 남고, 수동 링크는 건드리지 않는다.

| 확인 | 시험 |

| GitHub 연결 두 개의 같은 번호가 따로 조회된다 | `test_GitHub_연결_두_개의_…` |

| 재수집해도 중복·덮어쓰기·상태 혼입이 없다 | `test_다시_수집해도_…` |
| 연결 필터가 사업 접근 권한을 우회하지 않는다 | `test_연결_필터가_…` |

| 잘못 이어졌던 자동 링크가 정정(대체·제외)으로 닫히고, 근거가 사라진 것만 끊김이다 | `test_잘못_이어졌던_자동_링크는_…` |

수정 전 코드로 돌리면 추적 링크 시험과 기존 데이터 시험이 실패한다(둘째 연결이 첫째 연결의 링크를 가져간다).

## 5. 하지 않은 것

- `GH-n` 에 저장소를 적는 표기(`owner/repo#n`)는 읽지 않는다. 다른 도구 연결이 여럿인 사업에서 모호한 참조를 풀려면 필요하다. 그런 사업이 생기면 규칙을 정한다.
- 같은 Redmine 프로젝트 식별자를 서버만 달리해 두 번 붙이는 경우는 `uq_tool_connection__target(project_id, tool, target_resource)` 에 막혀 둘째 연결을 등록할 수 없다. 이번에 풀지 않았다. 후속 결함 GH-145 로 남긴다.
- 참여 업체 표시는 공동 수급 작업(GH-138) 뒤에 붙인다.
- 요구사항 화면의 원천 표기는 응답 필드만 같이 늘었다. 화면은 이번에 바꾸지 않았다.
