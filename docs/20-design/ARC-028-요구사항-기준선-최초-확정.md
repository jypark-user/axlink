## 1. 문제

- 요구사항이 GitHub 이슈 라벨(`유형: 요구사항`)과 제목 `[코드]` 로 늘 만들어졌다. ARC-016 의 "연결별 선택, 기본은 끈다"가 구현되지 않았다. 다른 업체 저장소에 붙이면 그 업체의 라벨 체계가 곧 우리 사업의 요구사항이 된다.
- 문서 정형화 초안을 용역사가 확정하면 그 목록이 곧바로 사업 요구사항이 됐다. 발주기관이 확정하지 않은 목록이 이행률 분모가 된다.
- 문서로 먼저 만든 코드와 같은 코드의 요구사항 이슈가 들어오면 `uq_requirement__code` 위반으로 수집 트랜잭션 전체가 실패했다(시험으로 재현). 합쳐진 행은 다음 수집이 제목·본문을 이슈 값으로 다시 덮었다.
- 사업에 없는 코드를 가리킨 커밋·이슈는 "오타"로 보고 규칙 단계에서 버려 화면에 보이지 않았다.
- 명세서 안의 위치와 문서 버전이 남지 않았다.

## 2. 결정

### 2-1. 흐름

```
용역사: 명세서 등록(관련자료에 올린 문서) → 추출 결과 정리(고치기·지우기·더하기) → 제출
발주기관: 보고 돌려보내기(사유) 또는 확정
```

| 상태 | 누가 | 보이는 곳 |
|---|---|---|
| `DRAFT` 정리 중 | 용역사(관리자) | 기준선 화면. 발주기관에게는 "정리 중"만 보이고 목록은 안 보인다 |
| `SUBMITTED` 확정 대기 | 발주기관(관리자)이 확정·반려 | 기준선 화면. 고칠 수 없다 |
| `CONFIRMED` 확정 | — | 요구사항 목록·추적표·지표 |

확정 전 목록은 `requirement_baseline_item` 에만 있고 `requirement` 에 쓰지 않는다. 요구사항 목록·이행률·추적표·AI 답 어디에도 나오지 않는다. 사업에 작업 중 기준선은 하나, 확정 기준선도 하나다(부분 유일 색인).

### 2-2. 추출과 문제 표시

`structuring.spec_items` 가 정형화 초안과 같은 규칙(표가 있으면 표만, 없으면 줄머리 코드)으로 뽑되 버리는 행이 없다. 행마다 위치(`표 2 · 5행`, `41번째 줄`)와 추출 원문(`extracted_json`)을 남긴다. 사람이 고쳐도 원문은 그대로라 무엇을 바꿨는지 보인다.

| 문제 | 제출 |
|---|---|
| `DUPLICATE_CODE` 같은 코드가 둘 이상(모든 행에 표시) | 막음 |
| `INVALID_CODE` 코드 칸이 비지 않았는데 코드 꼴이 아님 | 막음 |
| `MISSING_TITLE` 명칭 없음 | 막음 |
| `UNTRACEABLE_CODE` 코드 꼴이지만 커밋·이슈 참조 규칙(`SWFR.CON.004` 꼴)이 읽지 못함(`REQ-001` 등) | 경고만 |
| 한 건도 못 뽑음 | 막음. 화면에 "찾지 못함" |

### 2-3. 확정

요청 하나가 트랜잭션 하나다. 기준선 행을 잠그고 상태를 다시 본다. 같은 확정이 두 번 와도 둘째는 409 다. 중간에 실패하면 아무것도 바뀌지 않는다(시험으로 확인).

| 명세서 항목 | 처리 |
|---|---|
| 새 코드 | 새 `requirement`(원천 `DOCUMENT`, 상태 `DEFINED`) |
| 같은 코드, 제목·중요도 같음 | 기존 행에 `baseline_id` 만 붙인다 |
| 같은 코드, 내용 다름 | 기본은 기존 정의를 둔다. 발주기관이 고른 코드만 명세서 내용으로 바꾸고 이력(`title`·`priority`)을 남긴다 |
| 기존에만 있는 코드 | 지우지 않는다. 기준선 밖(`baseline_id` 없음)으로 남고 화면에 따로 보인다 |

- 기존 행은 ID·원천 연결·근거 상태·발주기관 지정(ARC-025)·추적 링크·이력이 그대로다. 요구사항마다 이력 `baseline: v1 SAME|CHANGED|NEW` 를 더한다.
- 본문은 판정에 쓰지 않는다. 이슈에서 온 요구사항의 본문은 이슈 본문 전체라 명세서 칸과 늘 다르다. 화면에서 나란히 본다.
- 사업의 모든 연결에서 `requirement_from_issues` 를 끈다. 끈 연결은 확정 결과와 연결 이력에 남는다.
- 같은 트랜잭션에서 추적 링크를 다시 만든다. 새 코드가 생겨 미해결이던 참조가 이어진다.
- 확정한 역할(`CLIENT`·`SUPER_ADMIN`)을 남긴다. 관리자가 확정하면 화면에 "(관리자)"로 보인다.

### 2-4. 수집

| 경우 | 요구사항으로 분류된 이슈 |
|---|---|
| 연결 설정 켜짐, 기준선 없음 | 지금처럼 만든다. 단, 같은 코드가 이미 있으면 새로 만들지 않는다. 원천이 없는 행(문서)이면 이 이슈를 원천으로 잇고 근거 상태만 준다. 다른 원천이 가진 코드면 붙이지 않고 충돌로 센다(일반 이슈로 간다) |
| 연결 설정 꺼짐 또는 기준선 확정 | 만들지 않는다. 이미 이어진 요구사항이면 근거 상태만 갱신한다. 아니면 일반 이슈로 간다 |

문서에서 온 행과 기준선에 든 행은 수집이 코드·제목·본문·중요도를 덮지 않는다. 발주기관 지정은 어느 경우에도 덮지 않는다(ARC-025 그대로).

### 2-5. 미해결 참조

근거 규칙에 코드 꼴이면 다 넘기고, 사업에 없는 코드는 잇지 않고 `requirement_unresolved_ref` 에 (코드, 출처, 근거 줄, 링크)로 남긴다. 링크를 만들 때마다 사업 단위로 다시 쓴다. 설계 문서 판별(ARC-024)은 오탐을 막으려고 사업의 실제 코드 목록을 그대로 쓴다.

### 2-6. 문서 정형화 초안

초안 확정은 산출물 버전 등록만 한다. 요구사항을 만들지 않는다. 확정한 기준선이 있는 사업에 새 명세서를 올려도 기준선은 바뀌지 않는다. 기준선 등록은 확정한 기준선이 있으면 거절한다(409).

## 3. DB (V53)

- `requirement_baseline`: 버전, 상태, 원천 문서(파일 이름·해시·문서 버전), 등록·제출·확정한 사람과 시각, 확정한 역할, 반려 사유, 확정 결과(기존 정의, 명세서에 없는 코드, 끈 연결).
- `requirement_baseline_item`: 순서, 코드·명칭·설명·중요도, 위치, 추출 원문, 사람이 더했는지, 확정 때 붙은 요구사항과 판정.
- `requirement.baseline_id`·`baseline_item_id`.
- `tool_connection.requirement_from_issues`: 기존 행은 `true`, 새 행 기본 `false`.
- `requirement_unresolved_ref`.
- `entity_history` 유형에 `REQUIREMENT_BASELINE`.

지우거나 다시 만드는 데이터는 없다. 적용된 V51·V52 는 고치지 않았다.

## 4. 기존 사업 전환

1. 마이그레이션만으로는 아무것도 바뀌지 않는다. 기존 연결은 계속 이슈로 요구사항을 만든다. 요구사항 화면 머리에 "기준선 미확정 · 지금 목록은 도구 이슈에서 만든 요구사항"이 보인다.
2. 용역사가 IM-001 을 명세서로 등록·제출한다. 미리보기에서 같음·다름·새 코드·명세서에 없는 코드·끌 연결이 보인다.
3. 발주기관이 확정한다. 내용이 다른 코드 중 명세서로 바꿀 것만 고른다.
4. 실데이터 전환은 5174 DB 사본에서 먼저 해 본다. 5173 공개 DB 는 사용자가 정한 시점 전에는 바꾸지 않는다.

## 6. 하지 않은 것

- 확정 뒤 변경(새 명세서 버전 대조·사유·확정, 폐기 표시). 후속 단위다.
- 요구사항 화면에서 기준선 밖 요구사항을 따로 거르는 필터. 응답에 `inBaseline` 만 더했다.
- 연결별 요구사항 생성 설정을 화면에서 켜고 끄는 것. 확정이 끄는 것만 있다.
- 실제 모델·5174 화면으로 확인하지 않았다.
