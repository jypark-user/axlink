# AX Link 진척률 산정 체계

데이터 분석과 AI의 역할 분담 · 데이터 수준별 산출 결과
v0.2 · 2026-08-27

---

## 0. 전제 — 진척률은 AI가 추측하지 않는다

이 문서에서 가장 중요한 원칙이다.

> **진척률은 결정론적 계산으로 산출한다. AI는 수치를 만들지 않는다.**

AI가 담당하는 것은 **연결**과 **설명**뿐이다. 발주기관이 *"AI가 진척률을 추측하는 것"* 으로
오해하면 이 프레임워크의 신뢰성 근거가 무너진다.

| | 데이터 분석 (결정론적) | AI (임베딩 · LLM) |
|---|---|---|
| **하는 일** | WBS 파싱 · 가중합 · 계획선 안분 · 산출물 존재 확인 · 이슈 집계 · 편차·지연 판정 · 일별 스냅샷 | 산출물명↔파일 매칭 · WBS항목↔이슈 연결 · 문서 유형 판별 · 지연 사유 추출 · 자연어 응답 생성 |
| **출력** | **수치** | **연결과 문장** |
| **재현성** | 동일 입력 → 동일 출력 | 유사도 임계값에 따라 변동 → **근거·신뢰도 병기** |

즉 **`진척률 39%`는 계산 결과이고, `"외부 연계 규격 협의 지연"`은 AI가 찾아낸 설명이다.**

## 1. 데이터 수준 정의

용역업체가 제공하는 데이터의 완비도에 따라 4단계로 나눈다.

| 수준 | 조건 |
|---|---|
| **L1** | WBS 완비 — 항목 · 산출물 지정 · 가중치 · 실적 |
| **L2** | WBS 구조만 — 항목 · 산출물 지정 · 계획기간 (가중치·실적 없음) |
| **L3** | WBS 없음 — 이슈 관리 도구 사용 (상태 · 진척도 · 마일스톤) |
| **L4** | 형상관리만 — 커밋 · PR · 파일 |

## 2. L1 — WBS 완비

### 2.1 필요 요소

| 구분 | 항목 | 출처 |
|---|---|---|
| 필수 | WBS ID · 업무분류 · **산출물** · 시작일 · 종료일 · **가중치** · **실적** | WBS 파일 (xlsx) |
| 필수 | 산출물 저장 위치 | 형상관리 저장소 `docs/` 등 |
| 1회 확인 | 산출물명 ↔ 실제 파일 경로 매핑 | 온보딩 (AI 추정 + 사람 승인) |

### 2.2 처리

```
[데이터 분석]
  WBS 파싱 (헤더 자동 탐지 · 계층 판정 · 말단 추출)
    → 가중치 합 검증 (≈ 1.0)
    → 진척률   = Σ(말단 가중치 × 말단 실적)
    → 계획선(t) = Σ(말단 가중치 × clamp((t−시작)/(종료−시작), 0, 1))
    → 편차     = 진척률 − 계획선(오늘)
    → 지연 판정 = 계획 종료일 경과 && 실적 < 1.0

[AI]
  산출물명 → 저장소 파일 매칭 (임베딩 유사도 + 문서 유형 판별)
  WBS 항목 → 이슈·커밋 연결 (텍스트 유사도)
  지연 사유 추출 (이슈 코멘트·변경이력에서)
```

### 2.3 산출 결과

```
진척률          39.0%   (계획 55.2%, −16.2%p)          ← 측정
일정 준수율      40%     (마일스톤 2/5)                  ← 측정
진척 추이        계획선(곡선) vs 실적선(계단)             ← 측정
지연 작업        3.2 설계, 3.3 구현/인증모듈              ← 측정
근거 미확인      1건 — 3.2 실적 40% 신고, 산출물 미제출   ← 측정
지연 사유        "외부 연계 규격 협의 지연" (이슈 #204)   ← AI, 출처 표시
```

**핵심 산출물은 「근거 미확인」이다.** 실적 신고와 산출물 관측이 어긋난 지점을 짚어낸다.
이것이 착수보고서가 말한 *"보고 시점·감리 시점에 의존하는 사후적 방식"* 을 벗어나는 실체다.

### 2.4 신뢰도

`확정` — 진척률·계획선·편차·지연 판정
`추정` — 산출물 매칭 결과, 지연 사유 (근거·신뢰도 병기)

## 3. L2 — WBS 구조만

### 3.1 필요 요소

L1에서 **가중치와 실적을 제외**한 것. WBS 항목 · 산출물 지정 · 계획기간만 있으면 된다.

### 3.2 보완 산정

| 없는 것 | 보완 방법 | 표기 |
|---|---|---|
| 가중치 | **계획 기간 길이에 비례 배분** — `w_i = 기간_i / Σ기간` | "가중치 미지정 — 기간 비례 산정" |
| 실적 | **산출물 제출 여부로 이진 판정** — 제출 100% / 미제출 0% | "실적 미기재 — 산출물 기준 산정" |

기간 비례 배분은 실제 가중치를 잘 근사한다. PM-002 샘플로 검증했을 때
기간 안분 계획선이 파일의 계획값을 0.2%p 차이로 재현했다.

### 3.3 산출 결과

L1과 **같은 화면**이 나오되 진척률에 `추정` 표기가 붙는다.

```
진척률          33.3%  (추정 — 산출물 기준)   [ⓘ 산정 방식]
계획선          기간 안분                     ← 측정
지연 작업        3.2 설계                     ← 측정
근거 미확인      해당 없음 — 실적을 산출물로 산정하므로 대조 대상이 아님
```

**잃는 것은 「근거 미확인」 항목 하나다.** 실적 자체를 산출물에서 뽑았으니 대조할 짝이 없다.
자기신고와 관측을 비교하는 기능이 사라지는 것이 L2의 실질적 손실이다.

이진 판정이라 진척률이 계단식으로 움직인다. 부분 진행을 표현하지 못한다.

## 4. L3 — WBS 없음 · 이슈 관리만

### 4.1 필요 요소

| 구분 | 항목 | 출처 |
|---|---|---|
| 필수 | 이슈 · 상태 · **진척도(done_ratio)** · 버전(마일스톤) · 기한 | Redmine 등 이슈 도구 |
| 선택 | 산출물 저장 위치 | 형상관리 저장소 |

Redmine은 이슈마다 `done_ratio`(0~100%) 필드를 기본 제공하며 REST API로 조회된다.
이슈 수집에 이미 포함되므로 **추가 수집 비용이 없다.**

### 4.2 보완 산정

```
[데이터 분석]
  마일스톤(버전)을 WBS 대분류로 간주
    → 마일스톤 진척 = Σ(이슈 done_ratio) / 이슈 수
    → 전체 진척률   = Σ(마일스톤 가중치 × 마일스톤 진척)
       · 마일스톤 가중치는 이슈 수 또는 기간에 비례 배분
    → 계획선 = 마일스톤 기한 기준 안분

[AI]
  이슈 제목·본문을 클러스터링하여 작업 성격별로 묶어 제시
  (WBS 대분류를 대신하는 구조를 추정 — 참고용)
```

### 4.3 산출 결과

```
진척률          41%  (추정 — 이슈 진척도 기준)
계획 대비        마일스톤 기한 기준으로만 판정 (작업 단위 계획선 없음)
지연             마일스톤 단위 — "2차 마일스톤 기한 8/15 경과, 미완료 이슈 7건"
지연 사유        ✓ AI 추출 가능 (이슈 코멘트가 오히려 풍부)
근거 미확인      ✗ 산출물 지정 정보가 없어 대조 불가
```

**작업 단위 해상도가 떨어진다.** *"3.2 설계가 지연됐다"* 는 못 하고
*"2차 마일스톤이 지연됐다"* 까지만 된다. 관리 대화의 구체성이 한 단계 낮아진다.

다만 **지연 사유 추출은 오히려 잘 된다.** 이슈 코멘트가 WBS 셀보다 정보량이 많다.

## 5. L4 — 형상관리만

### 5.1 필요 요소

커밋 · PR · 저장소 파일 목록.

### 5.2 처리 — 진척률을 산출하지 않는다

**커밋 수로 진척률을 만들지 않는다.** 근거 게이트와 같은 원칙이다.

```
[데이터 분석]
  활동량 집계 — 커밋 빈도 · PR 처리 시간 · 저자 수 · 최근 활동일
  산출물 현황 — docs/ 파일 목록과 갱신 시각
  정체 감지   — 최근 N일 활동 없음

[AI]
  커밋 메시지·PR 제목에서 작업 주제 추출 (무엇을 하고 있는지)
```

### 5.3 산출 결과

```
진척률          산출 불가
                WBS 또는 이슈 진척도 정보가 없어 근거를 확보할 수 없습니다.
                WBS를 등록하면 산출됩니다.

관측 가능 항목
  최근 30일 커밋      128건 (주 평균 30건, 직전 4주 대비 −18%)
  산출물 제출         3 / 12건 확인
  최근 활동           2일 전
  진행 중 주제        인증 모듈, 데이터 파서   ← AI 추출
```

**"진척률 산출 근거가 없다"는 사실 자체가 관리 정보다.** 억지 숫자보다 유용하다.

## 6. 수준별 답변 가능 범위

발주기관이 실제로 던지는 질문 기준으로 정리하면 이렇다.

| 발주기관의 질문 | L1 | L2 | L3 | L4 |
|---|---|---|---|---|
| 진척률이 얼마인가 | **측정** | 추정 | 추정 | ✗ |
| 계획 대비 어떤가 | **측정** | **측정** | 마일스톤만 | ✗ |
| 어느 작업이 지연됐나 | **작업 단위** | 작업 단위 | 마일스톤 단위 | ✗ |
| 왜 지연됐나 | AI 추출 | AI 추출 | **AI 추출 (양호)** | 부분 |
| 신고가 사실인가 | **대조 가능** | ✗ | ✗ | ✗ |
| 산출물은 나왔나 | ✓ | ✓ | ✓ | ✓ |
| 활동은 있나 | ✓ | ✓ | ✓ | ✓ |

**「신고가 사실인가」에 답할 수 있는 것은 L1뿐이다.** 이것이 WBS 완비를 요구할 실질적 근거다.
그리고 **산출물 현황과 활동 여부는 모든 수준에서 나온다** — 형상관리만 붙어도 확보되는 최소 보장선이다.

## 7. 구현 비용

| 수준 | 추가 구현 | 비용 |
|---|---|---|
| L1 | WBS 파서 · 가중합 · 계획선 · **산출물 매칭** | **중~대** |
| L2 | 기간 비례 배분 · 이진 실적 판정 | 소 |
| L3 | 마일스톤·`done_ratio` 집계 | 소 (수집에 이미 포함) |
| L4 | 활동량 집계 | 소 |

**비용의 대부분이 L1에 몰려 있고, L2~L4는 거의 부가 비용이 없다.**
L1을 만들면 나머지는 같은 파이프라인에서 입력만 갈아 끼우는 수준이다.

L1 안에서도 **산출물 매칭이 유일한 난제**다. AI 임베딩으로 추정하고
온보딩에서 사람이 한 번 승인하는 방식으로 우회한다.

## 8. 화면 표기 원칙

수준이 낮을 때 **무엇이 없어서 무엇을 못 하는지**를 화면에 드러낸다. 숨기지 않는다.

```
진척률  41%   추정                              [ⓘ]
              이슈 진척도 기준으로 산정했습니다.
              WBS를 등록하면 작업 단위 진척률과
              실적 대조가 가능합니다.
```

이 안내가 두 가지를 동시에 한다. 발주기관에게는 **수치의 한계**를 알리고,
용역업체에게는 **WBS를 올릴 동기**를 준다. 강제하지 않고 유도한다.

## 9. PoC 적용 범위

| | 구현 | 근거 |
|---|---|---|
| L1 | ✓ 완전 구현 | 자기참조 프로젝트에 WBS를 작성하여 시연 |
| L2 | ✓ 구현 | 추가 비용 소 |
| L3 | ✓ 구현 | Redmine `done_ratio` 수집에 포함 |
| L4 | ✓ 구현 (산출 불가 안내 포함) | 활동량 집계만 |

전 수준을 구현하되 **시연은 L1 중심**으로 한다.
L2~L4는 최종보고서의 **확산 방안**에서 *"용역업체 성숙도에 따른 단계적 적용"* 으로 서술한다.

## 10. 도구 조합별 대응 — "GitHub만 쓰는 업체는?"

### 10.1 핵심 — WBS는 도구가 아니라 파일이다

GitHub에는 WBS 기능이 없다. 그러나 **`SWFR.PIP.010`은 WBS 도구가 아니라 WBS 문서를 파싱한다.**
이 구분이 전체 대응의 열쇠다.

```
WBS 도구가 필요한 게 아니다.   →   WBS 파일이 저장소에 있으면 된다.
```

용역업체가 이미 xlsx로 WBS를 관리하고 있다면 — 대부분 그렇다 —
그 파일을 저장소 `docs/00-management/` 에 커밋하기만 하면 **L1이 성립한다.**
새로 배울 도구도, 이중 입력도 없다. 시나리오 S2-4가 정확히 이 장면이다.

### 10.2 도구 조합별 도달 수준

| 용역업체 도구 | WBS 파일 | 도달 수준 | 비고 |
|---|---|---|---|
| GitHub + Redmine/Jira | 저장소에 있음 | **L1** | 완전. 자기참조 프로젝트가 이 경우 |
| **GitHub만** | 저장소에 있음 | **L1** | **가중치·실적이 파일에 있으면 도구 무관하게 L1** |
| GitHub만 | 있으나 가중치 없음 | L2 | 항목 수 균등 가중 · 추정 표기 |
| GitHub만 | 없음 | **L3** | GitHub Milestone + Issue 종료율로 대체 산출 · 추정 표기 |
| GitHub만 | 없음 · 이슈도 안 씀 | L4 | 산출하지 않음. 커밋·PR 활동만 표시 |
| Redmine/Jira만 | — | L3 | `done_ratio` · 버전 달성률 |

**GitHub만 쓰는 업체도 L1~L4 어디든 갈 수 있다.** 결정하는 것은 도구가 아니라
그 업체가 WBS를 관리하고 있느냐다. 도구 문제가 아니라 관리 성숙도 문제다.

### 10.3 L3에서 GitHub이 제공하는 것

WBS가 없을 때 GitHub에서 끌어올 수 있는 진척 근거는 셋이다.

| 근거 | GitHub 요소 | 한계 |
|---|---|---|
| 단계 구분 | Milestone | 가중치가 없다 — 균등 가중 |
| 항목 진행 | Issue open/closed | 이슈 크기가 제각각이다 |
| 산출물 | 저장소 파일 (`docs/`) | 계획 산출물 목록이 없어 **제출률 분모를 모른다** |

세 번째가 결정적이다. **계획이 없으면 지연을 판정할 수 없다.**
그래서 L3의 결과는 "지금까지 무엇을 했는가"까지이고,
"계획 대비 얼마나 늦었는가"는 나오지 않는다. 화면에도 그렇게 표기한다.

### 10.4 온보딩에서 하는 일

용역업체 연결 시점(S2-4)에 시스템이 판정하고, **그 자리에서 무엇이 없는지 알려준다.**

```
연결된 도구      GitHub
WBS 파일         찾지 못했습니다

  현재 산출 가능 수준: L3 (추정)
    · 진척률은 Milestone·Issue 기준 추정치로 표시됩니다
    · 계획 대비 지연 판정은 제공되지 않습니다

  L1로 올리려면
    WBS 파일(xlsx)을 저장소에 커밋하고 아래 4개 컬럼을 포함해 주세요.
      업무분류 · 가중치 · 계획기간(시작·종료) · 연결 산출물
                                          [WBS 파일 지정]  [L3로 진행]
```

**강요하지 않는다.** L3로도 동작하고, 무엇을 하면 무엇이 좋아지는지만 알려준다.
발주기관 화면에는 그 프로젝트의 산출 수준이 함께 표시되므로,
WBS를 올리지 않았다는 사실 자체가 발주기관에게 보인다.

### 10.5 자기참조 프로젝트가 곧 이 시연이다

우리 프로젝트는 GitHub에 **요구사항 이슈 41건 + 마일스톤 M1~M6 + WBS 파일**을 모두 둔다.
Redmine은 작업 이슈·리스크·결함을 맡는다. 그래서 한 저장소에서 두 가지를 보여줄 수 있다.

- Redmine을 함께 연결한 상태 → L1 (완전)
- Redmine 연결을 끊은 상태 → **여전히 L1** (WBS 파일이 저장소에 있으므로)
- WBS 파일 지정을 해제한 상태 → L3 (Milestone·Issue 기준 추정)

**같은 프로젝트로 세 수준을 모두 시연할 수 있다.** M4 시연에서 이 전환을 보여주면
"우리 회사는 Jira도 Redmine도 안 쓰는데요"에 대한 답이 화면 하나로 끝난다.
