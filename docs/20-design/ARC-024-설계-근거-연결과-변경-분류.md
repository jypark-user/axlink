## 1. 문제

요구사항 추적표의 설계 칸이 41건 모두 비어 있었다(10-08 공개 환경: 설계 0 · 구현 348 · 시험 7).
설계 문서는 저장소에 있고 요구사항 코드를 적었는데, 앱은 설계 근거를 세 길(이슈 라벨 `유형: 설계`,
Redmine 트래커 `설계`, 설계 산출물 경로 언급)로만 만들었고 저장소 설계 문서의 내용은 읽지 않았다.

커밋 분류도 넓었다. 제목 유형이 `test` 가 아니면 전부 구현으로 셌다. docs 유형 21건(링크 37개)과
병합 커밋 53건(링크 53개)이 구현으로 잡혔고, 병합 커밋 링크 47개는 같은 PR 의 링크와 겹쳤다.

## 2. 결정

### 2-1. 저장소 설계 문서를 설계 근거로 잇는다

- **어디서:** 연결마다 설정 `designDocPaths`(매핑 규칙, 쉼표로 나눈 경로 패턴)에 맞는 파일만 본다.
  기본값은 비어 있다. 다른 업체 저장소가 같은 경로·형식을 쓴다고 가정하지 않는다. 우리 저장소는
  `docs/20-design/*.md` 를 적는다.
- **무엇을 읽나:** 아래 세 꼴의 **명시적 참조**만 인정한다.

  | 꼴 | 예 | 근거 이름 |
  |---|---|---|
  | 머리 표 `관련` 행, 목록형 `- 관련 요구사항:` 줄 | `\| 관련 \| SWFR.PIP.003 ... \|` | 관련 행 |
  | "요구사항 대응표" 절의 표 행(첫 칸이 코드) | IM-003 12절 | 대응표 |
  | 절 제목 괄호 안의 코드 | `### 4.2 매핑 설정 (SWFR.CON.002)` | 절 제목 |

  본문에 지나가듯 나온 코드, 범위 표기(`SWFR.CON.001~007`), 유사한 문장은 근거가 아니다.
- **무엇을 남기나:** 저장소, 경로, 커밋 SHA, blob SHA, 줄 번호, 절 제목, 문서 ID, 문서에 선언된 상태,
  근거 꼴, 한정어. 링크 주소는 그 커밋의 그 줄(`blob/<커밋>/<경로>#L<줄>`)이다.
- **문서 상태:** 문서가 스스로 선언한 값만 읽는다. 머리 표 `상태` 행, 목록형 `- 상태:` 줄, 또는
  `v0.1 초안` 같은 판 표기. `확정` → 확정, `초안` → 초안, 그 밖은 미상. 발주기관 승인과 같지 않다.
- **한정어:** 참조 바로 뒤(괄호 안이나 바로 다음 낱말)에 `미결`·`검토 필요`가 붙으면 그대로 남긴다(예: `SWFR.PIP.007`(미결), `(SWFR.PIP.007 미결)`).
  "설계 참조가 있음"과 "완료 조건을 충족하는 설계가 있음"을 구분하는 표시다.

### 2-2. 저장소 설계 문서와 정식 산출물을 나눈다

| | 정식 산출물(`work_product`) | 저장소 설계 문서 |
|---|---|---|
| 뜻 | 제출·승인·현행 버전이 있는 29110 산출물 | 저장소에 커밋된 문서. 작성 사실만 있다 |
| 링크 출발점 | `WORK_PRODUCT` | `REPO_DOCUMENT`(원본 `raw_artifact` 의 id) |
| 근거 | `TEXT_FILE_PATH` | `DOC_REQ_REF` |

저장소 설계 문서를 산출물로 넣지 않는다. 넣으면 산출물 판정이 설계서를 제출로 센다.

### 2-3. 변경(커밋·PR)은 변경 파일과 명시적 근거로 분류한다

변경 파일을 알 때(커밋 상세·PR 파일 목록):

| 바뀐 파일 | 메시지에 요구사항 참조가 있을 때 |
|---|---|
| 코드(문서·시험이 아닌 파일) 포함 | 구현 관련 변경(IMPLEMENTS) |
| 시험 파일(`tests/`·`test/` 아래, `test_*.py`, `*_test.py`, `*.test.ts(x)`, `*.spec.ts(x)`) 포함 | 시험 연결(TESTS) |
| 설계 문서(`designDocPaths`) 포함 | 설계 변경(DESIGNS) |
| 그 밖의 문서만(`docs/` 아래이거나 `.md` 등 문서 확장자. 관리·매뉴얼) | 잇지 않는다(산출물 경로가 맞으면 기존 DELIVERS 규칙) |

파일 분류는 경로 관례만 쓴다. 시험·문서 관례를 벗어난 저장소에서는 대부분 "코드"로 읽혀 지금과 같은
구현 관련 변경이 된다. 덜 나누는 쪽으로 틀리지, 근거를 지어내지 않는다.

섞인 변경은 해당하는 관계를 모두 만든다. 제목 유형(`docs`, `test`)만으로 정하지 않는다.
변경 파일을 모를 때는 지금 규칙(제목 `test` → 시험, 그 밖 → 구현)을 그대로 둔다.

"구현 관련 변경"은 구현 완료 증거가 아니고, "시험 연결"은 시험 통과 증거가 아니다. 이행률은
요구사항 상태(VERIFIED·ACCEPTED)로만 센다. 이 작업으로 요구사항 상태를 바꾸지 않는다.

### 2-4. 병합 커밋

`Merge pull request #n` 병합 커밋의 근거 가운데 **같은 PR 이 이미 같은 요구사항·같은 관계로 가진 것만**
뺀다. PR 에 없는 근거는 남긴다. PR 번호가 없는 병합(`Merge branch …`)은 그대로 둔다.

### 2-5. 기존 오분류 정정

다시 확인되지 않은 자동 링크를 세 갈래로 나눈다.

| 상태 | 언제 | 남기는 것 |
|---|---|---|
| `SUPERSEDED` 대체 | 같은 출발·도착에 다른 관계가 새로 생김(예: 구현 → 설계) | 사유, 바뀐 시각, 대체한 링크 id |
| `SUPERSEDED` 제외 | 분류 규칙이 뺀 것(병합 커밋 중복, 관리 문서만 바꾼 변경) | 사유, 바뀐 시각 |
| `BROKEN` 끊김 | 원천 근거가 사라짐(문서 삭제, 참조 행 삭제, 원본 소실) | 사유, 바뀐 시각 |

옛 링크의 관계·근거·만든 시각은 그대로 두고 새 링크가 따로 생긴다. 수동 링크는 손대지 않는다.
대체·제외는 화면 칸에서 빼고, 요구사항 상세의 링크 목록에는 사유와 함께 남긴다.

### 2-6. 수집과 오류

- 파일 목록(트리)을 받을 때 HEAD 커밋 SHA 와 경로별 blob SHA 를 함께 남긴다.
- 설계 문서는 blob SHA 가 바뀐 것만 그 커밋 기준으로 받는다. 커밋·PR 의 변경 파일은 아직 없는 것만 받는다.
  이미 받은 것은 원본에 남은 값을 다시 쓴다. 증분 수집이 원본을 다시 받아도 변경 파일은 이어 붙인다.
- 한 번에 받는 양에 상한을 둔다(설정). 차례로 하나씩 부르고, 남은 호출 한도가 낮거나(`X-RateLimit-Remaining`)
  429 가 오면 거기서 멈추고 다음 회차로 넘긴다.
- 호출 수(요청·변경 없음·실패)를 수집 잡 통계에 남긴다.
- **조회 실패는 삭제가 아니다.** 실패한 문서는 이전 원본과 링크를 그대로 둔다. 트리에서 경로가
  빠지고 트리가 잘리지 않았을 때만 삭제로 본다(원본에 삭제 표시, 링크는 끊김). 경로가 바뀐 것은
  옛 경로 삭제 + 새 경로 추가다.

## 3. 하지 않는 것

- 본문 유사도·지나가는 언급으로 설계 근거를 짐작하지 않는다.
- 설계 연결로 요구사항 상태·VERIFIED 를 바꾸지 않는다. 설계 연결 수를 요구사항 달성률로 보고하지 않는다.
- 초안 문서를 승인·설계 완료로 판정하지 않는다.
- 공개 환경(5173)과 그 자동 동기화에는 사용자 결정 전까지 적용하지 않는다.

## 4. 추적표 생성기와 앱

`scripts/build_traceability.py`(로컬 저장소 → `docs/traceability.csv`)도 2-1 의 세 꼴만 설계 근거로 읽는다.
같은 판별 함수(`app/standard/design_refs.py`)를 쓴다. 두 결과가 다르면 원천이 다른 것이다.
생성기는 작업 트리의 현재 파일을, 앱은 마지막으로 수집한 커밋의 파일을 본다.

## 5. 대가

- 수집이 GitHub 를 더 부른다. 첫 회는 설계 문서 수만큼 + 커밋·PR 수만큼(우리 저장소 기준 약 300),
  그 뒤는 바뀐 것만이다.
- 정정 첫 회에 대체·제외가 한꺼번에 생긴다. 사유가 남아 끊김과 구분된다.
- 마이그레이션이 링크 상태·출발 유형·근거 유형 CHECK 를 넓히고 열 넷을 더한다.
