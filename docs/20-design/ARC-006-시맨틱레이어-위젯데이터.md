## 1. 결정

**화면의 모든 수치는 카탈로그 조각으로 조립한 SQL 의 집계 결과에서만 나온다.** 위젯은
명세(`spec_json`)이고, 명세에 적힌 지표·차원·필터 키가 카탈로그에 없으면 저장도 조회도
되지 않는다. LLM 은 명세의 키를 고르는 데까지만 관여한다.

파일럿의 `SemanticQueryBuilder` 풀이 방식을 파이썬 `app/semantic/` 으로 옮겼다. 카탈로그 표
세 개(`semantic_measure` `semantic_dimension` `semantic_filter`, V1 시드 + V18·V19·V23)가
원천이고 파이썬 코드에는 SQL 조각이 없다. 지표를 늘리는 일은 마이그레이션 한 줄이다.

## 2. SQL 조립 방식 (`app/semantic/builder.py`)

조립은 검증과 조립 두 단계다. 검증을 통과하지 못한 명세는 조립까지 가지 않는다.

| 단계 | 하는 일 | 실패 시 |
|---|---|---|
| validate | 템플릿이 23종 안에 있는가, measure 가 ACTIVE 인가, dimension 이 measure 의 `allowed_dimensions` 에 있는가, filter 가 `allowed_filters` 에 있고 값이 유형(enum 목록·UUID·정수·날짜·월)에 맞는가, 요청 사업 범위와 접근 가능 범위의 교집합이 비지 않는가 | `CATALOG_VALIDATION_FAILED` (400) 또는 `PROJECT_ACCESS_DENIED` (403) |
| build | 카탈로그 정의의 `select_expr` `label_expr` `requires_join` `join_clause` `row_filter` `value_expr` `column_expr` 를 이어 붙인다 | 카탈로그 정의 자체가 깨진 경우만 |

SQL 문자열에 들어가는 것은 카탈로그 표의 조각뿐이다. 사용자가 준 값(필터 값·사업 ID·행 수)은
전부 psycopg 바인드 파라미터로 간다. 이 경계 하나가 안전의 근거다.

조립 규칙 중 파일럿과 다르게 정한 것.

- **시계열은 최근 구간이 남는다.** `limit` 은 정렬 뒤에 걸리므로 시간 오름차순으로 자르면
  오래된 구간이 남고 추이 그림이 과거에 멈춘다. 시간 차원이 있으면 내림차순으로 자른 뒤
  다시 오름차순으로 감싼다.
- **한 줄 더 읽어 잘림을 안다.** `limit + 1` 로 읽고 넘치면 `truncated` 를 켠다. 화면은 이
  값으로 "상위 N건" 배지를 단다.
- **행 상한은 템플릿에 따른다.** 표·점검표·격자(`DATA_TABLE` `PROGRESS_LIST` `CHECKLIST`
  `HEATMAP`)는 200, 그래프는 100. 파일럿의 그래프 상한 20 은 산출물 22종·PM·SI 활동 10단계를
  잘랐다.
- **구간 필터는 종료일을 포함한다.** `timestamptz` 컬럼에 날짜를 `between` 으로 비교하면
  종료일 0시까지만 잡혀 종료일 하루가 빠진다. `>= 시작 and < 종료 + 1일` 로 쓴다.
- **필터가 쓰는 별칭의 조인을 찾아 붙인다.** `contractor_org_id__in` 은 `tc.` 별칭을 쓰는데
  `semantic_filter` 에는 조인 정의가 없다. 별칭을 만드는 차원(`contractor_org`)의
  `requires_join` 을 찾아 붙이고, 같은 조인이 두 번 오면 별칭 기준으로 한 번만 남긴다.
- **기간 축이 가리키는 시각 컬럼**은 표마다 다르다(`TIME_COLUMNS`). 이슈는 원천 생성시각,
  산출물은 제출시각, 형상은 발생시각, 스냅샷은 스냅샷 일자다.

### 응답 모양

컬럼은 차원 순서대로 `d0` `d1`, 라벨식이 있는 차원은 `d0_label` 이 따라붙고, 마지막이 `value` 다.
프런트 `features/widgets/widget-data.ts` 가 이 키 규칙으로 축과 계열을 고른다.

`total` 은 숫자 카드·진행 목록·불릿(`STAT_CARD` `PROGRESS_LIST` `BULLET_CHART`)에만 준다.
차원이 있으면 차원 없이 한 번 더 집계한 값이다. 카드에 기간 축을 달면 추세선은 행에서,
숫자는 `total` 에서 나온다. 진행 목록은 이 값을 기준선으로 긋는다.

`previousTotal` 은 `compareWithPrevious` 이고 차원이 없을 때, 기간 필터가 최근 N일 또는
구간이면 같은 길이의 직전 구간을 한 번 더 집계한 값이다. 그 밖의 경우는 null 이다.

`target` 은 `semantic_measure.target_value` 다. 불릿 차트가 목표선을 긋는다.

## 3. 위젯 생성 (`POST /api/widgets/generate`)

LLM 이 하는 일은 카탈로그에서 **지표·차원·템플릿을 고르고 제목 한 줄을 쓰는 것**이다.
시스템 프롬프트에 ACTIVE 지표(키·라벨·설명·허용 차원)와 차원, 템플릿 23종을 넣고 JSON
한 개만 답하게 한다. 파일럿의 도구호출 방식은 `LlmPort.complete` 만 승계했으므로(ARC-003)
JSON 텍스트를 해석한다. 생각 블록과 코드 펜스는 걷어낸다.

고른 결과의 처리.

| 모델이 고른 것 | 처리 |
|---|---|
| 카탈로그에 없는 지표 | `NOT_EXPRESSIBLE`. 그 키를 `unmatchedTerms` 로 돌려준다 |
| `measure: null` 과 이유 | `NOT_EXPRESSIBLE`. 모델이 적은 이유와 용어를 그대로 돌려준다 |
| 지표는 맞고 차원이 허용 밖 | 차원을 버리고 지표의 기본 차원을 쓴다. 추이 템플릿이면 기간 축을 붙인다 |
| 사이드바에서 고른 템플릿이 있음 | 모델의 템플릿보다 우선한다 |

차원을 거절하지 않고 바로잡는 이유는, 값은 어차피 카탈로그 집계라 지표만 맞으면 수치의
신뢰성이 훼손되지 않기 때문이다. 경량 모델은 차원 키를 자주 틀린다.

미리보기 값은 위 2절의 같은 경로로 계산한다. 생성 응답의 `preview` 와 배치 뒤 `data` 가
어긋날 수 없다.

## 4. 일별 스냅샷 (`progress_snapshot`, V23)

추이는 지금 값을 아무리 잘 세어도 나오지 않는다. 어제의 진척률은 어제 세어 둔 값뿐이다.
`progress_snapshot` 은 사업·일자당 한 줄로 핵심 지표만 담는다.

| 갈래 | 컬럼 | 근거 |
|---|---|---|
| 진척 | `level` `representative_pct` `wbs_actual_pct` `wbs_planned_pct` | SWFR.PIP.006. `app/dashboard/service.py` 의 세 갈래 산정을 그대로 쓴다 |
| 일정 | `behind_task_count` 와 계획선 대비 편차 | SWFR.PIP.007. 마일스톤 표준 객체가 없어 WBS 계획선 대비로 본다 |
| 품질 | 이슈 해결·전체, 요구사항 검증·전체, 리스크 종료·전체 | SWFR.PIP.008 |
| 산출물 | 제출·승인·적용 대상 | SWFR.PIP.009 |

WBS 진척은 저장소에서 수집한 xlsx 를 파이썬이 읽어 계산하므로 SQL 로는 못 센다. 세 갈래
진척이 위젯으로 나오려면 이 표가 다리다. `progress_*` 지표 7종과 `snapshot_*` 지표 3종을
`base_table = 'progress_snapshot'` 으로 카탈로그에 넣었다.

스냅샷 지표의 값식은 **가장 최근 스냅샷의 값**이다
(`(array_agg(col order by snapshot_date desc))[1]`). 기간 축을 달면 구간마다 마지막 값이고,
달지 않으면 최신 값이다. 평균을 내지 않는다. 진척률 30% 와 60% 의 평균 45% 는 어느 날의
사실도 아니다.

생성 경로는 `POST /api/projects/{id}/snapshots?at=` 하나다. 같은 날 다시 찍으면 덮어쓴다.
수집이 더 들어온 뒤의 값이 그날의 사실이다. **스케줄러는 두지 않았다.** 운영에서는 cron 이
이 경로를 하루 한 번 부른다. 프로세스 안 스케줄러는 워커가 둘이면 두 번 찍고, 폐쇄망
배포에서 외부 스케줄러보다 감사가 어렵다.

## 5. 대시보드·위젯 API

프런트 `features/dashboard` 가 부르는 경로를 그대로 채웠다.

| 경로 | 하는 일 |
|---|---|
| `GET /api/dashboards?projectId=` | 내가 만든 것 + 접근 가능한 사업의 기본 대시보드 |
| `GET /api/dashboards/{id}` | 레이아웃 + 위젯 명세 |
| `PUT /api/dashboards/{id}/layout` | 레이아웃 교체. 없는 위젯을 가리키면 거부 |
| `POST /api/dashboards/{id}/widgets` | 명세를 카탈로그로 검증해 저장하고 자리를 레이아웃에 붙인다 |
| `PATCH /api/widgets/{id}` · `DELETE /api/widgets/{id}` | 명세 수정 · 삭제(자리도 함께 뺀다) |
| `POST /api/widgets/{id}/data` · `POST /api/widgets/preview` | 2절의 집계 |
| `GET /api/semantic/catalog` | ACTIVE 카탈로그 |

편집 권한은 **소유자, 그리고 사업 기본 대시보드는 그 사업의 발주기관 담당자(CLIENT)와
관리자(SUPER_ADMIN)** 다. 용역사(CONTRACTOR)는 보기만 한다. 발주기관 화면은 읽기 전용이지만
(QUR.WEB.001) 그것은 원천 데이터 이야기이고, 대시보드 구성은 발주기관의 것이다.

사업에 기본 대시보드가 없으면 발주기관 담당자나 관리자가 목록을 처음 열 때 만든다. 시드
사업 말고는 만들어 주는 경로가 없어서 화면이 빈 채로 멈추기 때문이다.

## 6. 검토한 대안

**LLM 에게 SQL 을 쓰게 한다.** 값이 모델 출력에 종속되고 같은 질문에 다른 SQL 이 나온다.
절대 규칙 1 과 정면으로 어긋난다. 배제한다.

**LLM 이 명세 JSON 을 통째로 만들고 서버는 실행만 한다.** 필터 값까지 모델이 적으면 enum
밖의 값, 없는 사업 ID 가 섞인다. 검증으로 막을 수는 있지만 거절이 잦아진다. PoC 는 지표·차원·
템플릿까지만 고르게 하고 필터는 화면(사업 범위·기간 덮어쓰기)이 준다.

**스냅샷 대신 이력 표에서 시점 복원.** `entity_history` 로 임의 시점의 상태를 되짚는 방식.
WBS 진척은 파일에서 오기 때문에 이력 표로 복원되지 않고, 매 조회마다 되짚는 비용이 크다.
하루 한 줄이 단순하고 감사가 쉽다.

**프로세스 안 스케줄러(APScheduler 등).** 4절의 이유로 배제한다.

## 7. 대가

카탈로그를 매 요청마다 읽는다. 세 표 합쳐 60행이 안 되고, 캐시를 두면 마이그레이션 직후
낡은 카탈로그로 조립하는 문제가 생긴다. 요청당 수 밀리초를 감수한다.

스냅샷은 찍은 날만 점이 된다. 찍지 않은 날은 추이에 빈 구간이 생기고, 그 빈 구간은 "수집이
안 됐다" 는 사실 그대로 화면에 보인다. 메운다면 그 자체가 만들어 낸 수치가 된다.

마일스톤 달성 기준 일정 준수율(SWFR.PIP.007 의 원문)은 마일스톤 표준 객체가 생긴 뒤에
스냅샷 컬럼 하나와 지표 한 줄로 붙는다. 지금은 WBS 계획선 대비 편차와 지연 작업 수다.

`previousTotal` 은 최근 N일·구간 필터에만 정의된다. 월 필터(`IN_MONTH`)의 직전 달 비교는
아직 없다.
