# ARC-025 요구사항 상태: 근거 상태와 발주기관 지정

| 항목 | 내용 |
|---|---|
| 상태 | 초안 (2026-10-14) |
| 관련 | SWFR.PIP.008(이행률), SWFR.WEB.002(추적 조회), QUR.WEB.002(지표 산출 근거) |
| 선행 | ARC-018(요구사항 상태 출처 표시), ARC-019(작업 완료 확인) |

## 1. 문제

요구사항 이행률은 검증(VERIFIED)·인수(ACCEPTED) 상태인 요구사항 수를 전체로 나눈다. 그런데 앱에는
요구사항을 검증·인수로 바꾸는 경로가 없었다.

- 상태를 정하는 곳은 GitHub 요구사항 이슈뿐이다. 열려 있으면 정의(DEFINED), 닫히면 구현(IMPLEMENTED)까지 간다.
- DB 를 직접 고쳐도 수집이 원천 상태로 다시 덮는다.
- 이행률의 산출 근거 문장(V43)은 "시험 결과서(통과)를 올리면 검증완료로 바뀐다"고 안내했지만 그런 동작은 없다.

그래서 이행률은 늘 0% 였고, 발주기관이 근거를 보고 판단한 결과를 남길 곳도 없었다.

## 2. 결정

요구사항 상태를 둘로 나눈다.

| 상태 | 누가 정하나 | 저장 |
|---|---|---|
| 근거 상태 | 수집이 원천에서 정한다(지금은 GitHub 이슈 열림·닫힘) | `requirement.evidence_status` |
| 발주기관 지정 | 발주기관이 사유와 함께 정한다 | `requirement.decided_status` · `decided_reason` · `decided_by_user_id` · `decided_at` |

`requirement.status` 는 화면·지표·질의가 읽는 "지금 상태"다. 지정이 있으면 지정 상태, 없으면 근거 상태다.
기존에 `status` 를 읽던 이행률·요약·추적표·스냅샷·AI 표는 바꾸지 않아도 같은 값을 쓴다.

- 기본은 근거대로 움직인다. 수집은 근거 상태만 바꾼다(`status = coalesce(decided_status, 근거)`).
- 발주기관(CLIENT, 관리자)은 사유를 적고 어느 상태로든 지정한다. 올리는 것도 내리는 것도 된다.
- 지정을 거두면(되돌리기) 근거 상태로 돌아가고 그 뒤로는 다시 근거대로 움직인다. 되돌리는 사유도 남긴다.
- 지정·되돌림은 변경 이력(`entity_history`: `status`, `status_decision`, `status_decision_revert`)과
  활동 기록(`REQUIREMENT_STATUS_DECIDED`·`REQUIREMENT_STATUS_REVERTED`, 용역사 대상 알림)에 남는다.
- 용역사는 지정할 수 없다. 지정 결과와 사유, 근거 상태는 볼 수 있다.

DB 제약으로 지킨다.

- 지정이 있으면 사유(공백 아님)와 시각이 있다. 없으면 셋 다 비어 있다(`ck_requirement__decision_complete`).
- 지정이 있으면 지금 상태는 지정 상태와 같다(`ck_requirement__decided_effective`).

## 3. 화면·API

- `PUT /api/projects/{id}/requirements/{rid}/status` `{status, reason}` 지정
- `POST /api/projects/{id}/requirements/{rid}/status/revert` `{reason}` 되돌리기(지정이 없으면 409)
- 요구사항 목록·추적표·상세 응답에 `evidenceStatus`, `decision{status, reason, decidedBy, decidedAt}`,
  `statusBasis = CLIENT_DECIDED` 를 더한다. 요약에 `decided`(지정 건수)를 더한다.
- 요구사항 화면 상태 칸: 지정이면 "발주기관 지정" 표시와 근거 상태, 사유(마우스를 올리면 보임).
  발주기관에게는 "상태 지정" 버튼과 지정 창(근거 상태·지금 상태·사유 입력·되돌리기)이 보인다.
- AI 질의의 요구사항 표는 지정 상태를 "VERIFIED(발주기관 지정)" 처럼 출처와 함께 말한다.

## 4. 이행률 산출 근거 문장

V51 에서 고친다. 검증·인수는 발주기관이 근거를 보고 사유와 함께 지정한다고 쓰고, 없는 동작(시험 결과서
업로드로 자동 전환)은 지운다.

## 5. 하지 않은 것 · 다음 단계

- 시험 결과(TST-###)를 원천으로 받아 통과하면 근거 상태를 검증으로 올리는 규칙. 시험 결과서 양식과
  완료 판단 기준을 발주기관과 정한 뒤 근거 상태 쪽에 더한다. 그때도 지정은 그대로 우선한다.
- 지정 일괄 처리, 지정 사유 양식. 실제 사용 의견을 보고 정한다.
- 근거 상태가 지정과 크게 어긋날 때(예: 인수 지정 뒤 원천 이슈가 다시 열림) 알리는 일. 지금은 화면에 근거 상태를
  나란히 보이는 것까지다.

## 6. 대안

| 대안 | 버린 이유 |
|---|---|
| 상태 열 하나를 사람이 고치게 둔다 | 수집이 덮어쓴다. 근거와 판단이 섞여 출처를 알 수 없다 |
| 검증·인수만 수동, 나머지는 근거로만 | 0% 를 움직이기는 되지만, 범위 밖 판단(반려)이나 근거가 늦는 경우를 반영하지 못한다. 사용자 결정(10-14)으로 어느 상태로든 지정하게 했다 |
| 지정을 별도 표로만 두고 읽는 곳마다 합친다 | 이행률·스냅샷·AI 표·추적표가 모두 바뀌어야 하고 하나라도 빠지면 수치가 어긋난다(절대 규칙: 메뉴와 질의의 값이 같아야 한다) |
