# ARC-002 추적 ID 체계를 요구사항 코드로 통일

| | |
|---|---|
| 상태 | **확정** |
| 일자 | 2026-09-08 |
| 결정 | 유저인사이트(주) 수행 책임자 |

---

## 1. 결정

**추적 ID 의 요구사항 축을 `REQ-###` 에서 요구사항정의서(IM-001)의 코드 체계로 바꾼다.**

| 축 | 종전 | 확정 |
|---|---|---|
| 상위 기능요구사항 | 없음 | `SFR.<영역>.###` (과업지시서 항목) |
| 소프트웨어 요구사항 | `REQ-###` | `SWFR.<영역>.###` |
| 품질 요구사항 | `REQ-###` | `QUR.<영역>.###` |
| 보안·기타 요구사항 | `REQ-###` | `SER.<영역>.###` |

영역 코드는 `CON`(연계) `PIP`(파이프라인) `WEB`(워크스페이스) `RAG`(질의) `DEM`(데모)
`SEC`(보안) 여섯이며, 과업지시서 Ⅱ.1 의 구분을 그대로 쓴다.

설계·시험·리스크·결함 축(`ARC-###`·`TST-###`·`RSK-###`·`DEF-###`)은 그대로 둔다.

---

## 2. 배경

작업 규약(CLAUDE.md 2절)은 착수 시점에 요구사항 ID 를 `REQ-###` 로 정했다. 그런데 이후
작성한 IM-001 요구사항정의서는 과업지시서 구조를 그대로 따라 `SWFR.CON.001` 형식으로
41건을 확정했고, GitHub 이슈 51건도 같은 형식으로 등록했다. 커밋 태그 역시 실제로는
`[SWFR.PIP.010]` 을 써 왔다.

즉 **규약만 혼자 옛 체계에 남아 있었다.** 그 결과 두 가지가 깨져 있었다.

1. `scripts/build_traceability.py` 가 `REQ-###` 만 인식해 정상 커밋 8건을 규약 위반으로
   잡았다. CI 가 계속 빨간불이고 PR 이 병합되지 못했다.
2. `docs/traceability.csv` 가 헤더 한 줄짜리 빈 파일이었다. **요구사항추적표는 납품
   산출물이다.** 자기참조 시연에서 우리 저장소가 추적표를 못 만들면 제품 주장이 성립하지 않는다.

---

## 3. 근거

**요구사항 코드는 발주기관 문서에서 온다.** 영역 코드가 과업지시서 Ⅱ.1 의 구분을 그대로
가리키므로, 발주기관 담당자가 과업지시서를 펴 놓고 추적표를 읽을 때 코드만으로 어느 과업
항목인지 짚을 수 있다. `REQ-012` 는 그 연결이 없다.

**번호를 두 벌 관리할 이유가 없다.** `REQ-###` 를 유지하려면 41건에 대해 대응표를 따로 두고
계속 맞춰야 한다. 대응표는 틀리기 시작하면 추적표 전체를 못 믿게 만든다.

**되돌리는 비용이 더 크다.** 반대 방향(코드를 `REQ-###` 로 바꾸기)은 요구사항정의서 41건,
GitHub 이슈 51건, 기존 커밋 8건을 전부 고쳐야 한다. 커밋 메시지는 소급 수정이 불가능하다.

---

## 4. 영향

- CLAUDE.md 2절 추적성 ID 표를 개정한다.
- `scripts/build_traceability.py` 의 ID 파서를 새 체계로 바꾸고, 요구사항정의서 표에서
  제목과 상위 과업 항목(`SFR.*`)을 읽어 추적표를 채운다.
- 기존 커밋은 고치지 않는다. 이미 새 체계를 쓰고 있었으므로 그대로 통과한다.
- 파일럿 시절 표기 `DSN-###` 는 종전처럼 읽기만 하고 새로 쓰지 않는다.
- 문서·커밋에 요구사항정의서에 없는 코드가 쓰이면 CI 가 잡는다. 이 규칙을 넣자마자
  `인프라-배치방안.md` 의 요구사항 오기 1건이 걸려 `SER.SEC.002` 로 고쳤다.

## 5. 대가

과업지시서 구조가 바뀌면 요구사항 코드도 따라 바뀐다. 그때는 커밋 이력에 남은 옛 코드가
고아가 된다. 사업 기간이 1년이고 과업지시서는 확정 문서라 실현 가능성이 낮다고 보고 감수한다.
