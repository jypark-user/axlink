# ARC-012 인포 템플릿 카탈로그: 그림 23종의 입력 계약

| | |
|---|---|
| 상태 | **확정** |
| 일자 | 2026-09-17 |
| 결정 | 유저인사이트(주) 수행 책임자 |
| 관련 | `SWFR.WEB.001` `SWFR.RAG.001` `SWFR.RAG.005` · ARC-006 · ARC-010 |

---

## 1. 결정

**인포 템플릿은 화면 조각이 아니라 입력 계약이다.** 템플릿마다 "어떤 모양의 값이 들어오면
어떤 그림이 그려지는가"를 한 곳(`app/dashboard/widget_template.py`)에 적고, 대시보드 위젯과
AI 답변의 인포그래픽과 관리자 화면이 모두 그 정의를 읽는다.

지금까지 템플릿은 이름 23개뿐이었다. 각 그림이 무엇을 받는지는 렌더러 코드, 대시보드
프리셋의 주석, 모델 프롬프트의 한 줄 힌트, 시맨틱 실행기의 예외 목록에 흩어져 있었다.
그래서 모델이 비율 지표에 파이를 고르거나 기간 축 없는 추이를 고르면 빈 그림이 나왔고,
사람이 새 위젯을 만들 때도 무엇이 되는지 알 길이 없었다.

## 2. 계약의 항목

| 항목 | 뜻 | 누가 읽나 |
|---|---|---|
| `purpose` `screen` | 무엇을 보여 주는 그림이고 화면에 무엇이 그려지는가 | 관리자 화면 |
| `when` | 언제 고르는가 | 모델 프롬프트와 관리자 화면이 **같은 문장**을 쓴다 |
| `measure_types` | 받는 지표 값 유형 (건수·비율·일수·편차) | 고를 때 바로잡기 |
| `dims_min` `dims_max` | 차원 수 | 저장·미리보기 검증(초과만), 고를 때 바로잡기 |
| `time_axis` | 기간 차원이 필수인지, 있어도 되는지, 안 쓰는지 | 저장·미리보기 검증(필수만), 고를 때 바로잡기 |
| `category_max` | 읽을 수 있는 범주 수. 표 성격이면 없음 | 관리자 화면. 행 상한(`row_cap`)이 실제로 자른다 |
| `uses_total` `uses_target` `uses_previous` | 전체 값·목표값·직전 구간 값을 같이 쓰는가 | 시맨틱 실행기(ARC-006 2절) |
| `options` | 렌더러가 읽는 `spec.options` 항목 | 관리자 화면 |
| `example` | 지표 + 차원 + 제목 | 관리자 화면이 실제 사업의 집계로 그린다 |
| `chat` | AI 답변의 인포그래픽으로 쓸 수 있는가 | 질의 라우팅 프롬프트 |

가족(`family`)은 여섯이다. 수치(지금 위치) · 추이(시간이 지나며) · 분포(어디에 몰렸나) ·
구성(무엇으로 이뤄졌나) · 변화(순위와 기울기) · 점검(하나씩 짚기). 대시보드 프리셋의 배열
순서와 같다.

## 3. 어디서 쓰나

```
widget_template.CATALOG
  ├─ GET /api/widget-templates      관리자 화면 「인포 템플릿」 (목록 · 계약 · 실데이터 예시)
  ├─ generation.system_prompt       위젯 생성 프롬프트의 「템플릿 (언제 고르는가)」 절
  ├─ routing.system_prompt          질의 라우팅 프롬프트. chat=True 인 것만
  ├─ builder.validate               저장·미리보기 검증. 차원 초과와 기간축 필수만 막는다
  └─ generation._fits               모델이 고른 템플릿이 값 모양과 안 맞으면 값 모양으로 정한다
```

**검증은 굳은 제약만 막는다.** 차원이 상한을 넘거나 기간축이 필수인데 없으면 400 이다. 차원이
모자라거나 지표 유형이 다른 것은 그려지기는 하므로 사람이 고른 것을 거절하지 않는다. 대신
모델이 고른 것은 `strict` 로 다 보고, 안 맞으면 `_default_template`(값 모양으로 정하는 규칙)로
바꾼다. 값은 어차피 카탈로그 집계라 그림을 바꿔도 수치의 신뢰성은 그대로다.

**프롬프트의 템플릿 절이 카탈로그에서 나온다.** 전에는 23개 이름과 한 줄 힌트였다. 지금은
템플릿마다 "언제 고르는가" 한 줄이 붙는다. 관리자 화면의 같은 칸과 문장이 같으므로, 화면에서
보이는 규칙이 곧 모델이 받는 규칙이다.

## 4. 관리자 화면은 쇼케이스다

`/templates`. 플랫폼 관리자만 메뉴에 보인다. 왼쪽은 가족별 목록, 오른쪽은 고른 템플릿의
목적·화면·입력 계약·언제 고르나·기본 크기, 그리고 **예시 값과 그 값으로 그려진 결과**를
나란히 둔다. "이런 모양의 값이 들어오면 이렇게 그려진다"를 눈으로 확인하는 자리다.

예시 값은 사업의 실제 집계가 아니라 **계약에서 만든 값**이다(`app/dashboard/template_samples.py`).
사업에 값이 없으면 빈 그림이 떠서 쇼케이스가 안 되기 때문이다. 값은 씨앗으로 만들어 매번 같고,
차원 수·시간축·전체값·목표값은 그 템플릿의 계약을 그대로 따른다. 프런트에 목업 데이터를
두지 않는다는 규칙(작업 규약 1절 7번)은 지킨다. 값은 `GET /api/widget-templates` 한 곳에서만
온다. `GANTT_SUMMARY` 도 계획·실적 두 열을 가진 예시로 그려지되, 시맨틱 집계로는 그 모양이
안 나온다는 사실을 함께 적는다.

## 4-1. 「언제 고르는가」가 모델의 판단 근거다

템플릿 선택에서 모델이 받는 정보는 이 한 문장이다. 프롬프트의 템플릿 절은 첫 줄에 "각 줄의
「언제 고르는가」를 근거로 고른다. 그림 이름의 인상으로 고르지 않는다" 를 못 박고, 템플릿마다
`KEY (라벨, 차원 n개 · 기간 차원 필수/선택/없음 · 받는 지표): 언제 고르는가 → 문장` 으로 준다.
차원 수와 기간 차원 유무가 괄호 안 계약과 맞아야 한다고 같이 적어, 모델이 값 모양과 문장을
맞춰 보게 한다. 관리자 화면의 같은 칸과 문장이 같으므로 화면에서 고친 문장이 곧 모델의 기준이다.

## 5. 뒤에 올 것

- **LLM 답변의 특정 지점에 템플릿 대입.** 지금은 집계 질문(AGGREGATE)일 때만 인포그래픽이
  붙는다. 문서 답변 안에서도 "이 문단은 숫자 카드로", "이 나열은 표로" 같은 대입이 되려면 답변
  스키마에 템플릿 슬롯을 두고 값은 시맨틱 레이어에서 가져와야 한다. 계약이 먼저 있어야 그
  슬롯을 정의할 수 있어서 이 문서가 앞선다.
- 범주 상한(`category_max`)을 값 조회 뒤에 검사해 "범주가 12개를 넘어 가로 막대로 바꿨다"
  같은 자동 교정을 붙일 수 있다. 지금은 안내 문장에만 있다.
- 시맨틱 카탈로그(`semantic_measure`)처럼 DB 로 옮기는 것은 하지 않는다. 템플릿은 렌더러
  코드와 한 몸이라 코드 배포와 같이 움직여야 한다. 대신 시험이 DB CHECK(V18)·프런트 렌더러
  등록과 같은 23종인지 고정한다.
