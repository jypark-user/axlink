## 1. 결정

**Ollama 의 `num_ctx`(컨텍스트 길이)와 `num_predict`(한 턴 최대 생성 토큰)를 코드에 박지 않고
모델별로 저장한다.** 값은 플랫폼 관리자가 설정 화면에서 정하되, 사용자가 스스로 알 수 없는
값이므로 이 서버에서 실측한 생성 속도로 권장값을 계산해 보여 준다.

같은 설계가 다른 사업(OCS-OPS Authoring Suite SDD 앱)에서 검증됐고 그것을 옮겼다. 다만
원본은 두 값을 전역 설정 하나에 두어 모델을 바꾸면 컨텍스트만 따라 바뀌고 생성 토큰은 그대로였다.
여기서는 **두 값을 모델 캐시 레코드에 모델별로 저장**하고, 모델을 고르면 그 모델의 값이
따라온다.

## 2. 왜 필요한가

Ollama 는 모델마다 최대 컨텍스트가 다르다. 그리고 로컬 장비는 생성이 느려서 **한 턴의 최대 생성
토큰이 곧 한 턴의 최장 소요 시간**이다.

실사고. `num_predict` 16000 에 생성 속도 18.6 tok/s 면 최악 860초가 걸린다. 요청 시간 제한이
600초면 그 안에 못 끝나고 프록시가 504 로 끊는다. 값을 코드에 박아 두면 장비가 바뀔 때마다
같은 사고가 난다.

기존 구현은 `AXLINK_LLM_NUM_CTX` 환경변수 하나(8192)를 모든 모델에 썼고 `num_predict` 는
보내지 않았다(모델 기본값, 대개 무제한). 09.14 실측에서 qwen3:4b 가 JSON 으로 묶지 않으면
120초를 넘긴 것(ARC-010)도 결국 이 상한이 없어서였다.

## 3. 저장 구조 (V27)

| 표 | 무엇 |
|---|---|
| `llm_model_cache` | `GET /api/tags` 응답의 캐시. (서버 주소, 모델 이름) 이 키. 최대 문맥·도구 호출 지원·파라미터 수·양자화 + 실측 속도·측정 시각 + 사람이 고른 `num_ctx`·`num_predict` |
| `llm_setting` | 지금 쓰는 서버 주소와 모델. 한 줄(id=1). 없으면 환경변수 기본값 |

목록은 캐시다. 주소를 바꾸거나 새로 고치면 **그 주소의 행을 통째로 갈아 끼운다.** 같은 이름이
남아 있으면 실측값과 설정은 물려받는다. 목록을 다시 받았다고 설정이 날아가면 안 된다.

기본값. 처음 보는 모델은 `num_ctx` 에 서버가 알려준 최대치를 그대로 채운다. 긴 문서와 코드를
한 번에 담아야 앞부분이 조용히 잘리지 않기 때문이다. 서버가 최대치를 모르면(0) 비워 모델
기본값에 맡긴다. `num_predict` 는 16000 이다.

## 4. 흐름

```
주소 입력(타이핑) ─디바운스 500ms─▶ POST /api/ai/models/refresh?baseUrl=  ─▶ /api/tags ─▶ 캐시 교체
모델 선택 ─▶ 그 모델 행의 num_ctx·num_predict 를 칸에 채움
「이 서버에서 재보기」 ─▶ POST /api/ai/models/measure ─▶ /api/generate (64토큰) ─▶ tok/s 를 행에 저장
저장 ─▶ PUT /api/ai/settings ─▶ llm_setting + 그 모델 행 갱신
```

- **조회 실패는 예외가 아니다.** 주소를 치는 중에 불리므로 한 글자마다 오류 대화상자가 뜨면
  안 된다. 200 에 `error` 문구를 실어 보내고 화면은 상태 줄에만 쓴다.
- **측정은 버튼으로만.** 모델을 고를 때 자동으로 재지 않는다. 적재 안 된 모델은 수십 초가
  걸려 화면이 멎는다. 측정 요청은 `stream:false, think:false, num_predict:64` 이고 속도는
  `eval_count / (eval_duration / 1e9)` 다. 적재 시간은 빠지고 순수 생성 속도만 나온다.
  `think` 를 끄는 이유는 추론 모델이 여기서도 길게 생각하기 때문이다.
- **측정 결과는 알림(토스트)으로.** 폼 필드에만 쓰면 화면이 안 바뀌어 아무 변화가 없던 사고가
  원본 사업에 있었다.
- 도구 호출을 지원하지 않는 모델을 고르면 그 자리에서 경고한다. AX Link 는 도구 호출을 쓰지
  않으므로(ARC-003 4절) 지금 기능에는 영향이 없다고 같이 적는다.

## 5. 권장값 계산

`frontend/src/features/settings/llm-advice.ts` 의 순수 함수다. 입력은 실측 속도 `rate`(0 이면
미측정), 현재 `predict`, 한 요청이 쓸 수 있는 초 `limit`(`AXLINK_LLM_TIMEOUT`, 0 이면 미설정),
예비 `reserve`(기본 150초. 접두 캐시가 깨졌을 때의 프리필 몫).

```
rate == 0            → "생성 속도를 아직 재지 않았습니다 …"      (숫자를 지어내지 않는다)
worst = predict / rate
limit == 0           → 최악 소요만 말하고 프록시 read timeout 확인을 권한다
budget = max(limit - reserve, 0)
advised = floor(budget * rate / 1000) * 1000
worst > budget       → ⚠ 504 경고. 값을 낮추거나 시간 제한을 worst + reserve 초로 올리라고
그 외                → 권장값과 상한 대비 % 를 보여 준다
```

시험은 실사고 재현(16000 · 18.6 tok/s · 600초 → 경고, 권장 8000), 경계값(최악 = 예산이면
여유), 미측정, 미설정 네 부류다.

`limit` 은 우리 배포의 요청 시간 제한을 읽는다. 지금은 어댑터의 httpx 타임아웃
`AXLINK_LLM_TIMEOUT`(기본 120초)이다. 프록시를 앞에 두면 그 read timeout 도 이 값 이상이어야
한다(인프라-배치방안).

## 6. 응답 처리

- Ollama 의 `done_reason` 이 `"length"` 면 내부 `stop_reason` 을 `max_tokens` 로 둔다. 도구
  호출이 있으면 `tool_use`, 그 외는 `end_turn`. `LlmResult` 에 `stop_reason`·입력 토큰·출력
  토큰이 실린다.
- `complete()` 는 `max_tokens` 면 잘린 답을 assistant 메시지로 붙이고 "출력이 길이 제한에
  걸렸으니 같은 내용을 더 작게 나눠 다시 제안하라" 는 지시를 사용자 메시지로 실어 **최대 3회**
  다시 묻는다. 3회 뒤에도 잘리면 `AI_OUTPUT_TRUNCATED`(422) 로 멈춘다. 잘린 답을 정상 답처럼
  흘리지 않는다. 도구 호출 봉합은 여기 없다. 도구 호출을 쓰지 않으니 봉합할 것이 없다.
- `stream()` 은 재시도하지 않는다. 조각이 이미 화면에 나간 뒤 다시 시작하면 답이 두 번 붙는다.
  마지막 조각의 `done_reason` 을 로그에만 남긴다.
- 로그에 모델, 입력 토큰(`prompt_eval_count`), 출력 토큰(`eval_count`), 멈춘 이유를 남긴다.

## 7. 어댑터와 기동

`llm_port()` 가 DB 의 활성 설정을 읽어 `OllamaLlm` 을 만든다. DB 에 행이 없거나 DB 에 닿지
못하면 환경변수(`AXLINK_OLLAMA_BASE_URL`·`AXLINK_LLM_MODEL`·`AXLINK_LLM_NUM_CTX`)로 돈다.
설정 화면을 한 번도 안 열어도 기동과 답변은 된다. `num_ctx` 가 비어 있으면 옵션에 넣지 않는다.

`AXLINK_LLM_PROVIDER=fake` 면 이 설정은 쓰이지 않는다. 화면이 그 사실을 알린다.

## 8. 범위 밖

- **외부 API 경로(Claude 등)** 는 이 사업에 없다. 외부 클라우드 LLM 비의존이 전제(QUR.RAG.001)
  라 어댑터가 Ollama 하나뿐이다. 출력 상한은 Ollama 가 서빙하는 모든 모델(`-cloud` 접미 모델
  포함)에 같은 설정으로 걸린다. 외부 API 어댑터가 생기면 `num_predict` 를 같은 자리에서
  읽게 한다.
- 주기 수집·프록시 타임아웃 자체를 여기서 바꾸지는 않는다. 화면은 값을 읽어 보여 줄 뿐이다.
