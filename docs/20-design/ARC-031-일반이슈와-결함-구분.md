## 1. 문제

ARC-018 은 `issue` 테이블 전부를 「일반 이슈」로 세고, 요약 카드 `total` 도 사업의 `issue` 전부로 정했다. 그런데 Redmine 결함 트래커나 GitHub 결함 라벨로 들어온 결함도 같은 `issue` 테이블에 들어간다. 그래서 일반 이슈 건수와 처리율에 결함이 섞였다. 시험 자료(IM-005A 7.3)로 보면 일반 이슈 9건이어야 할 값이 11건(처리율 7/11)으로 나왔다.

## 2. 결정

사용자 결정 DEC-02: 「전체 이슈, 일반 이슈(결함 제외), 결함을 구분한다. 포함 관계를 표시하고 중복 합산하지 않는다.」

- 결함 판별은 연결 설정의 결함 트래커 이름(Redmine `defectTracker`)과 결함 라벨 이름(GitHub `defectLabel`)으로 한다. 기본값은 비워 둔다. 승격 때 `issue.issue_kind` 를 `GENERAL`·`DEFECT` 로 채운다(V63).
- 일반 이슈 지표 6종은 `issue_kind = 'GENERAL'` 만 센다. ARC-018 2-1절의 「산식은 그대로」를 이 범위에서 대체한다.
- 이슈 요약의 기본 `total` 은 일반 이슈(결함 제외)다. 전체 이슈는 `kinds.allTotal` 로 따로 낸다. ARC-018 2-2절을 이 범위에서 대체한다.
- 전체 이슈 건수(`all_issue_count`)는 같은 `issue` 테이블의 두 종류를 함께 센 값이다. ARC-018 이 금지한 「요구사항 + 이슈 합산」과는 다르다. 화면과 산출 근거에는 「전체 = 일반 + 결함」 관계를 적고, 세 값을 더해 하나의 합계로 쓰지 않는다.
- 결함 매핑이 없는 사업은 결함을 가르지 않는다. 일반 이슈 = 전체이고, 결함 처리율은 「산출 불가」와 이유를 보인다.
- 일별 스냅샷의 일반 이슈 열은 V63 부터 결함을 뺀 값이다. 예전 행은 고치지 않고, 산출 근거에 기준이 바뀐 날을 적는다.

## 3. 대가

- V63 이전 스냅샷과 이후 스냅샷의 일반 이슈 값은 기준이 다르다. 추이를 볼 때 기준 변경일을 함께 봐야 한다.
- 결함 매핑은 지금 관리 API 로만 바꾼다(DEC-09 (a)).
