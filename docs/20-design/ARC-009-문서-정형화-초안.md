# ARC-009 문서 정형화 초안: 올린 문서를 산출물 항목과 요구사항으로

| | |
|---|---|
| 상태 | **확정** |
| 일자 | 2026-09-14 |
| 결정 | 유저인사이트(주) 수행 책임자 |
| 관련 | `SWFR.CON.007` `SWFR.PIP.001` `SWFR.PIP.002` `QUR.RAG.002` `SWFR.RAG.003` |

## 1. 결정

**올린 문서에서 산출물 유형과 요구사항 목록의 초안을 뽑고, 사람이 확인한 뒤에만 표준
모델에 넣는다.** 초안은 규칙(정규식·표 구조)이 먼저 만들고, 규칙이 못 정한 유형과 제목만
LLM 에 묻는다. LLM 이 만드는 것은 22종 중 코드 하나와 제목 한 줄뿐이다. 요구사항 코드·
본문·중요도·건수는 전부 문서에 적힌 글자에서 온다.

과업지시서 Ⅱ.1 가항의 "29110 기반 비정형 문서 수집"과 ARC-005 의 산출물 22종 항목을 잇는
자리다. ARC-005 4절이 "문서 업로드는 `source_kind` 값만 예약돼 있다"고 적어 둔 것이 이
문서로 채워진다. 스키마는 V1 의 `structuring_draft` 를 그대로 쓴다. 새 마이그레이션은 없다.

## 2. 흐름과 상태

```
업로드 → 추출(EXTRACTED) → 초안 생성(STRUCTURED) → 사람 확인 → 확정(CONFIRMED)
                                                          └→ 반려(REJECTED)
```

- 초안은 업로드 요청 안에서 추출 직후에 만든다(`app/document/service.py` → `draft_service.propose`).
  실측 70,650자 HWP 가 1초 안쪽이라 추출을 동기로 두었고, 초안도 같은 이유로 동기다.
  규칙이 다 정한 문서는 모델을 부르지 않으므로 대부분 추출 시간에 묻힌다.
- 문서 상태(`document_upload.status`)는 초안이 생기면 STRUCTURED, 확정하면 CONFIRMED,
  반려하면 REJECTED 다. 추출이 실패한 문서(FAILED)에는 초안이 없다.
- 초안 상태(`structuring_draft.status`)는 PROPOSED 로 시작한다. 확정하면 CONFIRMED,
  제안한 유형과 **다른** 유형으로 확정하면 MANUAL_OVERRIDE, 반려하면 REJECTED 다.
  MANUAL_OVERRIDE 는 규칙·모델이 틀린 기록이라 따로 센다.
- 확정과 반려는 PROPOSED 일 때만 된다. 두 번 확정하면 같은 요구사항이 두 벌 들어가므로
  `DRAFT_ALREADY_DECIDED`(409) 로 막는다.
- 목록의 "초안 확인" 은 PROPOSED 인 동안만 뜬다(`draftAvailable`). 확정 뒤에는 만들어진
  산출물 행(`workProductId`)이 붙는다.

| API | 하는 일 |
|---|---|
| `GET /api/documents/{id}/draft` | 초안 조회. 상태와 무관하게 읽힌다 |
| `POST /api/documents/{id}/draft/confirm` | 사람이 고친 값으로 확정. 산출물 한 버전 + 요구사항 + 색인 |
| `POST /api/documents/{id}/draft/reject` | 반려. 표준 모델에는 아무것도 쓰지 않는다 |

접근 범위는 문서 API 와 같다. 문서가 속한 사업에 권한이 있어야 한다.

## 3. 규칙 (`app/document/structuring.py`)

### 요구사항 추출

코드 꼴은 `[A-Z]{2,6}(.|-)[A-Z]{2,6}(.|-)\d{2,4}` 에 가운데 토막이 없는 꼴까지다.
우리 체계(`SWFR.CON.004`)가 기본이고 `REQ-001`, `FR-01` 같은 다른 사업의 표기도 받는다.
한 글자 접두(`R-1`)는 받지 않는다. 문서 안의 항목 번호와 구분이 안 된다.

**표 규칙**이 먼저다. 추출기가 표를 마크다운으로 내므로(`|` 로 시작하는 연속 줄) 그것을
행으로 읽는다.

1. 머리행에서 열을 정한다. 코드 열은 `ID·코드·번호·식별`, 글 열은 `요구사항·명칭·명·제목·
   이름·내용·설명·기능·상세`, 본문 열은 그중 `설명·내용·상세`, 중요도 열은 `중요도·우선순위·
   필수·priority` 다. 머리행에 코드 열 이름이 없어도 첫 데이터 셀이 코드 꼴이면 첫 열을 코드
   열로 본다. 머리행 자체가 코드 꼴이면 머리행 없는 표다(첫 열 코드, 둘째 열 글).
2. 코드 열의 값이 코드 꼴인 행만 요구사항이다. 같은 코드가 뒤에 또 나오면 처음 것만 받는다.
   IM-001 의 8절(시나리오 연계 표)처럼 코드를 다시 인용하는 표가 있어도 건수가 늘지 않는다.
3. 본문 열이 없으면 제목이 본문이다. 제목은 100자에서 자르고 본문은 2,000자까지 남긴다.
4. 중요도는 MoSCoW 로 옮긴다. `필수·상·높음·high·must` → MUST, `권장·중·보통·should` →
   SHOULD, `선택·하·낮음·low·could` → COULD, `제외·보류·wont` → WONT. 빈 값과 모르는 말은
   SHOULD 다.

표에서 하나라도 나오면 **줄 규칙은 돌리지 않는다.** 표가 있는 문서에서 줄 규칙까지
돌리면 표를 설명하는 문장(상위 항목 제목, 본문의 인용)이 요구사항으로 섞여 들어온다.

**줄 규칙**은 표가 없는 문서용이다. `[SWFR.CON.004] 제목` 이나 `SWFR.CON.004: 제목` 꼴의
줄이 요구사항이고, 다음 줄부터 빈 줄이나 표제나 다음 코드 전까지가 본문이다.

### 산출물 유형 판별

22종마다 단서 낱말을 둔다(`요구사항정의서·요구사항 명세서`, `회의록·참석자·협의 내용`,
`시험결과서·시험 결과` 같은 것). 점수는 파일명에 있으면 3, 문서 머리 다섯 줄에 있으면 2,
본문 앞 4,000자에서 나온 횟수(최대 3)를 더한다. 파일명 가중치가 큰 이유는 사람이 붙인
이름이 가장 정직한 단서라서다. 요구사항이 3건 이상 뽑혔으면 요구사항정의서에 4를 더한다.

1위가 3점 이상이고 2위와 2점 이상 벌어졌을 때만 정한다. 그 밖에는 유형을 비워 둔다.
확신도는 `1위 / (1위 + 2위)` 를 0.95 로 막은 값이다. 틀린 확신보다 빈칸이 낫다는 것이
원칙이다. 빈칸이면 화면에서 사람이 고른다.

### 제목·버전·작성일

문서 머리에서 읽는다. 제목은 첫 표제(`#`)나 120자 이하의 첫 줄, 버전은 `v0.4`·`버전 1.2`
꼴, 작성일은 `2026-08-27`·`2026년 8월 27일` 꼴의 첫 날짜다. 없으면 비운다.

활동 구분(PM·SI)은 판별한 유형의 산출물 자리(`work_product` 현행 행)에서 그대로 가져온다.
유형이 비었으면 활동도 비운다.

## 4. LLM 개입 범위

| | 규칙이 정했을 때 | 규칙이 못 정했을 때 |
|---|---|---|
| 유형 | 모델을 부르지 않는다 | 22종 코드 하나 또는 UNKNOWN 만 답하게 한다 |
| 제목 | 모델을 부르지 않는다 | 문서에 적힌 제목 한 줄만 옮기게 한다 |
| 요구사항 코드·본문·중요도·건수 | 모델은 관여하지 않는다 | 관여하지 않는다 |
| 버전·작성일 | 모델은 관여하지 않는다 | 관여하지 않는다 |

- 모델에는 파일명과 표를 뺀 본문 앞 3,000자만 준다. 표는 길기만 하고 유형 단서가 적다.
- 답은 `<think>` 블록을 걷어낸 뒤 22종 코드가 정확히 하나 있을 때만 받는다. 둘 이상이거나
  없으면 유형을 비우고 답 원문을 `rejectedTypeRaw` 로 화면에 보여 준다. 모델이 고른 유형의
  확신도는 0.5 로 고정한다. 규칙이 정한 것보다 낮게 본다는 뜻이다.
- 모델에 닿지 못하면(`AI_UNAVAILABLE`) 초안은 규칙 결과만으로 만들고 문서의 `error` 에
  "유형 판별을 건너뛰었습니다" 를 적는다. 모델이 죽었다고 초안을 안 만들 이유는 없다.
- 어느 모델이 관여했는지 `structuring_draft.model` 에 남긴다. 모델을 안 불렀으면 `rules` 다.

호출은 `LlmPort.complete` 하나다(SWFR.RAG.002). 구현체 선택은 `app/ai/llm.py` 의
`llm_port()` 이고, 시험은 `fake` 로 돈다.

## 5. 확정 시 적재

확정 요청(`StructuringConfirmRequest`)의 값은 사람이 고친 값이다. 초안 값을 그대로 쓸지
바꿀지는 화면에서 정한다.

**산출물 항목(`work_product`).** 도구 수집(`upsert_work_product`, ARC-005 4절)과 같은 버전
누적 규칙을 따른다. 다른 버전이면 앞 버전의 현행 표시를 내리고 새 행을 넣는다. 같은 버전
표기가 이미 있으면 그 행을 고쳐 쓴다. 같은 버전을 다시 올린 것은 내용을 바로잡은 것이지
새 버전이 아니고, 버전 유일 제약(`uq_work_product__version`)도 그렇게 요구한다.
원천은 `source_kind = DOCUMENT`, `document_upload_id`, `file_uri`(보관 경로), `authored_at`
(작성일)이다. 확정 상태가 APPROVED 면 `approved_at`·`approved_by_user_id` 를 같이 채운다.
활동 구분을 안 주면 자리 것을 물려받는다.

**요구사항(`requirement`).** `source_kind = DOCUMENT`, 상태 DEFINED, 산출물 행과 문서를
가리킨다. 같은 사업에 같은 코드가 이미 있으면(`uq_requirement__code`) 제목·본문·중요도만
갱신한다. GitHub 이슈에서 온 요구사항이면 도구 연결은 그대로 둔다. 문서는 정의를, 이슈는
이행 추적을 맡는 것이라 한 행에 합쳐야 추적이 산다. 코드가 없는 요구사항은 늘 새 행이다.

**색인.** 확정한 요구사항을 `REQUIREMENT` 소스로 색인한다(건당 1청크, 제목은 `코드 제목`,
위치는 문서 보관 경로). 문서 본문 자체는 업로드 때 `DOCUMENT_UPLOAD` 로 이미 색인돼
있으므로 두 번 넣지 않는다. 색인이 실패해도(모델 불통) 확정은 되돌리지 않고 `error` 에
적는다. 표준 모델에는 있는데 색인만 없는 상태가 반쯤 지워진 확정보다 낫다.

값 검사는 스키마 CHECK 에 걸리기 전에 사람이 읽을 말로 돌려준다. 22종에 없는 유형, 빈
제목·버전, 겹치는 요구사항 코드, 잘못된 날짜, NONE·REJECTED 로의 확정은 400 이다.

  나오는지, 표·줄 규칙, 중요도 변환, 유형 점수, 모델 답 해석.

  뽑히고(코드가 문서와 정확히 같다), 확정하면 요구사항정의서 0.4 가 현행 산출물이 되고
  요구사항 41건이 UPLOAD 원천으로 조회되며 41청크가 색인된다. 반려, 재확정 차단, 유형 변경
  기록, 같은 버전 고쳐 쓰기와 새 버전 쌓기, 모델이 유형을 고르는 경우, 모델 답을 못 읽는
  경우, 모델 불통, 규칙이 정했을 때 모델을 안 부르는지.
- `tests/test_structuring_live.py`: 실모델. 단서 낱말을 뺀 회의 기록을 `qwen3:4b` 가
  MEETING_RECORD 로 답하고 제목을 문서에서 옮기는지. 로컬 실측으로 호출당 40초 안팎이다.
  규칙이 먼저인 이유가 이것이다.

## 7. 검토한 대안

**LLM 에 추출 전부를 맡긴다.** 문서를 통째로 주고 JSON 으로 유형·요구사항을 받는 방식이다.
빠르게 만들 수는 있지만 코드와 건수를 모델이 지어낼 길이 열린다. "요구사항 41건" 이라는
수치가 모델 출력이 되면 절대 규칙 1(수치는 집계에서만)이 무너진다. 규칙이 글자를 옮기고
모델은 빈칸만 채우는 쪽으로 정했다.

**초안을 별도 엔드포인트나 큐에서 만든다.** 업로드 응답을 빨리 돌려줄 수 있다. 그러나
규칙이 정하는 문서는 모델을 안 부르므로 지연이 거의 없고, 모델을 부르는 경우도 PoC 규모에서는
요청 안에서 기다릴 만하다. 큐를 들이면 폐쇄망 반입 요소가 늘고, 화면이 "초안 만드는 중" 상태를
하나 더 다뤄야 한다. 동기로 두고 필요해지면 그때 뺀다.

**새 마이그레이션으로 초안 표를 다시 설계한다.** V1 의 `structuring_draft` 가 문서당 한 초안,
제안 유형, 확정자, 만든 산출물 행을 이미 갖고 있다. 초안 본문은 `draft_json` 에 넣으면 되고
빠진 열이 없어 그대로 쓴다.

## 8. 대가

- 규칙의 폭이 좁다. 머리행 어휘가 위 목록 밖이거나 코드가 한 토막이면 표를 못 읽는다.
  그런 문서는 요구사항이 0건인 초안이 되고 사람이 화면에서 채운다. 어휘는 겪는 문서에 맞춰
  늘린다.
- 표가 없는 요구사항 문서는 줄 규칙만 돌아 본문 경계가 거칠다.
- DOCX 추출기는 문단을 먼저, 표를 뒤에 낸다. 표와 문단의 원래 순서가 섞이지만 표 규칙에는
  영향이 없다.
- 모델을 부르는 문서는 업로드가 모델 응답 시간만큼 늦다. 화면은 업로드 응답을 기다린다.
- 같은 코드의 요구사항을 문서로 확정하면 도구에서 온 제목·본문이 문서 것으로 바뀐다.
  정의처를 문서로 보기 때문인데, 이슈 제목을 기준으로 삼는 사업이면 거꾸로일 수 있다.
