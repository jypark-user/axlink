## 1. 문제

10-07 외부 공개 확인 중 3MB 문서를 올리자 API 전체가 7분 넘게 응답하지 않았다. 업로드 요청이
`async` 처리 안에서 파일 저장·추출·청크·임베딩·초안(LLM)·DB 저장을 끝까지 동기로 돌렸고, 그동안
요청을 받는 이벤트 루프가 막혔다. ARC-009 는 "추출이 1초 안쪽이라 동기로 둔다" 고 했지만 시간은
추출이 아니라 임베딩에서 나왔다.

격리 환경(개발 DB 사본, 같은 이미지)에서 잰 단계별 시간이다. 임베딩은 CPU 의 bge-m3 다.

| 문서 | 크기 | 쪽 | 조각 | 추출 | 임베딩 | DB 저장 |
|---|---|---|---|---|---|---|
| 작은 md | 52B | | 1 | 0.0초 | 0.2초 | 0.0초 |
| PDF | 475KB | 23 | 13 | 2.7초 | 22초 | 0.05초 |
| PPTX | 1.7MB | 24 | 30 | 0.1초 | 31초 | 0.03초 |
| DOCX | 38KB | | 121 | 0.07초 | 36초 | 0.3초 |
| md | 300KB | | 100 | 0.0초 | 200초 | 0.3초 |
| md | 3MB | | 1,000 | 0.0초 | 33분 넘게(중단) | |

바꾸기 전 이미지로 올리는 동안 다른 요청은 처리가 끝날 때까지 기다렸다. PDF 16초, PPTX 29초, DOCX 37초,
300KB 문서는 60초 제한을 넘겨 헬스체크·로그인·목록이 시간 초과됐다.

## 2. 결정

### 2-1. 접수와 처리를 나눈다

- 업로드는 파일을 해시 경로에 저장하고 문서 행을 남긴 뒤 바로 끝난다. 처리 상태는 접수됨(QUEUED)이다.
- 추출·색인·초안은 API 안의 작업자(`app/document/worker.py`)가 대기열에서 하나씩 가져가 스레드에서 한다.
- 처리 상태는 `document_upload.processing_state` 다. 접수됨 · 처리 중(RUNNING) · 완료(DONE) · 실패(FAILED).
  실패 이유는 `processing_error`, 단계별 시간·쪽수·조각 수는 `processing_steps` 에 남고 화면에 보인다.
  문서 단계(`status`: 올림·추출·구조화·확정)와는 따로 둔다.

### 2-2. 처리 중으로 영원히 남지 않는다

- 처리 중에는 30초마다 신호를 남긴다. 신호가 10분 없으면 멈춘 작업으로 보고 다시 대기열에 넣는다.
- API 가 뜰 때는 처리 중인 것 전부를 다시 넣는다. 처리하는 프로세스가 이 API 하나뿐이라는 전제다(스케줄러와 같다).
- 같은 작업이 세 번 끊기면 실패로 남긴다. 같은 파일을 다시 올리면 다시 처리한다.

### 2-3. 겹치지 않는다

- 같은 사업에 같은 파일은 한 문서다(해시 유일). 동시에 두 번 올라와도 먼저 들어간 행을 돌려준다.
- 작업자는 `for update skip locked` 로 가져가 같은 문서를 두 번 처리하지 않는다.
- 청크는 문서마다 지우고 넣기를 한 트랜잭션에서 한다. 임베딩은 문서 행을 잠그지 않은 채 하고,
  쓰기 직전에 잠근다. 그사이 문서가 지워졌으면 아무것도 쓰지 않는다.

### 2-4. 동시 처리 수와 임베딩 묶음

- 동시에 처리하는 문서 수는 `document_workers`(기본 1)다. 임베딩이 CPU 를 다 쓴다.
- 임베딩 서버는 요청을 하나씩 처리한다. 문서 조각 32개를 한 번에 보내면 그동안 질문의 임베딩이 뒤에서
  기다려, 300KB 문서 색인 중 기존 문서 질문의 첫 답이 53초 늦었다. 뒤에서 색인할 때는 4개씩 나눠 보낸다
  (`document_embed_batch`). 같은 조건에서 9초 안쪽이 됐고 전체 처리 시간은 그대로다.

### 2-5. 같은 프로세스로 충분한가

바꾼 뒤 같은 문서들을 올리면서 0.5~3초 간격으로 다른 요청을 보냈다.

| 문서 | 접수 응답 | 처리 완료 | 헬스체크 최대 | 로그인 최대 | 목록 최대 | 질문 첫 답 최대 |
|---|---|---|---|---|---|---|
| PPTX 1.7MB | 0.02초 | 30초 | 0.02초 | 0.49초 | 0.03초 | 4.2초 |
| DOCX | 0.02초 | 38초 | 0.03초 | 0.48초 | 0.03초 | 1.4초 |
| md 300KB | 0.01초 | 202초 | 0.02초 | 0.50초 | 0.04초 | 9.2초 |

추출(PDF 2.7초)·청크 계산은 스레드에서 돌아도 요청 처리를 눈에 띄게 늦추지 않았다. 늦어진 것은 같은
임베딩 서버를 나눠 쓰는 질문뿐이고 묶음을 줄여 줄었다. 따로 작업자 프로세스를 두지 않는다. 문서가 더
커지거나 동시 업로드가 잦아지면 작업자 프로세스·임베딩 서버 분리를 다시 본다.

## 3. 하지 않은 것

- 앞단 프록시 시간 제한을 늘리지 않았다. 늘려도 그동안 API 가 멈추는 것은 같다.
- 처리 중인 작업을 사용자가 취소하는 기능은 두지 않았다. 문서를 지우면 쓰기 전에 멈춘다.

## 4. 대가

- 업로드 직후에는 본문·초안이 없다. 화면이 접수됨·처리 중을 보이고 끝날 때까지 다시 부른다.
- 시험은 요청 안에서 처리하는 모드(`document_processing=inline`)로 돈다. 뒤에서 처리하는 길은
  `tests/test_document_worker.py` 가 따로 본다.
