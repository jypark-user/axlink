# ARC-019 작업 완료 확인과 완료 확인율

| | |
|---|---|
| 상태 | **확정** |
| 일자 | 2026-10-06 |
| 결정 | 유저인사이트(주) 수행 책임자 |
| 관련 | `SWFR.PIP.006` `SWFR.PIP.009` `SWFR.WEB.004` `SWFR.WEB.005` `SWFR.WEB.006` · ARC-008 · ARC-016 |

---

## 1. 문제

WBS 실적률은 용역사가 WBS 파일에 적은 값이다. 100% 로 적으면 산출물·검토 증거 없이도 완료로 보인다.
산출물 판정은 파일·문서가 있는지 대조한 결과인데 화면은 이를 "제출"이라고 불렀다.
산출물 승인은 문서 확정과 같은 요청으로 처리돼 용역사도 승인 상태를 만들 수 있었다.

## 2. 결정

### 2-1. 지표

- 대표값은 그대로 **보고 진척률**(WBS 실적의 가중 평균, ARC-016)이다.
- 옆에 **완료 확인율**을 둔다. 현재 WBS 말단 작업 가중치 중 발주기관이 완료를 인정한 작업의 가중치 비율이다.
- 분모(말단 작업)가 없으면 **산출 불가**다. 확인이 없으면 0% 이고 "완료 확인 기록 기준"을 함께 적는다.
- 집계는 뷰 `v_wbs_completion` 하나에서 한다. 화면 API 와 시맨틱 지표 `wbs_completion_rate` 가 같은 뷰를 읽는다.

### 2-2. 완료 확인

- 확인 요청에 목적을 둔다. `GENERAL`(일반)과 `WBS_COMPLETION`(작업 완료 확인)이다. 기존 요청은 모두 일반이다.
- 작업 완료 확인 요청에는 **확인할 완료 내용**이 있어야 한다. WBS 파일에 완료 조건 열은 요구하지 않는다.
- 용역사의 조치 보고에는 **근거**가 하나 이상 있어야 한다. 종류는 산출물 문서, 저장소 파일, 커밋, 시험 결과, 시연, 회의 기록, 기타다.
- 발주기관은 "이 작업의 완료를 인정합니다"를 표시해야 확인할 수 있다. 이것이 확인 절차이고 완료 조건 자체는 아니다.
- 보고 실적이 100% 가 아니어도 확인할 수 있다. 화면이 알리고, 보고 실적은 바꾸지 않는다.
- 산출물 승인과 시험 통과는 근거로 보일 뿐 그것만으로 완료 처리하지 않는다.

### 2-3. 기록

`wbs_completion_record` 에 확인·철회를 한 줄씩 더한다. 고치거나 지우지 않는다.

확인 시점 값을 고정한다.
- 작업 식별자, 번호, 작업명·산출물 열·기간
- 가중치, WBS 계획서 버전, 보고 실적
- 확인할 완료 내용
- 근거: 파일 대조·대조 파일·저장소 기준·정식 제출·산출물 승인·산출물 버전과 용역사 근거
- 확인자·시각

근거가 나중에 바뀌어도 기록은 그대로다. 화면은 "확인 후 근거 개정됨"으로 표시하고 확인은 유지한다.
새 산출물 버전은 따로 미승인으로 보인다.

### 2-4. 작업 식별과 범위

둘을 나눈다.

| | 무엇 | 쓰임 |
|---|---|---|
| `task_key` | 작업의 정체 | 확인 기록이 어느 작업의 것인가 |
| `scope_hash` | 작업명 + 산출물 열 | 확인 뒤 작업 내용이 바뀌었는가 |

계획서를 다시 올릴 때 직전 계획과 같은 작업이라는 증거가 모두 있을 때만 `task_key` 를 잇는다.

| 경우 | 판정 | 결과 |
|---|---|---|
| 같은 번호·같은 이름·말단 유지 | CONTINUED | 확인 유지 |
| 같은 내용 재업로드 | CONTINUED | 확인 유지 |
| 가중치만 조정(형제 구성 그대로) | CONTINUED | 확인 유지, 현재 가중치로 셈. 확인 당시 가중치·버전은 기록에 |
| 작업명 변경(동명 작업 교차 포함) | RENAMED | 새 작업. 예전 확인 승계 안 함 |
| 빠졌다가 다시 들어온 번호 | REAPPEARED | 새 작업 |
| 말단이 묶음이 되거나 그 반대(분할) | LEAF_CHANGED | 새 작업 |
| 형제가 생기거나 빠지며 가중치가 바뀜(병합) | RESTRUCTURED | 새 작업 |
| 같은 작업인데 산출물 열 변경 | 범위 변경 | 재확인 필요, 분자 제외 |

새 작업이 된 번호에 예전 확인이 있으면 화면이 "재확인 필요(사유)"로 알린다.

### 2-5. 권한과 일관성

- 작업 완료 확인 요청·확인·철회는 그 사업 발주기관만 한다. 최고관리자도 하지 않는다. 일반 확인 요청은 운영 지원을 위해 최고관리자도 계속 열 수 있다.
- 요청 상태 변경과 기록 저장은 한 트랜잭션이다. 어느 쪽이 실패하면 둘 다 되돌린다.
- 중복 클릭·재시도는 막는다.
  - 상태 조건부 갱신(`REPORTED` 일 때만 확인)
  - 기록의 (요청, 종류) 유일 제약
  - 작업마다 열린 완료 확인 요청은 하나뿐(부분 유일 인덱스)
- 요청 뒤 작업 정체나 범위가 바뀌면 확인을 막는다(409). 바뀐 작업으로 다시 요청해야 한다.

### 2-6. 산출물 승인

문서 확정과 산출물 승인을 나눴다.
- 확정은 올린 문서를 산출물 한 버전으로 등록하는 일이다. 초안·제출 상태만 가능하다.
- 승인·반려는 발주기관(최고관리자 포함)이 현행 버전에 한다. 반려에는 사유가 있어야 한다.
- 승인된 버전을 같은 버전 표기로 다시 확정할 수 없다.

## 3. 하지 않은 것

- 작업별 완료 조건 열(WBS 파일)은 두지 않았다. 확인할 완료 내용은 요청마다 적는다.
- 항목 단위 격차 경고(ARC-016 4절)는 이번 범위가 아니다.
- 확인 진척을 대표값으로 쓰지 않는다. ARC-016 의 "진척률은 WBS 실적으로만 낸다"는 그대로다.
