## 1. 문제

10-06 미리보기에서 "예상 일정대비 진척률 어때?" 에 질문과 무관한 참고 현황 그림 네 장이 나왔다.
조사해 보니 원인이 여럿이었다.

- 일정 질문("계획보다 늦고 있어?", "일정대로 가고 있어?")을 현황(OVERVIEW)으로 보냈다. 프롬프트에 일정 질문 예시가 없었다.
- 계획 대비 비교가 지표 하나(편차)뿐이라 기준일·계획값·보고값·산식이 한 번에 나오지 않았다.
- 문서 근거가 막히면 ARC-017 대로 고정 참고 현황을 붙였다. 문서 없음·값 없음·지원 안 함·해석 불명확·조회 오류가 같은 문구로 뭉쳤다.
- 집계 지표에 값이 없으면 문서 경로로 내려 보냈다. DB 에 답이 있는데 문서 검색 실패로 막혔다.
- `schedule_variance_pct` 는 채우는 경로가 없는 `progress_record` 를 읽어 늘 비어 있었다. 대시보드 추천 구성 두 곳과 저장된 위젯이 이 키를 쓴다.
- 제출률(파일 관측)과 완료 확인율(발주기관 인정)을 모델이 가르지 못했다.

## 2. 결정

### 2-1. 일정 질문 묶음 (`app/rag/intents.py`)

라우팅에 `INTENT` 를 둔다. 값은 진척 카드와 같은 `dashboard.compute` 와 일별 스냅샷에서 온다.

| 묶음 | 답 | 값이 없을 때 |
|---|---|---|
| `PLAN_VS_ACTUAL` 계획 대비 | 같은 사업·같은 기준일의 계획(추정)·보고·차이(%p)·늦은 작업 수. 표 아래에 계획선 산식 | WBS 가 없으면 마지막 스냅샷의 보고값이나 대표 진척률을 날짜·기준과 함께 내고 "계획과 비교하지 못했다" 고 덧붙인다(부분 답). 그것도 없으면 무엇이 있어야 답할 수 있는지 말한다 |
| `BEHIND_TASKS` 늦은 작업 | 계획선보다 실적이 뒤진 말단 작업. 진척 카드와 같은 기준(1%p 여유), 차이가 큰 순 | WBS 가 없으면 그렇다고 말한다 |
| `PROGRESS_CHANGE` 기간 변화 | 최근 스냅샷과 지난주(7일 전)·지난달(같은 날) 스냅샷. 그날이 없으면 가장 가까운 앞 날짜를 쓰고 밝힌다 | 앞 스냅샷이 없으면 비교할 수 없다고 한다 |
| `DELAY_CAUSE` 지연 사유 | 늦은 작업 + 문서 검색 | 문서가 막히면 늦은 작업까지만 답하고 사유는 근거가 없다고 서버가 덧붙인다 |

계획 진척률은 실제 계획값이 아니라 WBS 기간을 날짜로 안분한 추정이다. 답과 표에 "추정" 을 적는다.
진척률은 %, 두 진척률의 차이는 %p 로 쓴다. 수치는 이 줄에서만 나오고 수치 검문(ARC-017)을 그대로 거친다.

### 2-2. 답의 종류

모델을 부르지 않고 서버 문안으로 끝나는 경우를 갈라 `done.finishReason` 과 메시지에 남긴다.

| 종류 | 뜻 |
|---|---|
| `STOP` | 답했다 |
| `PARTIAL` | 일부만 답했다. 못 한 부분은 서버 문안이 말한다 |
| `NUMBER_GUARD` | 근거 없는 수치 문장을 숨겼다 |
| `CLARIFY` | 두 뜻으로 읽혀 선택지를 냈다 |
| `NO_DOCUMENTS` | 범위에 문서·이슈가 아직 없다 |
| `NO_RELEVANT_DOCUMENTS` | 문서는 있으나 맞는 내용이 없다 |
| `NO_DATA` | 지표·현황 값이 아직 없다. 무엇이 생기면 답할 수 있는지 말한다 |
| `UNSUPPORTED` | 맞는 조회 항목이 없다 |
| `QUERY_ERROR` | 조회가 깨졌다. 값이 없다는 뜻이 아니라고 말한다 |
| `OFF_TOPIC` | 사업과 무관하다 |

ARC-017 의 고정 참고 현황은 걷는다. 전체 현황은 사용자가 물을 때(OVERVIEW)만 낸다.
값이 없는 집계는 문서 경로로 돌리지 않는다. 조회는 세이브포인트 안에서 돌려 오류를 값 없음과 가른다.

### 2-3. 권장 질문 (`app/rag/suggest.py`)

- 라우팅 모델이 `related`(되묻기는 `options`)에 키를 0~3개 고른다. 키는 `intent:<묶음>`, `measure:<지표>`, `overview`, `list:<종류>:<상태>` 다.
- 서버가 카탈로그로 검증하고, 지금 범위에서 값이 나오는 것만 남긴다. 문장은 서버 틀이다. 셋을 채우려고 관계없는 것을 넣지 않는다.
- 이번에 답한 것과 막힌 것은 다시 내지 않는다. 무관 질문에는 내지 않는다.
- 누르면 질문 문장과 키(`hint`)가 같이 간다. 서버는 키를 다시 검증하고(틀리면 400) 범위 권한을 보며(밖이면 403), 재분류하지 않는다. 재분류가 빗나가 같은 안내가 반복되지 않게 하려는 것이다.
- 화면은 답이 끝나면 메시지를 다시 읽으므로 권장 질문과 답의 종류를 메시지에 저장한다(V48).

### 2-4. 지표

- `schedule_variance_pct` 는 끄지 않고 일별 스냅샷으로 옮긴다. 값은 계획 대비 편차와 같은 식이다(V48).
- 지연 작업 수·계획 진척률·편차·제출률·완료 확인율의 설명을 고쳐 모델이 가를 수 있게 한다. 지연 작업 수의 설명은 실제 기준(계획선)과 달랐다.

### 2-5. 모델 표시

질의 화면에 지금 답변 모델을 보인다(`GET /api/ai/runtime`). 고정 응답(시험용)이면 실제 모델 답이 아니라고 알린다.
실모델이 실패하면 오류로 보이고 고정 응답으로 바꾸지 않는다.

### 2-6. 분류 안내 보강 (10-07)

같은 질문 48개를 바꾸기 전 코드와 견줘 보니, 일정 절이 들어간 뒤 실제 모델이 전체 상태를 묻는 질문에
되묻고, "요구사항이 몇 개야?" 에 이슈 건수 지표를 골랐다. 작은 모델은 "이슈가 몇 건이야?" 를 문서
질문으로 보냈다. 라우팅 안내에 세 가지를 더했다.

- 건수를 묻는 질문은 집계다. 지표는 질문 대상과 같은 대상의 것만 쓰고, 없으면 그 종류의 목록으로 낸다.
- 사업 전체가 괜찮은지·무엇을 볼지 묻는 질문은 되묻지 않고 현황이다. 분야를 말했으면 그 분야 지표나 현황이다.
- "심각한 이슈 있어?", "리스크 있어?" 처럼 있는지 묻는 것은 목록이다. "지연된 작업 있어?" 는 늦은 작업이다.

### 2-7. 건수가 비었을 때: 0건과 셀 자료 없음 가르기 (10-08, GH-127)

건수 지표(`value_type = COUNT`)가 도구 수집 표(이슈·리스크·커밋·요구사항)에서 비면 바로 `NO_DATA` 로
끝내지 않는다. 판정이 차원(예: 심각도별)으로 묶이면 이슈가 없을 때 행이 하나도 안 나와 "값 없음" 이
됐다(10-07 5174). 사업마다 연결과 가장 최근 수집 작업 결과를 보고 가른다(`app/rag/collection.py`).

| 상태 | 답 |
|---|---|
| 모든 사업이 수집 성공 | 차원 없이 다시 센 전체 값. 0 이면 0건 |
| 연동한 도구가 없는 사업이 있다 | `NO_DATA`, 연동 안 됨. 0건이라는 뜻이 아니라고 적는다 |
| 연결은 있는데 끝난 수집이 없다 | `NO_DATA`, 아직 수집 전 |
| 가장 최근 수집이 실패했다 | `NO_DATA`, 수집 실패. 앞선 수집 자료가 있어도 0건이라고 하지 않는다 |
| 조회 자체가 깨졌다 | `QUERY_ERROR` (지금과 같다) |

여러 사업을 같이 물으면 가장 나쁜 상태를 따른다. 문서 검색이 멈춰도(ARC-022) 이 경로는 DB 집계라
그대로 답한다.

## 3. 하지 않은 것

- 사업이 여럿인 범위에서 일정 질문을 되묻지 않는다. 사업마다 한 줄씩(다섯까지) 같은 기준으로 낸다.
- 일정 예측("마감까지 끝낼 수 있을까?")은 하지 않는다. 계산할 근거가 없다.

## 4. 대가

- 라우팅 프롬프트가 길어졌다. 프롬프트가 바뀌면 라우팅 캐시가 자연히 다시 찬다(ARC-014).
- 권장 질문을 확인하느라 질문마다 조회가 최대 몇 번 더 돈다.
- V48 은 심각도 수정(V47) 뒤에 병합해야 한다.
