# AX Link 배포·운영 절차

운영 서버에 AX Link 를 도커 스택으로 올리고 유지하는 절차다. 개발 PC 실행은
[로컬-실행](../00-management/로컬-실행.md)을 본다.

## 1. 구성

| 서비스 | 이미지 | 하는 일 |
|---|---|---|
| `postgres` | `pgvector/pgvector:pg16` | 표준 데이터 모델·임베딩·설정 |
| `migrate` | `axlink-migrate:<버전>` | 스키마 마이그레이션. `db/migration` 이 이미지에 들어 있다. 적용 전에 validate 를 먼저 하고, 끝나면 멈춘다 |
| `api` | `axlink-api:<버전>` | 화면 API·수집·일별 스냅샷 스케줄러. 컨테이너 하나, worker 하나 |
| `web` | `axlink-web:<버전>` | 화면(정적 파일)을 Nginx 로 내고 `/api` 만 api 로 넘긴다 |
| `ollama` | `ollama/ollama:0.33.1` | 생성 모델(클라우드 모델 중계)과 임베딩(bge-m3). 다른 서버의 Ollama 를 쓰면 끈다 |

- **기동 순서:** postgres 준비 → migrate 성공 → api 준비(`/api/health`) → web.
- **영속 볼륨:** `pgdata`(DB), `documents`(업로드 원본), `ollama`(모델·로그인 상태).
- **공통 설정:** 모든 서비스가 `restart: unless-stopped`, 로그 크기 제한(10MB × 5개)을 쓴다.

정의 파일은 `infra/docker-compose.prod.yml`, 변수 예제는 `infra/prod.env.example` 이다.
운영 스택은 소스를 마운트하지 않고 개발 PC 경로도 쓰지 않는다.

## 2. 이미지 만들기와 버전 확인

이미지는 검증된 빌드 장비나 CI 에서 만든다. 세 이미지에 같은 버전과 커밋을 넣는다.

```bash
VER=0.1.0
REV=$(git rev-parse --short HEAD)
docker build -f docker/api.Dockerfile --target prod --build-arg AXLINK_VERSION=$VER --build-arg AXLINK_REVISION=$REV -t <레지스트리>/axlink-api:$VER .
docker build -f docker/web.Dockerfile --target prod --build-arg AXLINK_VERSION=$VER --build-arg AXLINK_REVISION=$REV -t <레지스트리>/axlink-web:$VER .
docker build -f docker/migrate.Dockerfile --build-arg AXLINK_VERSION=$VER --build-arg AXLINK_REVISION=$REV -t <레지스트리>/axlink-migrate:$VER .
```

배포된 버전은 세 곳에서 확인한다.

- 웹: `http://<주소>/version.json` → `{"name":"axlink-web","version":"0.1.0","revision":"<커밋>"}`
- API: `http://<주소>/api/health` → `{"status":"UP","version":"0.1.0+<커밋>"}`
- 마이그레이션: 이미지 라벨 `org.opencontainers.image.version`·`revision`, 그리고 DB 의 `flyway_schema_history`

문서 처리 작업자는 API 와 따로 본다. `/api/health` 가 UP 이어도 작업자가 멈춰 있을 수 있다.

- `http://<주소>/api/health/documents` → `{"state":"running", ...}`. 작업자가 계속 실패하거나(`failing`) 멈췄으면(`dead`) 503 이다.
- `failing` 은 DB 에 닿지 못해 기동 정리를 되풀이하는 상태다. 60초마다 다시 시도한다. DB 가 돌아오면 저절로 `running` 이 된다.
- `dead` 는 작업자가 예상 밖 오류로 끝난 상태다. API 를 다시 띄우기 전까지 문서가 처리되지 않는다. 로그의 "문서 처리 작업자가 멈췄다" 를 본다.

서버 CPU 구조가 개발 장비와 다르면(예: arm64) `docker buildx build --platform` 으로 맞춰 만든다.

## 3. Portainer 로 배포하기

1. 레지스트리에 세 이미지를 올린다. 서버가 레지스트리에 로그인할 수 있게 Portainer 레지스트리 설정을 넣는다.
2. 스택을 새로 만들고, 내용에 `infra/docker-compose.prod.yml` 을 넣는다. 저장소 연결로 가져와도 된다.
3. Environment variables 에 `infra/prod.env.example` 의 이름으로 값을 넣는다. 필수 값이 비면 배포가 시작되지 않는다.
4. 배포한 뒤 다음을 확인한다.
   - `migrate` 가 종료 코드 0 으로 끝났다.
   - `api`·`web` 이 healthy 다.
   - `/version.json`·`/api/health` 의 버전이 맞다.
   - `/api/health/documents` 가 200 이고 `state` 가 `running` 이다.

### 필수 비밀값

| 변수 | 내용 | 만드는 법 |
|---|---|---|
| `AXLINK_DB_PASSWORD` | DB 비밀번호. 접속 URL 에 그대로 들어가므로 영문·숫자만 | 무작위 32자 |
| `AXLINK_JWT_SECRET` | 로그인 토큰 서명 키. 32자 이상 | `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `AXLINK_SECRET_KEY` | 도구 인증정보 암호화 키(base64 32바이트) | `python -c "import os,base64; print(base64.b64encode(os.urandom(32)).decode())"` |

- API 는 `AXLINK_ENV=production` 으로 뜬다. 이때 JWT 비밀값이 개발 기본값이거나 32자보다 짧으면, 또는 암호화 키가 없으면 기동하지 않는다.
- **암호화 키는 처음 정한 값을 계속 쓴다.** 키를 바꾸거나 잃으면 저장된 GitHub·Redmine 토큰을 풀 수 없다. 이 경우 도구 연결을 모두 다시 등록해야 한다.
- 키는 DB 백업과 다른 곳에 따로 보관한다.
- 비밀값은 스택 변수로만 넣는다. 이미지·저장소·로그에 넣지 않는다.

## 4. 처음 띄운 뒤 할 일

### 개발 계정 처리

마이그레이션이 개발용 계정 7개를 넣는다: `r1`(최고관리자), `r2`(발주기관), `r3`(용역사), `admin@axlink.co.kr`, `client@axlink.co.kr`, `contractor@axlink.co.kr`, `test`. 모두 같은 개발 비밀번호다. 운영 DB 에서는 그대로 두지 않는다.

지금은 비밀번호를 바꾸는 화면이나 API 가 없으므로 아래처럼 처리한다. 개발 PC 의 개발 DB 에는 하지 않는다.

```bash
# 1) 운영 관리자 비밀번호의 해시를 만든다(입력은 화면에 남지 않는다)
docker compose exec api python -c "import bcrypt,getpass; print(bcrypt.hashpw(getpass.getpass('새 비밀번호: ').encode(), bcrypt.gensalt()).decode())"

# 2) 최고관리자 하나만 새 비밀번호로 남기고 나머지 개발 계정은 막는다
docker compose exec postgres psql -U axlink -d axlink -c "begin;
  update app_user set password_hash = '<1에서 나온 해시>', updated_at = now() where username = 'r1';
  update app_user set status = 'DISABLED', updated_at = now()
   where username in ('r2','r3','test','admin@axlink.co.kr','client@axlink.co.kr','contractor@axlink.co.kr');
  commit;"
```

발주기관·용역사 사용자는 그 뒤 화면의 초대 기능으로 만든다.

### 모델 준비

같은 스택의 Ollama 를 쓰면 이렇게 한다.

```bash
docker compose exec ollama ollama pull bge-m3            # 임베딩(로컬)
docker compose exec ollama ollama signin                 # 클라우드 생성 모델을 쓸 때. 계정 연결 화면 주소가 나온다
docker compose exec ollama ollama pull gemma4:31b-cloud  # 목록에 보이게 등록
```

- 관리 화면의 AI 모델 설정에서 서버 주소를 `http://ollama:11434` 로 두고 모델을 고른다. 이 주소는 DB 에 저장된다.
- 다른 서버의 Ollama 를 쓰면 다음처럼 바꾼다.
  - `AXLINK_BUNDLED_OLLAMA=0` 으로 스택의 Ollama 를 끈다.
  - `AXLINK_OLLAMA_BASE_URL`·`AXLINK_EMBEDDING_BASE_URL` 을 그 서버 주소로 준다.
  - 관리 화면의 서버 주소도 같은 값으로 바꾼다.
- 클라우드 생성 모델은 인터넷이 필요하다. 폐쇄망 납품 구성에서는 같은 자리에 온프레미스 모델을 둔다.
  무엇을 들고 들어가야 하는지는 [폐쇄망 반입 목록](폐쇄망-반입-목록.md)에 있다.

## 5. 백업과 복구

백업 대상은 셋이다. 셋이 다 있어야 온전히 되살아난다.

| 대상 | 백업 | 없으면 |
|---|---|---|
| DB | `pg_dump -Fc` | 전부 잃는다 |
| 업로드 원본 | `documents` 볼륨을 tar 로 묶음 | 문서 목록은 있는데 내려받기·재색인이 안 된다 |
| 암호화 키 | 스택 변수 값을 따로 보관 | 저장된 도구 토큰을 풀 수 없다 |

```bash
# 백업
docker compose exec -T postgres pg_dump -U axlink -d axlink -Fc > axlink-$(date +%F).pgdump
docker run --rm -v <스택>_documents:/d:ro -v "$PWD":/out alpine tar -cf /out/documents-$(date +%F).tar -C /d .

# 복구(빈 스택에). api 를 띄우기 전에 넣는다
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U axlink -d axlink --no-owner < axlink-YYYY-MM-DD.pgdump
docker run --rm -v <스택>_documents:/d -v "$PWD":/in alpine sh -c "tar -xf /in/documents-YYYY-MM-DD.tar -C /d && chown -R 10001:10001 /d"
docker compose up -d
```

- 복구한 뒤에는 원래 `AXLINK_SECRET_KEY` 를 같은 값으로 준다.
- 관리 화면의 AI 서버 주소가 새 환경과 맞는지 본다.
- 백업 파일과 키의 외부 보관 위치는 아직 정하지 않았다(7절).

## 6. 버전 올리기와 되돌리기

**올리기.** 백업을 먼저 받는다. 그다음 `AXLINK_VERSION` 을 새 태그로 바꿔 스택을 다시 배포한다. migrate 가 새 마이그레이션을 적용한 뒤 api 가 뜬다.

**되돌리기.**
- 새 버전에 마이그레이션이 없었다면, `AXLINK_VERSION` 을 이전 태그로 바꿔 다시 배포하면 된다.
- 새 마이그레이션이 적용됐다면, 스키마는 되돌리지 않는다(Flyway 는 앞으로만 간다). 올리기 직전 백업으로 DB 를 복구한 뒤 이전 태그로 배포한다. 그 사이 쌓인 데이터는 잃는다.
- 그래서 올리기 전 백업을 빼먹지 않는다.

## 7. 정하지 않은 것

| 항목 | 영향 |
|---|---|
| Portainer 환경 유형(standalone·swarm·agent) | swarm 이면 `depends_on` 조건이 무시된다. 지금 정의는 standalone 기준이다 |
| 배포 서버 CPU 구조 | amd64 가 아니면 이미지를 그 구조로 다시 만든다 |
| 도메인·HTTPS 프록시 | 지금은 `web` 이 HTTP 8088 을 연다. 프록시 뒤에 두면 `AXLINK_PUBLIC_ORIGIN` 을 그 주소로 준다 |
| 이미지 레지스트리 | `AXLINK_IMAGE_PREFIX` 값 |
| 백업·암호화 키 외부 보관 위치 | 5절 |
| 폐쇄망 반입 | 이미지는 `docker save`/`load` 로 옮긴다. Ollama 모델은 볼륨째 옮긴다. 목록과 절차는 [폐쇄망 반입 목록](폐쇄망-반입-목록.md). 오프라인 설치 리허설은 아직 안 했다 |
