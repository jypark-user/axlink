**2026년 AX 프로젝트 관리 운영 프레임워크 개발 용역**
v0.2 · 2026-08-27

## 0. 전제

### 0.1 등장 인물

| 역할 | 인물 | 소속 | 관심사 |
|---|---|---|---|
| **발주기관 관리자** | 김주무관 | 진흥원 | 담당 프로젝트 **여러 건**의 진행 상황을 한눈에 파악하고, 지연·미제출을 조기에 발견 |
| **용역업체 관리자** | 박PM | B사업 수행사 | 기존 도구로 일하되, 발주기관 요청을 받고 조치 결과를 전달 |

### 0.2 진척 판단의 기준 (가장 중요한 원칙)

> **진척률의 기준은 WBS이고, 각 단계의 산출물이 그 진척을 뒷받침하는 근거다.**

커밋 수나 이슈 수는 진척률이 **아니다.** 발주기관은 WBS 항목과 산출물로 사업을 관리한다.

```
진척률 = Σ (WBS 항목 가중치 × 실적률)          ← 용역업체가 신고한 값
          └ 각 항목의 「산출물」이 실제로 제출되었는지로 근거 확인
```

**핵심은 대조다.** WBS 실적은 용역업체의 자기 신고이고, 산출물 제출 여부는 시스템이 관측한
사실이다. 둘이 어긋나면 그 지점이 곧 발주기관이 확인해야 할 곳이다.

```
WBS 항목            가중치  실적(신고)  연결 산출물     관측 결과      판정
3.1 요구사항 정의     0.15     100%     요구사항정의서   제출 · 승인    ✓
3.2 설계             0.20      40%     SW설계서        미제출         ⚠ 지연
3.3 구현             0.35      20%     소스코드        커밋 47건      ✓
3.4 시험             0.20       0%     시험결과서      미제출         −
3.5 인도             0.10       0%     매뉴얼          미제출         −
─────────────────────────────────────────────────────────────
진척률 = 0.15×1.0 + 0.20×0.4 + 0.35×0.2 + 0 + 0 = 30%
```

발주기관 화면에는 **30%** 와 함께 **"⚠ 실적 신고 대비 산출물 미제출 1건"** 이 함께 뜬다.
이것이 착수보고서가 말한 *"보고 시점·감리 시점에 의존하는 사후적 방식"* 을 벗어나는 지점이다.

### 0.3 시나리오 개요: 큰 그림

세부 장면에 들어가기 전에, 두 사람이 각각 무엇을 하는지 한 문단으로 잡아둔다.

#### S1 · 김주무관 (발주기관): **"묻지 않고 안다"**

> 여러 사업을 동시에 담당하는 사람이, 수행사에 요청하지 않고도
> **지금 무엇이 어긋나 있는지**를 스스로 찾아내고, 찾아낸 지점에만 확인을 요청한다.

| 흐름 | 하는 일 | 얻는 것 |
|---|---|---|
| **① 훑는다** | 담당 사업 목록을 본다 | 어느 사업이 문제인지 (S1-1) |
| **② 파고든다** | 그 사업의 통합 현황 → WBS 드릴다운 | 어느 **항목**이 문제인지 (S1-2·S1-3) |
| **③ 확인한다** | 근거가 되는 문서를 자연어로 묻는다 | 왜 그런지 (S1-4) |
| **④ 요청한다** | 그 항목에 확인 요청을 건다 | 수행사에 전달 (S1-5) |
| **⑤ 재확인한다** | 조치 보고 + 시스템 관측을 나란히 본다 | 실제로 바뀌었는지 (S1-6) |

**김주무관은 AX Link에 아무것도 입력하지 않는다.** 읽고, 묻고, 요청할 뿐이다.
①→⑤가 한 바퀴 돌면 다음 주에 다시 ①로 돌아온다. 이 순환이 이 제품의 전부다.

#### S2 · 박PM (용역업체): **"평소대로 일한다"**

> 자기 도구를 그대로 쓰면서, AX Link에는 **처음 한 번 연결만** 해두고
> 이후에는 발주기관 요청이 올 때만 들어온다.

| 흐름 | 하는 일 | 빈도 |
|---|---|---|
| **① 연결한다** | 형상관리·프로젝트관리 도구를 등록한다 | **1회** (S2-2·S2-3) |
| **② 기준선을 올린다** | WBS를 등록한다 (진척 판단의 기준) | 1회 + 변경 시 (S2-4) |
| **③ 평소대로 일한다** | GitHub에 push, Redmine에 이슈 처리 | 상시 · **AX Link 입력 없음** (S2-5) |
| **④ 응답한다** | 발주기관 확인 요청에 조치 결과를 보고한다 | 요청 시 (S2-6) |
| **⑤ 확인한다** | 자기 작업이 발주기관 화면에 어떻게 보이는지 본다 | 수시 (S2-7) |

**박PM에게 AX Link는 새로운 업무가 아니다.** ③이 전체의 99%이고 여기서 그는 AX Link를 열지 않는다.
이 전제가 깨지면, 즉 이중 입력이 생기면 프레임워크는 현장에서 쓰이지 않는다.

#### 두 관점이 만나는 지점

```
박PM ③ 평소 작업  ──push/이슈──▶  원천 도구
                                     │ (커넥터 · 읽기 전용 · 증분)
                                     ▼
                                  AX Link  ──▶ 김주무관 ①②③ 파악
                                     ▲                    │
                                     │                    ▼
박PM ④ 조치 보고  ◀────────────  김주무관 ④ 확인 요청
```

**단방향이 두 개**다. 데이터는 도구 → AX Link로만 흐르고(쓰기 없음),
요청은 AX Link 안에서만 오간다(원천 도구에 기록하지 않음).
이 두 경계가 `QUR.CON.001`과 `QUR.WEB.003`이다.

## 1. 시나리오 S1 · 발주기관 관리자 (김주무관)

**상황** 김주무관은 용역 3건을 담당한다. 각각 다른 수행사이고 도구도 제각각이다.
매주 월요일 아침, 지난주 상황을 확인해야 한다. 종전에는 3개 회사에 각각 메일로
주간보고를 요청하고, 받은 xlsx를 열어 비교했다.

### S1-1. 담당 프로젝트 한눈에 보기

김주무관이 AX Link에 접속하면 **본인이 담당하는 프로젝트 목록**이 먼저 나온다.

```
A 사업   진척 72%  (계획 76%, -4%p)   마일스톤 11/12   미확인 0건
B 사업   진척 30%  (계획 55%, -25%p)  마일스톤 2/5  ⚠  미확인 3건
C 사업   진척 91%  (계획 90%, +1%p)   마일스톤 8/8     미확인 0건
```

B 사업의 편차가 크다. 클릭한다.

> `SWFR.WEB.003` 프로젝트 목록 · `SWFR.WEB.006` 미처리 요청 건수 표시

### S1-2. 통합 현황 확인

B 사업의 진척·일정·품질·리스크·산출물이 한 화면에 나온다.

```
진척률 30%      일정 준수 40%      미해결 결함 7건     미해결 리스크 3건
(계획 -25%p)    (마일스톤 2/5)     (High 2)           (High 1)

진척 추이 ────  계획선과 실적선의 간격이 6월 이후 벌어짐
산출물 현황 ──  승인 4 · 검토중 1 · 미제출 5 · 합계 10
```

> `SWFR.WEB.001`, `SWFR.PIP.005~009`

### S1-3. WBS 드릴다운, 어디서 벌어졌는가

진척률을 클릭하면 WBS 항목별로 펼쳐진다. 위 0.2절의 표가 그대로 나온다.

`3.2 설계`가 실적 40%인데 **산출물(SW설계서)이 미제출**이다. 계획상으로는 지난달 종료였어야 한다.

```
3.2 설계   실적 40%  계획 100%   산출물: SW설계서 미제출
           ⚠ 실적이 신고되었으나 산출물이 확인되지 않습니다
           최근 활동: Redmine 이슈 #204 상태 「진행중」 (12일 전 갱신)
```

**진척률 숫자 하나에서 "어느 작업이, 왜, 무엇이 없어서" 까지 세 번의 클릭으로 도달한다.**

> `SWFR.PIP.003` `004` `006` `010` · `QUR.PIP.001` · `SWFR.WEB.002` · `QUR.WEB.002`

### S1-4. 자연어로 확인

*"B사업에서 이번 달 지연된 작업과 사유를 알려줘"*

```
지연 작업 2건입니다.

· 3.2 설계 (계획 07-31 종료 / 실적 40%)
  Redmine 이슈 #204 「외부 연계 규격 협의 지연」, 12일간 상태 변화 없음
  산출물 SW설계서 미제출

· 3.3 구현 중 「인증 모듈」 (계획 08-15 종료 / 실적 20%)
  3.2 설계 완료를 선행 조건으로 하는 작업입니다

근거 · WBS_B사업_v1.3.xlsx (WBS 시트 12행, 18행)
      · Redmine 이슈 #204  · Redmine 이슈 #211
```

수치는 집계 결과에서 오고, 문장만 생성된다. 근거를 클릭하면 원문 위치로 이동한다.

> `SWFR.RAG.001`, `SWFR.RAG.005~007`, `QUR.RAG.002`

### S1-5. 확인 요청 등록

김주무관이 `3.2 설계` 항목에 확인 요청을 남긴다.

```
[확인 요청]  대상: WBS 3.2 설계 / 산출물: SW설계서
내용: 설계서 제출 일정과 외부 연계 규격 협의 현황을 회신 바랍니다.
```

**AX Link는 용역업체의 도구에 아무것도 쓰지 않는다.** 요청은 AX Link 안에 기록되고,
용역업체 관리자가 자기 화면에서 확인한다.

> `SWFR.WEB.004` 확인 요청 등록 및 등록 시점 상태 저장 (착수보고 관리순환 ⑧)

### S1-6. 조치 결과 재확인

며칠 뒤 다시 접속하면 요청 상태가 바뀌어 있다.

```
✓ 조치 완료 (박PM, 08-26)
  "설계서 초안 제출하였습니다. 외부 연계 규격은 8/25 협의 완료."

  시스템 관측:
   · 산출물 SW설계서 제출 확인 (docs/20-design/, 08-26 수집)
   · WBS 3.2 실적 40% → 85% 갱신
   · Redmine 이슈 #204 상태 「진행중」 → 「해결」
   · 진척률 30% → 39%
```

**말과 데이터가 함께 온다.** 조치했다는 주장 옆에 시스템이 관측한 사실이 붙는다.
김주무관은 확인 완료로 닫는다.

> `SWFR.WEB.005` `006` · `SWFR.CON.005` · `SWFR.PIP.005`

## 2. 시나리오 S2 · 용역업체 관리자 (박PM)

**상황** 박PM은 B사업 PM이다. 팀은 GitHub과 Redmine으로 일한다.
발주기관이 AX Link 연결을 요청했다. 박PM의 우려는 두 가지다.
**"우리 저장소를 열어줘야 하나"** 와 **"관리 도구가 하나 더 늘어나는 건가"**.

### S2-1. 초대와 접속

발주기관이 보낸 초대로 접속하면 **B사업 하나만** 보인다. 다른 사업은 존재조차 보이지 않는다.

> `SER.SEC.003` 역할 구분 및 프로젝트 단위 접근 제한

### S2-2. 형상관리 연결

```
① 도구 선택      GitHub
② 인증정보 등록   토큰 입력

   이 연결에 필요한 권한
     · Contents  읽기          저장소 파일 · 커밋 조회
     · Issues    읽기          이슈 · 라벨 조회
     · Pull requests 읽기      PR 조회
   쓰기 권한은 요구하지 않습니다. AX Link는 저장소에 아무것도 쓰지 않습니다.

③ 대상 저장소     b-project/backend  선택
④ 연결 테스트     ✓ 연결 성공. 저장소 1개, 최근 커밋 08-19 확인
```

**필요 권한과 읽지 않는 것을 먼저 보여준다.** 이 화면이 박PM의 첫 번째 우려에 대한 답이다.

> `SWFR.CON.003`, `SWFR.CON.006`, `QUR.CON.001`, `SER.SEC.001`

### S2-3. 프로젝트관리 도구 연결

Redmine URL과 API Key를 등록한다. REST API가 꺼져 있으면 이렇게 나온다.

```
✗ 연결 실패
  Redmine의 REST 웹 서비스가 비활성 상태입니다.
  관리 → 설정 → API → 「REST 웹 서비스 사용」을 체크한 뒤 다시 시도해 주세요.
```

> `SWFR.CON.004`, `SWFR.CON.006`

### S2-4. WBS 등록 (진척의 기준선)

박PM이 WBS 파일을 지정한다. 저장소의 `docs/00-management/WBS_B사업_v1.3.xlsx` 이다.

AX Link가 파싱한 결과를 보여주고 확인을 받는다.

```
WBS 항목 24건을 인식했습니다.

  WBS ID  업무분류        산출물          가중치   계획기간
  3.1     요구사항 정의    요구사항정의서   0.15    03-01 ~ 04-15
  3.2     설계            SW설계서        0.20    04-16 ~ 07-31
  ...

  산출물이 지정되지 않은 항목 3건. 진척 근거 확인이 제한됩니다
                                                    [확인]  [다시 지정]
```

**이 순간이 시나리오 전체의 기준점이다.** 여기서 정해진 가중치와 산출물 지정이
이후 모든 진척률 계산의 근거가 된다.

> `SWFR.PIP.010` WBS 파싱·항목–산출물 연결 · `SWFR.CON.007` 문서 추출

### S2-5. 평소 업무에서는 AX Link를 열지 않는다

연결 이후 박PM의 팀은 **평소 하던 대로만** 한다.

```
개발자   코드 작성 → 커밋 → PR 생성 → 리뷰 → 머지
박PM     Redmine 이슈 상태 갱신 · 산출물 문서를 저장소 docs/ 에 push
         WBS 실적 컬럼 갱신 후 push
```

AX Link에 별도로 입력하는 것은 **없다.** 이것이 박PM의 두 번째 우려에 대한 답이고,
착수보고서의 *"용역업체는 AX Link 별도 입력 없이 원천 데이터 최신화"* 가 뜻하는 바다.

AX Link는 증분 수집으로 변경분만 가져와 지표를 다시 계산한다.

> `SWFR.CON.005`, `SWFR.PIP.005`

### S2-6. 발주기관 요청 수신

박PM 화면에 요청이 도착한다.

```
[확인 요청]  발주기관 · 08-22
  대상: WBS 3.2 설계 / 산출물: SW설계서
  설계서 제출 일정과 외부 연계 규격 협의 현황을 회신 바랍니다.
                                                  [조치 완료 보고]
```

박PM은 **자기 도구에서** 조치한다.

```
1. SW설계서 작성 → 저장소 docs/20-design/SW설계서_v0.9.xlsx push
2. Redmine 이슈 #204 상태 「진행중」 → 「해결」
3. WBS 실적 3.2 → 85% 갱신 후 push
4. AX Link에서 [조치 완료 보고]: "설계서 초안 제출. 규격 협의 8/25 완료."
```

> `SWFR.WEB.005` 조치 보고 · `SWFR.WEB.006` 상태 관리 · `QUR.WEB.003` 원천 도구 무기록 · `SER.SEC.003`

### S2-7. 반영 확인

## 3. 두 시나리오가 만나는 지점 · 관리순환

```
   발주기관                    AX Link                     용역업체
   ────────                   ────────                    ────────
   ① 현황 확인       ←   진척·산출물·리스크 집계   ←   ⑤ 원천 데이터 갱신
        ↓                                                     ↑
   ② 편차 발견                                            ④ 자기 도구에서 조치
        ↓                                                     ↑
   ③ 확인 요청       →      요청 전달 · 기록       →   요청 수신
        ↓                                                     
   ⑥ 조치 결과 확인   ←   증분 수집 · 지표 재산정   ←   ⑥ 조치 완료 보고
        ↓
   ↺ 반복
```

**AX Link가 원천 도구에 쓰지 않으면서도 순환이 성립한다.**
요청과 응답은 AX Link 안에 있고, 실제 작업은 각자의 도구에서 일어나며,
그 결과는 수집을 통해 다시 들어온다.

## 4. 시나리오에서 드러난 요구사항 보완

두 시나리오를 쓰면서 당시 요구사항 34건에 없던 항목 4건이 확인되었다.
모두 시나리오 성립에 필수적이므로 **요구사항정의서 v0.3에 반영 완료**했다 (현재 41건).

| 요구사항 | 내용 | 근거 | 규모 |
|---|---|---|---|
| `SWFR.WEB.003` | 담당자별 프로젝트 목록과 프로젝트별 요약 지표를 제공해야 한다 | 발주기관은 복수 프로젝트를 담당 (Ⅱ.3 발주기관 관점) | 소 |
| `SWFR.PIP.010` | WBS 문서를 파싱하여 항목·가중치·계획기간·**연결 산출물**을 인식하고, 항목별 산출물 제출 여부로 진척 근거를 확인해야 한다 | Ⅱ.2 진척 지표의 기준 · Ⅱ.1 비정형 문서 | **대** |
| `SWFR.WEB.004` | 발주기관이 특정 항목에 확인 요청을 등록하고, 용역업체가 조치 결과를 보고할 수 있어야 한다 | 착수보고서 관리순환 ⑧⑪ | 중 |
| `SER.SEC.003` | 발주기관·용역업체 역할을 구분하고 프로젝트 단위로 접근을 제한해야 한다 | 용역업체가 타 사업을 볼 수 없어야 함 | 소 |

> `SWFR.PIP.010`이 가장 무겁고 가장 중요하다. **WBS가 진척의 기준**이라는 원칙이
> 이 요구사항 하나에 걸려 있다. 발주기관 참고자료 PM-002의 컬럼 구조
> (`WBS ID · 업무분류 · 산출물 · 시작일 · 종료일 · 가중치 · 계획 · 실적`)를 기준으로 한다.
>
> `SER.SEC.003`은 앞서 「과업지시서에 요구 없음」으로 제외했던 항목이나,
> 시나리오 S2가 성립하려면 필수다. 최소 수준(역할 2종 · 프로젝트 단위 격리)으로 되살린다.

**요구사항 34건 → 38건.**

## 5. 시연 시나리오 (M4 · End-to-End)

위 두 시나리오를 이어 붙이면 그대로 최종 시연이 된다.

| # | 장면 | 시연 내용 |
|---|---|---|
| 1 | 용역업체 연결 | GitHub·Redmine 연결, 필요 권한 안내, 연결 테스트 |
| 2 | WBS 등록 | WBS 파싱 결과 확인, 항목–산출물 연결 |
| 3 | 첫 수집 | 전체 수집 → 표준 모델 적재 → 지표 산출 |
| 4 | 발주기관 확인 | 프로젝트 목록 → 통합 현황 → WBS 드릴다운 |
| 5 | 편차 발견 | 실적 신고 대비 산출물 미제출 경고 |
| 6 | 자연어 질의 | 지연 작업과 사유, 출처 표시 |
| 7 | 확인 요청 | 발주기관 → 용역업체 |
| 8 | 조치 | 용역업체가 자기 도구에서 산출물 push · 이슈 갱신 |
| 9 | 증분 수집 | 변경분만 수집 → 지표 재산정 |
| 10 | 결과 확인 | 진척률 갱신, 조치 완료 확인 |

**9번이 이 시연의 핵심이다.** 8번에서 AX Link를 건드리지 않았는데
9번에서 결과가 갱신된다는 것이 프레임워크의 운영 개념 그 자체다.
