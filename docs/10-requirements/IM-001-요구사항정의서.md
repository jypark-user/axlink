## 0. 작성 원칙

### 0.1 범위 원칙 (과업지시서 근거 필수)

**모든 요구사항은 과업지시서 조항에 근거한다. 근거가 없는 항목은 요구사항으로 세우지 않는다.**

문서의 형식·ID 체계·용어는 발주기관이 제공한 참고자료 「정부과제 품질관리 산출물」의 체계를
참고하여 작성하였다. 해당 자료는 타 사업(스마트 제조 AI 플랫폼)의 산출물 예시이므로,
분류·모듈 약어 등 프로젝트 고유 항목은 본 과업에 맞게 정의하였다.

과업지시서가 정한 PoC 판정 기준은 아래 두 조항이다.

> **Ⅱ.1 나항**: PoC 수준으로 대표 도구·대표 데이터셋을 우선 대상으로 하되 전 항목 연동을 강제하지 않는다.
>
> **Ⅱ.5 나항**: PoC는 프레임워크의 **구조와 운영 개념을 시연할 수 있는 수준**으로 구현하여야 하며,
> **핵심 기능 또는 화면 중심으로 구성할 수 있다.**

즉 판정 기준은 기능 완성도가 아니라 **구조와 운영 개념의 시연 가능성**이다.
구현 방식·내부 설계에 해당하는 사항은 요구사항이 아니라 SW설계서(IM-003, `ARC-###`)에서 정의한다.

### 0.2 ID 체계

참고자료 IM-001의 「요구사항 용어 정리」 체계를 참고한다. 형식은 `<유형>.<모듈>.<일련3자리>`

| 접두 | 명칭 | 본 과업 |
|---|---|---|
| `SFR` | 시스템 기능 요구사항 | 사용 |
| `SWFR` | 소프트웨어 기능 요구사항 | 사용 |
| `SER` | 보안 및 인터페이스 요구사항 | 사용 |
| `QUR` | 품질 요구사항 (ISO/IEC 25010 품질특성) | 사용 |
| `SPR` / `SWPR` | 성능 요구사항 | 미사용. PoC 수준으로 성능 목표치를 설정하지 않음 |

모듈 약어는 참고자료 「작성법」에 따라 **프로젝트마다 정의**한다.

> **근거** Ⅱ.1 가항의 *"비정형 문서(docx, xlsx, hwp, pdf) 수집 및 텍스트·표 구조 추출 기능 구현(한글 문서 포맷 처리 포함)"*

| SW ID | 소프트웨어 요구사항 | 중요도 | 검증 | 시나리오 |

>
> **비고.** 발주기관 제공 참고자료 실측 결과 XLSX의 헤더 행 위치가 파일별로 상이하고
> 상단에 집계 블록이 존재한다. 고정 헤더를 전제하지 않는 추출 방식이 필요하다.

### SFR.WEB.003 확인 요청 및 조치 보고
> 발주기관이 현황 화면의 특정 항목에 확인 요청을 등록하고, 용역업체가 자신의 도구에서 조치한 뒤

> **확인 → 조치 → 재확인**의 관리순환이 시스템 안에서 완결되어야 한다.
> **근거** 착수보고서 관리순환 ⑧ 「확인 및 조치 요청」 · ⑪ 「조치결과 확인」
> ※ 과업지시서 직접 조항은 아니며, 착수보고 제시 운영개념에 근거한다. (협의 안건)
> ※ 대화·메신저 기능이 아니라 **항목 단위 요청 이력 관리**다.

| SW ID | 소프트웨어 요구사항 | 중요도 | 검증 | 시나리오 |
|---|---|---|---|---|
| SWFR.WEB.004 | **요청 등록**: 발주기관은 WBS 항목·산출물·이슈·리스크·지표를 대상으로 확인 요청을 등록할 수 있어야 하며, 시스템은 **등록 시점의 해당 항목 상태**(실적률·산출물 제출 여부·이슈 상태·관련 지표값)를 함께 저장해야 한다 | 필수 | D | S1-5 |
| SWFR.WEB.005 | **조치 보고**: 용역업체는 요청에 대한 조치 결과를 보고할 수 있어야 하며, 시스템은 **요청 등록 시점의 저장 상태와 현재 상태를 비교한 변경 내역**을 보고 내용과 나란히 제시해야 한다 | 필수 | D | S2-6·S1-6 |

> **비고. 등록 시점 상태 저장이 이 기능의 핵심이다.**
> 데이터는 계속 변하므로 요청 시점의 상태를 저장해두지 않으면 조치 여부를 검증할 수 없다.
> 저장해두면 조치 보고 시 아래와 같이 **주장과 관측이 나란히** 제시된다.
>
> ```
> 용역업체 보고    "설계서 초안 제출하였습니다. 규격 협의 8/25 완료."
> 시스템 관측      산출물 SW설계서   미제출 → 제출 확인
>                 WBS 3.2 실적     40% → 85%
>                 이슈 #204        진행중 → 해결
>                 진척률           30% → 39%
> ```
>
> **비고. 범위 경계.** 아래는 포함하지 않는다.
> 자유 대화·스레드 · 첨부파일 · 멘션 · 이메일 알림 · 응답시간 통계 · 요청 분류 체계.

## 부록 B. 대표 질의세트 (확정)

착수보고 부록의 질의세트(안) 7종을 2026-11-23 확정했다. 발주기관이 수행사에 확정을 일임했다.
PoC 검수와 시연은 이 질의세트를 공통 기준으로 쓴다.

문안은 착수보고와 같다. 두 곳만 이 사업의 규약에 맞춰 바꿨다. 요구사항 번호는 `REQ-###`에서
`SWFR.<모듈>.###`로 바뀌었고(ARC-002), 이슈 번호는 도구를 가리는 접두를 붙인다(`#123` → `GH-123`, `RM-123`).

|---|---|---|---|

**PoC 한계로 정한 것**

- 산출물 담당자: ISO/IEC 29110 산출물 항목에는 담당자 칸이 없고 수집하는 도구에도 없다. 표에는 담당자를 보이지 않고, 답은 담당자 정보가 없다고 말한다.
- 지난 보고: 보고 일정은 수집하지 않는다. 질문에 기간이 없으면 7일 전부터 오늘까지로 보고, 그렇게 봤다고 답에 적는다. "최근 2주 동안 바뀐 것"처럼 기간을 적으면 그 기간으로 센다.
- 지연 사유: WBS 에는 사유 칸이 없다. 사유를 적은 문서·이슈가 근거로 걸릴 때만 말한다.
- 마일스톤: 도구(GitHub 마일스톤·Redmine 버전)에 마일스톤이 없는 사업은 없다고 답하고 WBS 일정 질문을 권한다.
